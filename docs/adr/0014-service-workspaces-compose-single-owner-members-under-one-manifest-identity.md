# 14. Service workspaces compose single-owner members under one manifest identity

Date: 2026-07-29

Status: Accepted


## Context

Every `keiro-dsl` command took exactly one `.keiro` file. A service that keeps
each aggregate in its own file — the shape the Kotei repository already uses,
with six-plus `kdsl/*.keiro` files all declaring `context kotei` — had no way to
be validated, scaffolded, or diffed as one service. Separate invocations share
no id, enum, rule, or mapped-type declarations and no resolved type graph, so a
duplicate aggregate name across files, a shared `ProjectId` declared twice, or
an aggregate referencing an enum declared elsewhere were all invisible.

Worse, the artifacts that record what was generated were keyed only by context.
Two same-context specs scaffolded into one output directory overwrite each
other's scaffold record, report each other's modules as stale, and each rewrite
the context-level structural facade from its own partial mapped-type graph.

Splitting a service across files must not become textual inclusion. The
notation's value comes from a checked, whole-service graph; an include or macro
mechanism would make meaning depend on source order and would reintroduce
exactly the ambiguity the checker exists to remove.


## Decision

A **service workspace** is declared by a `.keiro-workspace` manifest file that
names the service and lists its member `.keiro` files explicitly.

The workspace input is a *file*, not repeated CLI flags and not a directory
glob. `diff --since <rev>` must reconstruct the member set as it existed at an
older revision, which only works when membership is itself versioned; a stable
identity must outlive member renames, which flags cannot provide; and globs make
membership filesystem- and order-dependent.

**Identity.** The manifest's `service <name>` value is the workspace's durable
identity. It is the key for workspace-scoped scaffold history and the stamp on
whole-service reports. There is no secondary identity source.

**Membership is a set.** The loader normalizes member paths, canonically sorts
them in codepoint order, and refuses duplicates — including two paths equal
under Unicode case folding, because a case-insensitive filesystem makes them one
file. Source order therefore never changes meaning or generated bytes. Member
paths must be relative, forward-slashed, free of `..` segments, and must name a
`.keiro` spec, so that any member can be reconstructed with
`git show <rev>:<path>`. A manifest may not list another manifest; nesting is
order-sensitive include machinery under another name.

**Members are complete specs; declarations have exactly one owner.** Each
member is a whole, independently parseable `.keiro` file in the unchanged
grammar, and each declares whole aggregates — there is no partial-aggregate
form. A shared id, enum, rule, or mapped declaration belongs to exactly one
member. Two members declaring the same name are refused even when the
declarations are textually identical: identical repeated declarations do not
silently merge. This is the workspace-level reading of ADR 0012's one-schema-
authority rule — a shared declaration must produce exactly one nominal generated
type — and following ADR 0004 the conflict is refused at composition, the
earliest boundary where both owning files are visible, rather than surfacing
later as a scaffold path collision.

**Generated Haskell nominals have one context-level authority.** Source-member
ownership remains diagnostic provenance; it does not select a Haskell type
owner. Every generated service-level id and enum is declared exactly once in
the context `Nominals` module: `<root>.Generated.<Context>.Nominals` for the
prefixed layout, or `<root>.<Context>.Generated.Nominals` for the collocated
layout. The module name depends only on the effective context and layout, so
moving or reordering members cannot split or rename the type. It owns the
generated representation, JSON instances, canonical identity, and textual
wire helpers for the complete declaration set, including declarations with no
current aggregate use.

That same owner emits each generated nominal equality projection tag and
witness. Declaration identity, equality key, and domain therefore cannot split
across aggregate rings or workspace members. Witnesses are emitted only for
declarations used by generated equality expressions, while the nominal
declaration itself remains present even when unused. Consumer-bound nominals
keep their application owner and receive equivalent projection facades derived
from their checked binding rather than a copied generated type.

Each aggregate ring imports only the generated nominals in its resolved use
closure; codecs, expression lowering, and harnesses import their direct uses
from the same authority. An aggregate `Domain` no longer redeclares or
implicitly exports these constructors, so hand-owned modules that construct a
generated id or enum import `Nominals` explicitly. Consumer-bound version-2
nominals remain owned by their declared application module and total binding
under ADR 0012 rather than being copied into the generated owner.

**Context is member-declared and must be unanimous.** The manifest has no
`context` clause: the member grammar already makes `context` mandatory, so a
manifest clause would create a second authority that can only agree or conflict.
Members that disagree are refused, citing every member's context clause.

**The manifest is the module/layout authority, absent-or-exactly-equal.** When
the manifest carries a `module` or `layout` clause it is the workspace
authority, and each member's corresponding clause must be absent or exactly
equal; any disagreement is refused with both clause sites cited. When the
manifest is silent, all members that declare the clause must agree unanimously,
and that value becomes effective. The rule never silently overrides a clause an
author wrote, and never forces existing members to be edited during adoption.

**Composition is semantic, not textual.** Members are composed into one merged
`Spec` on which the existing whole-spec validation runs unchanged, so cross-file
references resolve by name exactly as if the files were one spec and no
node-specific rule can diverge between the single-file and workspace paths.
Multi-file attribution comes from a line map: each member's locations are
relocated into a disjoint line range, so any diagnostic resolves back to one
`(member file, original line)`. Workspace refusals reuse the shared
append-only diagnostic-code registry rather than a parallel enum, and carry a
non-empty list of locations so one refusal can cite every file involved.

The registry boundary is drawn at composition. Refusals that a *composed graph*
produces get codes; refusals raised while *reading the manifest itself* — a
member listed twice, a member path that is absolute or escapes the tree — do
not, because a malformed manifest never reaches the composer, exactly as a
malformed `.keiro` file never reaches the spec validator and carries no code
either. Codes are append-only and can never be retired, so constructors nothing
can emit must not be minted.

**Dispatch is by file extension.** A `FILE` argument ending in
`.keiro-workspace` is a workspace manifest; anything else takes the single-file
path. Content sniffing is rejected: a file's role must not depend on which
parser happens to succeed, and a corrupted manifest must produce a manifest
parse error rather than a confusing `.keiro` one.

**A single `.keiro` file is a one-member workspace.** This holds as a checked
semantic property — checking a one-member workspace yields exactly the
single-spec diagnostics — while the CLI keeps routing bare `.keiro` files
through the pre-existing code path, so existing users' behavior and generated
bytes are unchanged by construction.


## Consequences

- A fleet service can keep one aggregate per file and still be checked,
  scaffolded, and diffed as one contract.
- Adopting a workspace can require real edits: a repository that repeats an
  identical `id RunId prefix=run` in three files must move it to one owning
  member. That is the intended cost of the single-owner rule.
- Adopting the repaired nominal layout adds one generated `Nominals` module and
  overwrites generated aggregate modules to replace embedded declarations with
  imports. Keiro 0.6 did not emit separate aggregate-local nominal modules, so
  there is no old module path to report stale; adoption is a generated-file
  content/layout change, not wire or fold evolution. The scaffolder never edits
  hand-owned files, although their source may need the explicit import noted
  above.
- Whole-workspace "atomicity" means every refusal, collision, parse error, and
  validation error is detected before the first output byte changes, extending
  the existing plan-then-write architecture across members. Staged
  temp-file/rename writes are deliberately excluded as scope orthogonal to
  composition.
- Cross-member generated-path collisions are refused at composition. A
  collision entirely inside one member stays scaffold-time behavior, because
  pulling it forward would change existing single-file behavior.
- Generated equality expressions in different aggregate rings import the same
  declaration-tagged witness from the context authority, so member moves and
  reorderings cannot change nominal equality identity or proof domain.
- Coverage stays reporting-first per ADR 0013: a whole-service report
  aggregates the merged graph's findings and invents no new gate.
- Detecting one source file assigned to two *different* workspaces is out of
  scope for composition, which sees one manifest per invocation. Repository-wide
  manifest discovery would be the dynamic discovery this design excludes; double
  assignment becomes observable instead through workspace-keyed scaffold
  records.


## Alternatives considered

**Repeated `--spec` flags or a directory glob instead of a manifest file.**
Rejected because `diff --since <rev>` cannot reconstruct a flag list or a
historical directory listing from git, and neither provides an identity that
survives member renames.

**First-wins or silent merging of identical duplicate declarations.** Rejected
because it makes the generated nominal type depend on member order and hides a
genuine ownership question; refusal is the only answer that keeps one schema
authority per declaration.

**A `context` clause in the manifest.** Rejected as pure duplication of a fact
the member grammar already makes mandatory, creating a second authority that can
only ever agree or conflict.

**Textual includes or an `import` keyword in the member grammar.** Rejected
because meaning would depend on source order, and because it would make a member
file unreadable in isolation. Members stay complete specs and the manifest stays
a separate file format with its own parser.

**Content sniffing to decide whether a file is a manifest.** Rejected because a
file's role would depend on which parser happened to succeed, turning a
corrupted manifest into a misleading `.keiro` grammar error.

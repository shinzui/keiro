# 30. Declarative router selection is bounded, target-normalized, and coordination-versioned

Date: 2026-08-11

Status: Accepted


## Context

Keiro's original `Router` correctly models effectful, stateless fan-out. Its
application-owned resolver can query a read model and return any list of target
commands. Deterministic command ids make a repeatedly selected physical target
idempotent, but the DSL cannot inspect arbitrary resolver code. It therefore
cannot prove boundedness, stable ordering, duplicate handling, command mapping,
or the distinction between an empty query and a failed query. Changes inside a
resolver hole also have no checked coordination evidence.

The common case is narrower. One typed read-model query returns structural rows;
a pure predicate chooses rows; a scalar path derives a target identity; and a
total mapping constructs one command per chosen row. This subset can be checked
and generated without claiming that Keiro understands application SQL.

Router retries introduce a durable compatibility constraint. A source event may
be attempted against different read-model contents. Existing dispatch ids are
derived from router name, input key, source event id, physical target stream,
and same-stream occurrence. Changing those seed bytes would break duplicate
recognition for work already in flight. Conversely, silently changing recipient
semantics without an operator-visible edition would make a half-old,
half-new fan-out difficult to review.


## Decision

Candidate Keiro DSL Language 5 admits a `resolve declarative` form. It names a
mapped structural query input, a read model returning a list of mapped
structural rows, a checked boolean predicate, a `Text` recipient path, a total
target-command field mapping, a positive maximum recipient count, and closed
empty, failure, redelivery, and partial-dispatch policies. Released Language 4
syntax and generated bytes remain unchanged.

The read-model query body remains application-owned. Keiro verifies the types
and pure computation after that query returns; it does not inspect SQL, prove
query completeness or isolation, or infer database behavior from declarations.
Query and evaluation failures are explicit selection failures. Worker policy
never treats them as a successful empty result, and dead-letter/halt rendering
uses stable bounded application-failure codes without raw backend detail.

Before any target write, the runtime sorts selected commands by physical target
stream, collapses exact duplicate commands for one stream, rejects unequal
commands for one stream, and applies the positive recipient cap to the distinct
normalized targets. Conflict and overflow therefore fail without target writes.
Once dispatch begins, targets retain the existing independent transactions;
successful earlier dispatches remain durable if a later target fails.

The first closed normalization vocabulary is `order = target-stream`,
`dedupe = target-stream`, `redelivery = stable-union`, and
`partial = retain-successes`. A redelivery that first observes `{A, B}` and then
`{B, C}` leaves one durable dispatch each for `{A, B, C}`: `B` is a confirmed
duplicate and `C` is new. This is not exact-set replay and not an all-target
transaction.

The deterministic command-id derivation remains frozen. Selection identity,
declared version, and semantic fingerprint are coordination metadata and do not
enter the dispatch-id seed. The fingerprint is SHA-256 over checked query
identity and types, key, predicate, recipient, command mapping, target and
command, limit, and policies. It excludes comments, formatting, source
locations, selection identity, and declared version.

Every declarative selection has a stable identity and a positive
author-controlled version. Diff classifies identity changes, version decreases,
and changed fingerprints without a version increase as breaking. A fingerprint
change with a version increase and a metadata-only version increase are
advisory. Mapped-type changes that reach membership, recipient identity, or
command content produce coordination evidence alongside ordinary semantic
impact. Scaffold ledgers persist verified identity, version, and fingerprint so
drift remains visible independently of source formatting.

The existing read-model and hole resolver forms remain supported as
`custom-unverified`. Their create-once `RouterHoles` implementations are still
the explicit escape hatch for arbitrary effectful selection. Diff reports a
crossing between verified declarative and custom selection as advisory and does
not invent identity, version, or fingerprint evidence for custom code.


## Consequences

- Common dynamic fan-out can be checked, generated, scaffolded, and exercised
  without a hand-written selection function.
- Every generated fan-out has an explicit finite post-deduplication bound and a
  deterministic order independent of application query order.
- Exact duplicates are harmless, while two different commands for one physical
  stream are rejected before dispatch instead of acquiring order-dependent
  occurrence ids.
- Empty-selection policy is independent from query/evaluation/conflict/overflow
  policy. Failure cannot be acknowledged as empty success.
- Stable-union retry preserves previously committed work but may accumulate
  recipients across query-result drift. Operators must drain in-flight work and
  review replay effects when deploying a semantic selection change.
- Increasing a version documents that review; it deliberately does not reset
  deterministic ids or redispatch earlier targets.
- Per-target dispatch remains non-atomic. Applications requiring an atomic
  decision across streams need a different coordination abstraction rather than
  weakening router semantics.
- SQL, query plans, row freshness, and application migrations remain outside
  the verified boundary.
- The declarative subset may grow only by adding semantics the checker,
  fingerprint, generator, runtime normalization, diff, and conformance surfaces
  can all describe consistently.


## Alternatives considered

- Keep every effectful selection in `RouterHoles`. This preserves flexibility
  but cannot establish the requested boundedness, typed mapping, generated
  behavior, or evolution evidence.
- Include selection identity, version, or fingerprint in deterministic command
  ids. That would turn a coordination annotation into a redispatch mechanism and
  break duplicate recognition for in-flight source events.
- Trust query order or truncate the first N rows. Query order is not a stable
  physical-target contract, and truncation can silently omit recipients. Keiro
  instead normalizes by target and fails explicit overflow.
- Let one of several conflicting commands for a target win. Any winner would be
  order-dependent and could change command identity across attempts, so the
  whole selection fails before writes.
- Dispatch all targets in one database transaction. Target streams may span an
  unbounded operational unit and the existing router contract intentionally
  provides per-target idempotency and partial recovery, not multi-stream
  atomicity.
- Treat the declared read model as proof of SQL behavior. An unrestricted
  application-owned query cannot be verified from its DSL type signature; the
  decision keeps that boundary explicit.

BUG-13 owner reproduction: the three lock helpers from keiro-migrations/migrations/0029.sql (lines 72-214 at a010cea1, loaded verbatim as helpers.sql) against scratch tables shaped for their predicates, on PostgreSQL 18.6 (aarch64-darwin) in the project Nix shell, 2026-11-19. psql, simple query protocol, idle machine.
The gate failure itself was not re-run under load and its failing statement was not captured. These cases show the defect that makes it possible and the two ways a 57014 escapes the helpers' handlers.
Cases 1, 2 and 5: the helpers leave transaction-local statement_timeout and lock_timeout set, so later top-level statements are cancelled outside any handler.
Cases 3 and 4: the relation-lock statement runs under the timeout leaked by the promotion-lock helper. That timer expires later than the lock wait by the time spent between the two helpers; if the statement is still running then, it is cancelled outside the handler. locks_then_tail is a test scaffold that calls the real helper and then keeps the statement running.
Cases 6 and 7: lock_timeout restarts for each lock wait, so the helper alone overshoots a 500 ms budget on two contended relations; only the leaked statement_timeout from the promotion-lock helper holds the attempt to the deadline. This is the unexplained overshoot recorded in IR-47.

-- Test scaffold only: calls the real relation-lock helper, then spends `tail` seconds in the same top-level statement.
CREATE FUNCTION public.locks_then_tail(oids bigint[], d timestamptz, tail float8) RETURNS boolean LANGUAGE plpgsql AS $$
DECLARE r boolean;
BEGIN
  r := keiro.keiro_try_projection_relation_locks_v1(oids, d);
  PERFORM pg_sleep(tail);
  RETURN r;
END $$;

# Close the gap between check and scaffold refusals

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries,
Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.
If durable project context changes, update or create ADRs in docs/adr/ in the same change.


## Purpose / Big Picture

After this work, a green `keiro-dsl check` means `keiro-dsl scaffold` will not refuse:
every problem that is decidable from the spec alone is reported at `check` time, as a
located error with a line number, before any output directory exists. Today that promise
is broken in three ways. An empty aggregate or empty contract passes `check` with `OK`
and then fails scaffold with an unlocated, differently-shaped refusal message. A
single-file spec whose generated module paths collide under case folding passes `check`
entirely and refuses only at scaffold, while the equivalent workspace is caught at
`check`. And the two scaffold planners run the same refusal gates in different orders,
so the first-reported refusal for one defective spec depends on whether it arrived as a
file or as a workspace.

The change is visible at the command line. Checking a spec whose aggregate declares no
transitions prints `error[AggregateEmpty]` with the aggregate's declaration line and
exits non-zero, instead of printing `OK` and deferring the failure to scaffold. Checking
a single file whose nodes claim case-folded-equal generated module paths prints
`error[GeneratedPathCollision]` naming both claiming declarations. No generated byte
changes for any valid spec: this plan changes gates only, never output.

## Surprises & Discoveries

- Observation: the headline gap is narrower than "check misses lowering refusals".
  Of the eleven refusal classes `scaffoldRefusals` raises, nine already have
  unconditional `validateSpec` counterparts (aggregate field/register types via
  `validateAggregateTypes`, mapped register initials via `MappedMissingInitialValue`,
  publisher backoff via `PublisherBackoffInvalid`). Only `AggregateEmpty` and
  `ContractEmpty` have no counterpart at all.
  Evidence: `keiro-dsl/src/Keiro/Dsl/Scaffold.hs` (`scaffoldRefusals`, near line 6292)
  against `keiro-dsl/src/Keiro/Dsl/Validate.hs` (`validateAggregateTypes` near line
  480, `backoffProblemMaybe` near line 2062).

- Observation: workspace `check` already pays the full cost of building the generated
  module set in memory — `checkWorkspace` calls the whole scaffold planner just to
  harvest cross-member `PathCollision` refusals — and then deliberately discards every
  other refusal kind, and even discards collisions whose claimants sit in one member.
  Evidence: `crossMemberCollision` in `keiro-dsl/src/Keiro/Dsl/Workspace.hs` (near
  line 1069) pattern-matches only `PathCollision` and filters on more than one owner.

- Observation: the single-spec planner runs `scaffoldRefusals` twice — once as its own
  early gate and again inside `pureRefusals` — while the workspace planner reaches it
  only through `pureRefusals`. This is why the two paths report a different first
  refusal for the same defective graph.
  Evidence: `planServiceScaffoldWithRuntimePackageAndGoldens` in
  `keiro-dsl/src/Keiro/Dsl/ScaffoldRun.hs` (near line 224) versus
  `planWorkspaceScaffoldWithRuntimePackageAndGoldens` in
  `keiro-dsl/src/Keiro/Dsl/WorkspaceScaffold.hs` (near line 173).

- Observation: five pre-existing tests used aggregates that were deliberately incomplete beyond
  the rule under test: the frontend semantic golden had no commands or events, the eventless
  no-op had no event, two missing-initial fixtures had no commands/events/transitions, and the
  field-alias proof had no transition. The new unconditional diagnostic correctly made those
  shapes fail before their intended assertion.
  Evidence: the first complete run reported 578 examples and exactly five failures headed by
  `AggregateEmpty`. Each source now declares the smallest valid command/event/transition surface
  while preserving its original tested fact; the second complete run passes all 578 examples.


## Decision Log

- Decision: `AggregateEmpty` and `ContractEmpty` are unconditional errors under every
  language version, not gated behind the language-4 `StrictSpecSurfaceValidation`
  closure set.
  Rationale: a spec that cannot scaffold under any version is unconditionally broken;
  ADR 0004's inventory already commits to "values that cannot lower or generate a
  working service are rejected under every language version" and the precedent code
  `PublisherBackoffInvalid` (ExecPlan 180) is ungated for exactly this reason. There
  is no retroactive-tightening risk of the kind that motivated caution in MasterPlan
  29: any spec that ever scaffolded successfully was necessarily non-empty, so no
  previously-scaffoldable spec can newly fail `check`.
  Date: 2026-08-04

- Decision: every gate this plan promotes into `check` refuses only what scaffold
  already refuses. The plan's invariant is "check errors = old check errors plus specs
  scaffold already could not write", proven by the byte-stability and corpus tests.
  Rationale: this is the safe direction of ADR 0004's earliest-sound-boundary rule —
  moving an existing refusal earlier — and it is what makes the change releasable
  without a staged migration.
  Date: 2026-08-04

- Decision: only `AggregateEmpty` and `ContractEmpty` are promoted as new
  `validateSpec` rules; the other nine `scaffoldRefusals` classes keep their existing
  `validateSpec` counterparts, which Milestone 1 pins with parity tests instead of
  duplicating.
  Rationale: the enumeration in Context and Orientation shows the nine are already
  unconditional check errors; re-implementing them would create two sources of truth
  for one rule, the drift this plan exists to close.
  Date: 2026-08-04

- Decision: append exactly seven `DiagnosticCode` values — `AggregateEmpty`,
  `ContractEmpty`, `GeneratedPathCollision`, `GeneratedImportCycle`,
  `BehaviorDerivationInvalid`, `ConformanceFactKeyCollision`, and
  `GeneratedPlanningInvariantViolation` — at the end of the registry in
  `keiro-dsl/src/Keiro/Dsl/Validate.hs`, and emit them through the existing
  `Diagnostic` pipeline.
  Rationale: ADR 0004 makes the code registry append-only and machine-matchable;
  EP-193 owns the `check` CLI/JSON report contract, whose schema tolerates new codes
  without change, so these diagnostics are born into EP-193's report by flowing
  through `validateService`-adjacent rendering rather than a parallel renderer.
  MasterPlan 29's coordination rule applies: this plan adds codes and rules without
  reordering existing ones, and whichever of EP-192/194/197 merges later rebases its
  additions.
  Date: 2026-08-04

- Decision: the canonical gate order is the single-spec planner's order — fold
  surface, then lowering refusals, then module-set construction (facade fact keys),
  then conformance-package planning, then `pureRefusals` over the built module set —
  and the workspace planner adopts it.
  Rationale: spec-level gates that need no module set run before module-set gates
  (cheapest sound evidence first, per ADR 0004), and the single-spec order already
  has that shape. The workspace's first-reported refusal for a spec that violates
  both a fact-key duplicate and a lowering rule changes from the former to the
  latter; the refusal *set* is unchanged, and ADR 0015's detection-before-write
  contract (all preflights complete before any active output changes) is preserved
  because ordering here affects reporting only.
  Date: 2026-08-04

- Decision: `check` runs the planning gates only after `validateService` reports zero
  errors, and single-file `check` evaluates them under the spec-declared context
  (`mkContext Nothing False spec`) with no runtime package and no goldens.
  Rationale: the workspace path already guards planner consultation behind
  validation (`blocksCollisionPlanning` in `Keiro.Dsl.Workspace`) because the planner
  is only designed for validated graphs. Scaffold-time CLI overrides
  (`--module-root`, `--collocate`, `--runtime-package`, goldens) can change module
  placement, but scaffold re-runs the identical shared pipeline under its own
  context, so an override-induced collision still refuses before any write; `check`
  states what the spec itself declares, exactly as workspace `check` derives its
  planner context from the manifest. Adding `check`-side flags is EP-193's surface
  and out of scope here.
  Date: 2026-08-04

- Decision: refusals that a validated spec should never be able to cause — firewall
  breaches, generated-name audit failures, fold-surface resolution failures, residual
  lowering refusals, and conformance-package planning failures — are still surfaced
  at `check`, collapsed under the single code
  `GeneratedPlanningInvariantViolation` rather than one code each.
  Rationale: for a validated spec these indicate a keiro-dsl defect, not an author
  error; they must fail `check` loudly instead of surviving until scaffold, but they
  are not an author-facing vocabulary worth seven more append-only codes. The
  scaffold-side `Refusal` rendering keeps its detailed per-kind text.
  Date: 2026-08-04

- Decision: scaffold keeps every gate it has today. Promotion adds the earlier
  boundary; it never removes the later one.
  Rationale: ADR 0004's stated pattern — "scaffolding reuses the checked resolver as
  defense in depth but is not the first place an author learns" — and both planners
  will consume the one shared pipeline, so the defense cannot drift from the gate.
  Date: 2026-08-04

- Decision: append EP-194's diagnostic codes after `LanguageVersionBelowMinimum`, the current
  registry tail established by completed EP-193, rather than after the older
  `GeneratedHaskellNameChanged` position named when this plan was drafted.
  Rationale: `DiagnosticCode` is append-only. The MasterPlan's merge-order rule requires a later
  child to preserve all constructors already landed by earlier children; the code spellings, not
  obsolete planned positions, are the stable interface.
  Date: 2026-08-05

## Context and Orientation

keiro-dsl is the typed specification toolchain in this repository: an author writes a
`.keiro` file (or a `.keiro-workspace` manifest composing several member files into one
service), runs `keiro-dsl check` to validate it, and runs `keiro-dsl scaffold` to
generate deterministic Haskell modules plus hand-owned "create-once" Hole modules. Two
different failure vocabularies exist along that path, and this plan is about the seam
between them.

A *diagnostic* is a located, machine-coded validation result: the `Diagnostic` record
in `keiro-dsl/src/Keiro/Dsl/Validate.hs` carries a line number, a severity, a stable
`DiagnosticCode` (an append-only enum, per
[ADR 0004](../adr/0004-evolution-changes-are-gated-at-the-earliest-sound-boundary.md)),
related locations, and a message; `renderDiagnostic` prints it as
`<file>:<line>: error[Code]: message`. `validateService` (and its legacy wrapper
`validateSpec`) produces diagnostics; the `check` command prints them and exits
non-zero on any error.

A *refusal* is a scaffold-stage pre-write failure: the `Refusal` type in
`keiro-dsl/src/Keiro/Dsl/ScaffoldRun.hs` (constructors such as `PathCollision`,
`ImportCycle`, `FirewallBreach`, `LoweringRefusal`, `BehaviorRefusal`,
`FoldSurfaceRefusal`, `DuplicateConformanceFactKeys`). A refusal carries no write set,
so it cannot be executed by accident, but it also carries no `DiagnosticCode` and no
spec line number; `renderRefusals` prints free-form text such as
`error: scaffold cannot lower this spec faithfully -- refusing; nothing was written`.
An author who saw `check` print `OK` then meets this differently-shaped, unlocated
text is the user-visible defect this plan fixes.

*Planning* is the pure phase of scaffolding: `planServiceScaffoldWithRuntimePackageAndGoldens`
in `ScaffoldRun.hs` (near line 224) either returns the exact module write set or a
non-empty refusal list, with no IO. *Execution* (`executeScaffold` and relatives) then
performs filesystem preflights — generated-banner protection, golden-root divergence,
name-migration authorization, stale-evidence reporting per
[ADR 0015](../adr/0015-workspace-scaffold-history-is-workspace-keyed-with-attributable-adoption.md)
— and writes. Only planning is in scope here; execution-time preflights depend on the
filesystem and correctly stay scaffold-only.

### The three verified gaps

First, empty nodes. `scaffoldRefusals` in `keiro-dsl/src/Keiro/Dsl/Scaffold.hs`
(near line 6292) raises `AggregateEmpty` when an aggregate has no command, no event,
or no transition, and `ContractEmpty` when a contract declares no events — as
unlocated refusal text only. `validateSpec` has no counterpart rule, so `check` prints
`OK` for both shapes.

Second, single-file `check` skips the pure planning gates that workspace `check`
runs. `pureRefusals` (`ScaffoldRun.hs`, near line 255) is the shared pure gate set
over a built module list: case-folded generated-module-path collisions
(`collisionRefusals`, near line 480, which groups on `T.toCaseFold` of the whole file
path — strictly stronger than `check`'s normalized-occurrence collision detection in
`validateNames`, which inventories logical names, not every emitted file path),
generated/consumer import cycles and consumer-module collisions
(`dependencyRefusals`), firewall breaches, generated-name audit violations, lowering
refusals, and behavior-derivation refusals (`deriveBehaviorRequirements` in
`keiro-dsl/src/Keiro/Dsl/BehaviorCoverage.hs`, a pure function). Workspace `check`
deliberately consults this planner — `checkWorkspace` in
`keiro-dsl/src/Keiro/Dsl/Workspace.hs` (near line 1066) calls
`planServiceScaffoldWithRuntimePackageAndGoldens` on the validated merged graph — but
then harvests only `PathCollision` refusals whose claimants span more than one member,
mapping them to the `WorkspacePathCollision` diagnostic. Single-file `check`
(`app/Main.hs`, the `run (Check ...)` clause near line 229) never consults planning at
all: it runs `validateService`, prints `OK`, and stops.

Third, gate order. The single-spec planner checks fold surface, then
`scaffoldRefusals`, then facade fact-key duplicates, then `pureRefusals`
(`ScaffoldRun.hs` near lines 224–235). The workspace planner checks facade fact-key
duplicates (inside `workspaceModules`), then conformance-package planning, then fold
surface, then `pureRefusals`
(`keiro-dsl/src/Keiro/Dsl/WorkspaceScaffold.hs`, near lines 173–191). Same gates,
different first-reported refusal — which contradicts the spirit of
[ADR 0014](../adr/0014-service-workspaces-compose-single-owner-members-under-one-manifest-identity.md),
under which a single spec is semantically a one-member workspace and both paths must
produce identical semantic results.

### Complete enumeration of `scaffoldRefusals`

Every message class the function can emit, read from `Scaffold.hs` near lines
6292–6359, with its classification. All eleven are *graph-decidable*: pure functions
of the parsed `Spec` with no filesystem dependence. None is filesystem-dependent —
the filesystem-dependent refusals (`MissingGeneratedBanner`,
`GoldenRootDivergence`, `NameMigrationRequired`, `NameMigrationRefusal`) live in
execution, not in `scaffoldRefusals`, and stay scaffold-only.

`AggregateEmpty` — no command, event, or transition. No `check` counterpart.
**Promoted by this plan.**

`ContractEmpty` — contract with no events. No `check` counterpart. **Promoted by
this plan.**

`FieldTypeUnrepresentable` (command/event fields) and `RegTypeUnsupported`,
`RegTextInitialNotQuoted`, `RegInitialNotEnumCtor`, `RegInitialInvalidLiteral`
(registers) — already refused unconditionally by `validateAggregateTypes`
(`Validate.hs` near line 480) as `AggregateTypeUnknown`,
`AggregateTypeUnsupportedAtUse`, and `AggregateRegisterInitialInvalid` at the owning
declaration line. Defense in depth; parity pinned in Milestone 1.

`MappedRegisterInitialMissing` — already refused unconditionally as
`MappedMissingInitialValue` (`Validate.hs` near line 1056). Defense in depth.

`BackoffInvalidExponential`, `BackoffExponentialIncomplete`, `BackoffUnknownKind` —
already refused unconditionally as `PublisherBackoffInvalid` via
`backoffProblemMaybe` (`Validate.hs` near lines 2047–2072), whose arithmetic matches
the scaffold-side `windowSeconds` checks. Defense in depth.

### Milestone 2: One shared planning-gate pipeline for both check and both scaffold paths

Scope: after this milestone, one pure function owns the gate sequence; both scaffold
planners call it, both `check` paths report its refusals as located diagnostics, the
canonical order is pinned by a test, and a single-file spec with a case-folded
module-path collision fails `check`.

First, factor the pipeline. In `keiro-dsl/src/Keiro/Dsl/ScaffoldRun.hs`, introduce:

```haskell
-- | The one documented pure gate sequence. Both scaffold planners and both
-- check paths consume this; the order of first-reported refusal is part of
-- the deterministic output contract and is pinned by test.
planningGatePipeline ::
  Context ->
  CheckedService ->
  -- | Built module set, or the refusals of building it (facade fact keys).
  Either [Refusal] [ScaffoldModule] ->
  -- | Conformance-package planning result ('Right ()' when not requested).
  Either [Refusal] () ->
  Either [Refusal] [ScaffoldModule]
```

The body runs, in this order and stopping at the first non-empty result: the
aggregate fold-surface gate (`aggregateFoldSurfaceForService` over every aggregate);
`scaffoldRefusals` as `LoweringRefusal`; the module-set argument; the package-plan
argument; then `pureRefusals ctx spec modules` over the built set, whose internal
order (path collisions, dependency collisions/cycles, firewall, naming audit,
lowering again, behavior derivation) is unchanged. Rewrite
`planServiceScaffoldWithRuntimePackageAndGoldens` as a thin call: module-set argument
is the stamped `scaffoldServiceModulesWithGoldens` output plus the facade from
`serviceHarnessModule` (mapping duplicate fact keys to
`DuplicateConformanceFactKeys` exactly as today), package-plan argument `Right ()`.
Rewrite `planWorkspaceScaffoldWithRuntimePackageAndGoldens` in
`keiro-dsl/src/Keiro/Dsl/WorkspaceScaffold.hs` to build its tagged module list with
`workspaceModules` as today, pass `fmap (map fst)` of it as the module-set argument
and its `planConformancePackage` result (mapped to `ConformancePackageRefusal`) as
the package-plan argument, and construct `WorkspacePlan` from the tagged list only
when the pipeline returns `Right`. After this refactor neither planner may contain a
gate call outside `planningGatePipeline`; the compiler and the order-pinning test
below keep them from drifting.

Second, map refusals to diagnostics. Append the five planning codes
(`GeneratedPathCollision`, `GeneratedImportCycle`, `BehaviorDerivationInvalid`,
`ConformanceFactKeyCollision`, `GeneratedPlanningInvariantViolation`) to
`DiagnosticCode`. In `ScaffoldRun.hs` (which may import `Keiro.Dsl.Validate`; Validate
imports nothing from ScaffoldRun, so no cycle), add:

```haskell
-- | Present pure planning refusals as located check diagnostics. Line
-- attribution uses the "(line N)" evidence already embedded in module
-- origins; refusals with no source anchor report line 1 with the module
-- path in the message.
planningRefusalDiagnostics :: [Refusal] -> [Diagnostic]
```

with this mapping. `PathCollision path origins` becomes one `GeneratedPathCollision`
error whose primary line is the latest origin line among the claimants and whose
`relatedLocations` carry every other claimant (`claimed here by <origin>`); the
message names the colliding path and states that on a case-insensitive filesystem the
files are one file. Reuse the origin-line parser that
`Keiro.Dsl.Workspace.crossMemberCollision` already applies to origins (move that small
helper into `ScaffoldRun.hs` and re-export it rather than duplicating it).
`ImportCycle` becomes `GeneratedImportCycle` at line 1, message carrying the cycle
`a -> b -> a` and the existing remediation sentence about leaf binding modules.
`BehaviorRefusal` becomes `BehaviorDerivationInvalid`, one diagnostic per derivation
error, at the error's source line when `BehaviorDerivationError` exposes one and line
1 otherwise. `DuplicateConformanceFactKeys` becomes `ConformanceFactKeyCollision`,
one per duplicate key. Everything else the pure planner can return —
`FirewallBreach`, `GeneratedNameInvariantViolation`, `FoldSurfaceRefusal`,
`ConformancePackageRefusal`, and any residual `LoweringRefusal` (residual because
Milestone 1 plus the pre-existing counterparts mean a validated spec should never
reach one) — becomes `GeneratedPlanningInvariantViolation` at line 1 with the
rendered refusal text folded into the message (Decision Log). Execution-only refusal
constructors (`MissingGeneratedBanner`, `GoldenRootDivergence`,
`NameMigrationRequired`, `NameMigrationRefusal`, `SemanticContractMismatch`) cannot
be produced by the pure planner; map them to `GeneratedPlanningInvariantViolation`
defensively so the function is total.

Third, wire `check`. Add to `ScaffoldRun.hs` the semantic core both the CLI and tests
use, so tests exercise the real check path:

```haskell
-- | validateService plus, when validation is error-free, the shared
-- planning gates under the given context. This is the complete semantic
-- content of `keiro-dsl check`.
checkServiceDiagnostics :: Maybe RuntimePackageName -> Context -> CheckedService -> [Diagnostic]
```

It returns `validateService service` unchanged when any error is present (the
planner only sees validated graphs — the guard workspace `check` already applies via
`blocksCollisionPlanning`), and otherwise appends
`planningRefusalDiagnostics` of the pipeline run with no goldens. In `app/Main.hs`,
the single-file `run (Check ...)` clause replaces its `validateService` call with
`checkServiceDiagnostics Nothing (mkContext Nothing False spec) service`, keeping the
existing printing, `--emit`, `--explain-bindings`, coverage, and `OK` behavior —
`OK` now additionally attests the planning gates. In `Keiro.Dsl.Workspace`, replace
the `PathCollision`-only harvest in `collisionRefusals`: run the planner as today,

## Idempotence and Recovery

Every step is repeatable. The promoted rules and the gate pipeline are pure functions
of the checked graph, so re-running tests or `check` cannot drift; re-running the
closure commands is safe. The only filesystem effects in this plan are test-created
temporary directories and the explicitly created `proof_dir`; remove only those.

The edits are additive (appended enum constructors, new functions, one refactored
call path per planner). If a milestone fails midway, the tree still builds gate-wise:
Milestone 1 stands alone; Milestone 2's pipeline refactor should be committed only
when both planners compile against it and the parity tests pass. To back out, revert
only the files this plan touched with an explicit patch; never reset the worktree.
Because `DiagnosticCode` is append-only, a partial landing must not ship a code that
no rule emits — land the code and its rule in the same commit.

The plan changes no database, no wire byte, no fold fingerprint, and no persisted
identity; releasing it cannot strand any existing stream, and the strongest external
effect is that a spec which could never scaffold now fails one command earlier.

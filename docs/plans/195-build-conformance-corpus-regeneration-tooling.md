# Build conformance corpus regeneration tooling

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries,
Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.
If durable project context changes, update or create ADRs in docs/adr/ in the same change.


## Purpose / Big Picture

After this work, an intentional generator-output change becomes a one-command corpus
refresh reviewed as an ordinary diff. Today the repository commits the complete output of
`keiro-dsl scaffold` for dozens of fixture services — the "conformance corpus" — and
compiles it in 35 cabal test suites, so any change to generated bytes requires a human to
re-run every historical scaffold command by hand, re-commit every tree, and reconcile the
cabal module inventories. History shows the cost: whole-corpus migration commits such as
`cd22e7f2` ("test(dsl): migrate the stable fixture corpus") and `86b2dfa6` ("feat(dsl):
migrate generated naming corpus", 113 files changed) accompany every output-affecting
plan. That churn tax fossilizes known output defects because improving them is expensive;
MasterPlan 29's Phase 3 polish plan (EP-196) hard-depends on removing it.

This plan delivers a regeneration driver (`keiro-dsl-corpus-regen`) that replays every
committed scaffold through the public `keiro-dsl` CLI with the exact flags each tree was
created with, overwrites only banner-recognized generated files, preserves create-once
hand-owned modules exactly as the scaffolder does, updates the plain `.golden` fixture
files through the tests that own them, verifies the cabal module inventories against the
regenerated trees, and finishes with a git diff summary for human review. It never
commits. Its acceptance is conservative and observable: deliberately corrupt
one generated file and the tool restores it byte-identically; put a sentinel edit into a
create-once Hole module and it survives untouched. Implementation discovered that the
current generator already differs from the committed corpus in 387 files; EP-196 owns
that planned batched refresh and now also owns activating the zero-diff policy gate once
the baseline can pass it.

## Surprises & Discoveries

- Observation: Scaffold records already carry most of the provenance a regeneration
  manifest needs. Every single-spec record stores the spec path relativized against
  `git rev-parse --show-toplevel` (so it is repository-relative and cwd-independent),
  plus `module-root:` and `layout:` lines that determine the `--module-root` and
  `--collocate` flags.
  Evidence: `keiro-dsl/app/Main.hs` lines 317–323 (`makeRelative repoRoot absFp`) and
  the `spec:` header in every `keiro-dsl-scaffold-record.*.txt`.

- Observation: Three histories are not reproducible from records alone. The
  `test/conformance-skeletons` record says `spec: /dev/stdin` (the tree is eight
  successive stdin scaffolds of `keiro-dsl new <kind>` output, and only the last run's
  record survives because all eight share context `my-service`); workspace records store
  only the manifest basename (`manifest: service.keiro-workspace`), not its repository
  location; and the structural tree's codec-comparison module is emitted by opt-in flags
  that are deliberately not recorded ("opt-in tooling output and is not part of the
  production scaffold record", `keiro-dsl/keiro-dsl.cabal` comment above
  `keiro-dsl-conformance-codec-compare`). This forces the hybrid manifest design in the
  Decision Log.

- Observation: The committed corpus embeds no hand-captured golden payloads. The files
  under `keiro-dsl/test/golden-payloads/` are consumed only by in-test scaffolds in
  `keiro-dsl/test/Main.hs`; no committed tree contains their bytes (verified by grepping
  the distinctive `rsv_01hzy3v7q2e8kaw2m5x0d41n9c` value), and no `golden-payloads`
  directory exists beside any fixture spec, so the CLI's default golden root resolves to
  nothing for every committed tree. Regeneration therefore needs no `--goldens` flag.

- Observation: The cabal inventories deliberately compile subsets, so "generate the
  stanzas" is unsound. `keiro-dsl-conformance-codec-compare` compiles 10 hand-picked
  modules across two trees, the `keiro-dsl-codec-bench` benchmark compiles another
  subset of the structural tree, and
  `Generated.StructuralConformance.ArtifactCatalog.BehaviorContract` is committed and
  recorded but compiled by no component at all today. See the Decision Log entry
  choosing a checker with exemptions over stanza generation.

- Observation: The plan's record-derived discovery could not work in a clean checkout as
  drafted. `.gitignore` ignores every `keiro-dsl-scaffold-record.*.txt` and
  `keiro-dsl-manifest.*.txt`; only the newsurface pair was already force-tracked. The local
  tree also held one stale nested skeleton pair under
  `keiro-dsl/test/conformance-skeletons/SkelAggregate/`, while the authoritative eight-run
  skeleton history is the root pair whose last writer is `SkelWorkflow`.
  Evidence: `git ls-files keiro-dsl/test | rg 'keiro-dsl-scaffold-record'` returned one
  path, while the filesystem held 35 records; excluding the nested stale pair leaves the
  intended 34 histories.

- Observation: Single-spec and workspace scaffold reports have deliberately different
  idempotence vocabulary. The single-spec `writeModule` always writes a recognized
  Generated target and reports `(overwritten)`; only the workspace path compares bytes
  before writing and can report `(unchanged)`. Git still reports zero byte diff after the
  representative single-spec regeneration.
  Evidence: `WriteDisposition`'s comment and `writeModule` in
  `keiro-dsl/src/Keiro/Dsl/ScaffoldRun.hs` state this explicitly; the Milestone 1 run
  reported 12 overwritten Generated modules and left every tracked generated module
  byte-identical.

- Observation: The record/disk relation has two historical exceptions that need narrower
  provenance than a directory-wide waiver. The eight skeleton invocations share one
  last-writer-wins record, so each manifest row claims only its module-root subtree. The
  old newsurface facade predates the current record grammar and requires one
  `legacy-generated` path that fails once it becomes recorded or ceases to be generated.
  Evidence: the representative consistency run passes with both stale checks active.

- Observation: Cabal's checked component roots compile selected output surfaces, not every
  generated file in each scaffold tree. Resolving `main-is`, declared modules, autogen
  modules, and recursive local imports found 108 generated paths outside all component
  closures. Exactly one is the previously audited unexpected structural BehaviorContract;
  the other 107 are deliberate non-target surfaces in narrow legacy suites.
  Evidence: all 108 paths are explicit `uncompiled-generated` rows; removing the structural
  ReplayAudit declaration produces one precise uncovered-path failure, and restoring it
  passes.

- Observation: The first honest 41-invocation replay is not byte-idempotent against the
  current checkout. It changes 387 files (944 insertions, 417 deletions), including the
  0.9-to-0.10 banner transition, additive record/manifest rows, and generated facts already
  assigned to EP-196's single corpus refresh. All 387 tool-produced changes were restored.
  This invalidates the planned immediate CI gate but validates the driver's ability to
  enumerate and replay the complete corpus.


## Decision Log

- Decision: Derive the corpus inventory from the committed scaffold records, with one
  small checked-in supplement file (`keiro-dsl/test/conformance-corpus-manifest.txt`)
  for what the trees cannot state: the eight ordered skeleton invocations, the two
  workspace manifest locations, per-tree extra flags (the structural codec-comparison
  pair), and the uncompiled-generated-module exemption list.
  Rationale: Records already store repository-relative spec paths, module roots, and
  layout, and they are regenerated by every run, so deriving from them removes double
  bookkeeping — a new conformance tree joins the corpus the moment its record is
  committed. Hand-maintaining only the three unrecoverable facts keeps the supplement
  a dozen lines instead of a forty-entry mirror that would drift.
  Date: 2026-08-04

- Decision: Force-track the 34 authoritative scaffold-record and build-manifest pairs as
  corpus evidence, while preserving `.gitignore` for scaffold metadata outside the test
  corpus. Do not track the stale nested `conformance-skeletons/SkelAggregate` pair.
  Rationale: `git ls-files` is deliberately the driver's discovery boundary, so every
  provenance record it needs must exist in a clean checkout. Removing the global ignore
  rule would make consumer-local scaffold metadata appear as ordinary untracked files;
  force-tracking the bounded corpus evidence preserves both behaviors. The root skeleton
  record is authoritative because the declared eight invocations share one output and
  `SkelWorkflow` must be the final writer.
  Date: 2026-08-05

- Decision: Define corpus idempotence by resulting tracked bytes, while retaining the
  public CLI's existing per-path dispositions as supporting evidence rather than requiring
  `(unchanged)` from single-spec runs.
  Rationale: The driver must replay the public CLI without forking its write semantics.
  Workspace runs prove no-write idempotence through `(unchanged)`; single-spec runs prove
  byte idempotence through an empty Git diff after their expected `(overwritten)` report.
  Changing single-spec write behavior is outside this tooling plan.
  Date: 2026-08-05

- Decision: Implement the driver as a Haskell executable in a new local package
  `keiro-dsl-corpus-regen` under `keiro-dsl/tools/corpus-regen/`, not as a shell script
  and not as a second executable in the `keiro-dsl` package; thin Justfile recipes and
  one policy shell script wrap it.
  Rationale: The driver must parse scaffold and workspace records — and the real
  parsers already exist as exposed library modules (`Keiro.Dsl.ScaffoldRecord`,
  `Keiro.Dsl.WorkspaceRecord`), so a Haskell driver can never drift from the record
  grammar the way a shell re-parser would. The cabal-inventory check needs genuine
  `.cabal` parsing (`Cabal-syntax`), which bash cannot do precisely. The repository
  convention keeps the `keiro-dsl` package at exactly one executable and uses a
  separate local package for extra binaries (stated in
  `keiro-dsl/test/keiro-dsl-codec-compare-artifact-info.cabal`), so a new local
  package is the sanctioned home. Shell remains for the CI entry point,
  matching `scripts/check-extension-policy.sh` conventions.
  Date: 2026-08-04

- Decision: The cabal-inventory deliverable is a consistency checker that fails with a
  precise per-component diff, not generation of the `other-modules` stanzas; generated
  modules compiled by no component must appear in an explicit exemption list in the
  supplement manifest to pass.
  Rationale: Generation was preferred in principle but is infeasible here: corpus
  components deliberately compile subsets (the codec-compare suite and the benchmark
  pick modules out of the structural tree), the stanzas interleave with hand-written
  comments and per-suite `build-depends`, and one recorded generated module
  (`ArtifactCatalog/BehaviorContract.hs` in the structural tree) is compiled nowhere
  today. A generator would either flatten those deliberate choices or have to model
  them, gaining nothing over a checker whose failure output is the exact edit to make.
  The exemption list makes today's known gap visible and reviewable instead of silent,
  and hands it to EP-196 as an explicit finding.
  Date: 2026-08-04

- Decision: `.golden` updates run through the tests that own them: a
  `KEIRO_DSL_UPDATE_GOLDENS=1` accept mode added to a shared helper in
  `keiro-dsl/test/Main.hs`, invoked by the driver's `update-goldens` subcommand.
  Rationale: The six golden comparisons are produced by library renderers
  (`renderFoldBaseline`, diff finding/explain renderers, the diff-report JSON) inside
  `keiro-dsl/test/Main.hs`; no public CLI invocation reproduces those exact texts. Any
  external re-implementation would drift from what the assertions compare. Writing the
  accepted bytes from inside the same assertion site guarantees the updated golden is
  exactly what the test verifies.
  Date: 2026-08-04

- Decision: `check` mode refuses to start when corpus paths are already dirty, then
  regenerates in place and fails on any resulting diff; it does not regenerate into a
  temporary copy.
  Rationale: Records relativize spec paths against the out-directory's git root, so
  scaffolding into a copy outside the repository would change record bytes and
  manufacture false diffs. Refusing a dirty corpus keeps tool output from mixing with
  uncommitted human work, and on failure the drift left in the working tree is exactly
  the diff a reviewer needs — the tool never commits, so nothing is lost.
  Date: 2026-08-04

- Decision: Skeleton invocations execute in the fixed order of
  `skeletonModuleRoots` in `keiro-dsl/test/Main.hs` (aggregate, process, router,
  contract, intake, emit, workqueue, workflow), and the supplement manifest preserves
  that order.
  Rationale: All eight skeleton scaffolds share context `my-service` in one directory,
  so each run overwrites the shared record and only the last survives. The committed
  record says `module-root: SkelWorkflow`; byte-identical regeneration therefore
  requires workflow to run last. Order is part of the corpus contract and must be
  declarative, not incidental.
  Date: 2026-08-04

- Decision: Amend ADR 0015 with the clean-checkout conformance-history rule discovered
  during implementation; otherwise this plan enforces existing decisions rather than
  selecting a new product architecture.
  Rationale: The create-once/overwriteable and banner-provenance boundaries were already
  durable, but record-derived regeneration adds one repository-level consequence: every
  committed conformance history must force-track its authoritative record/manifest twins
  even though ordinary consumer metadata remains ignored. Without that rule, the same
  checkout can regenerate while CI cannot.
  Date: 2026-08-05 (revises the 2026-08-04 no-ADR expectation after implementation evidence)

- Decision: Out of scope, recorded as future work: changing any generated output byte
  (EP-196 owns the single reviewed refresh), reducing the 418
  `T.isInfixOf` substring assertions in `keiro-dsl/test/Main.hs`, and hardening the sed
  patterns in the twelve `keiro-dsl/test/*.sh` mutation scripts.
  Rationale: EP-196 owns output changes and will spend that churn once, through this
  tool; assertion and mutation-script robustness are independent maintainability items
  that would dilute this plan's single observable guarantee.
  Date: 2026-08-04

- Decision: Close EP-195 with the regeneration, consistency, and golden tooling, but move
  `check` mode and repository-policy activation to EP-196 Milestone 4 immediately after
  its already-owned corpus refresh.
  Rationale: Wiring a gate that necessarily changes 387 committed files would leave
  `just verify` red. Accepting those bytes in EP-195 would spend the same whole-corpus
  churn again when EP-196 changes the templates. The driver is independently usable and
  is the hard-dependency deliverable EP-196 needs; activating the gate after that one
  refresh preserves both the batching decision and a green repository.
  Date: 2026-08-05

## Context and Orientation

### What the conformance corpus is

`keiro-dsl` (package directory `keiro-dsl/`, library under `keiro-dsl/src/`, single CLI
executable built from `keiro-dsl/app/Main.hs`) compiles `.keiro` service specifications
into Haskell modules. The repository proves the generator against real code by
committing complete scaffold outputs — generated modules, hand-filled "Hole" modules,
scaffold records, and build manifests — and compiling them in dedicated cabal test
suites. This committed material is the *conformance corpus*.

Two file classes matter (defined by
[ADR 0015](../adr/0015-workspace-scaffold-history-is-workspace-keyed-with-attributable-adoption.md)
and
[ADR 0019](../adr/0019-generated-haskell-has-an-explicit-edition-and-local-extension-contract.md)):

- *Overwriteable generated files* carry a provenance banner as an exact line, currently
  shaped `-- @generated by keiro-dsl <package-version> (language keiro-dsl <effective
  version>) from <stable-node-origin>; do not edit.` (a historical fixed line is also
  recognized; see `isGeneratedBannerLine` in `keiro-dsl/src/Keiro/Dsl/Scaffold.hs`,
  around line 6249). The single-spec path overwrites these deterministically; the
  workspace path compares bytes first and reports `(unchanged)` without writing when they
  match. Both paths *refuse the whole run*
  (`MissingGeneratedBanner`, `keiro-dsl/src/Keiro/Dsl/ScaffoldRun.hs` around line 540)
  if a planned generated path exists without the banner, unless
  `--force-generated-overwrite` is passed.
- *Create-once files* (Hole modules such as `BehaviorHoles.hs`, application `Holes.hs`,
  bindings skeletons, conformance `Expectations.hs`, and the hand-owned runtime cabal
  file) are written only when absent; later runs report `(skipped: already present)`
  and never rewrite them. They are hand-owned application code.

A third banner exists: the opt-in codec-comparison module begins
`-- @generated by keiro-dsl codec comparison; non-production migration evidence; do not
edit.` and has its own banner-guarded overwrite preflight (`preflightComparison`,
`keiro-dsl/app/Main.hs` around line 739).

Every scaffold also writes a *scaffold record* — `keiro-dsl-scaffold-record.<context>.txt`
for single-spec runs, `keiro-dsl-scaffold-record.workspace.<service>.txt` for workspace
runs — listing the spec path (repository-relative), `module-root:`, `layout:`
(`prefixed` or `collocated`), and every `generated`/`hole` path, plus a build-manifest
twin (`keiro-dsl-manifest.*.txt`). Records are themselves committed corpus bytes and
must reproduce exactly.

### Why regeneration is currently expensive

The repository has no accept mode, regeneration script, or fixture-refresh tool of any
kind: nothing outside the twelve mutation shell scripts in `keiro-dsl/test/*.sh` (which
mutate copies to prove tests catch defects, and never refresh committed trees), and no
accept or regen hook in `keiro-dsl/test/Main.hs` or `keiro-dsl/app/Main.hs`. An
intentional generator-output change therefore means: re-run 41 historical scaffold
invocations by hand with the right flags, review and re-commit every tree, adjust the
`other-modules` inventories in the 1117-line `keiro-dsl/keiro-dsl.cabal` when layout
shifts, revisit as needed the 418 `T.isInfixOf` substring assertions in the 9215-line
`keiro-dsl/test/Main.hs`, and hand-edit six golden files. The corpus discipline itself
is good — banners, refusal of bannerless overwrites, create-once preservation, semantic
compiled suites, and normalized byte comparisons (`normalizeGenerated` in
`keiro-dsl/test/Main.hs` compares imports and pragmas as sets) all already exist. What
is missing is exactly one driver that replays the recorded provenance.

### Relevant ADRs

The local ADR scan found four relevant accepted decisions; no ADR covers regeneration
tooling itself (none is expected to — see the Decision Log):

- [ADR 0015](../adr/0015-workspace-scaffold-history-is-workspace-keyed-with-attributable-adoption.md)
  — the create-once versus overwriteable boundary, the two recognized banner forms,
  workspace-keyed records, observable idempotence (`(unchanged)` reporting), and the
  rule that stale evidence never authorizes deletion. The tool must inherit all of this
  by driving the public CLI rather than re-implementing writes.
- [ADR 0019](../adr/0019-generated-haskell-has-an-explicit-edition-and-local-extension-contract.md)
  — the generated compilation contract and the rule that only overwriteable `Generated`
  modules are ever regenerated; create-once modules stay hand-owned.
- [ADR 0004](../adr/0004-evolution-changes-are-gated-at-the-earliest-sound-boundary.md)
  — failures surface at the earliest boundary with enough evidence; the corpus policy
  script applies the same stance to corpus drift (refused at `verify`/CI, not at
  release).
- [ADR 0014](../adr/0014-service-workspaces-compose-single-owner-members-under-one-manifest-identity.md)
  — the workspace manifest is the authority for service name, module root, layout, and
  runtime package, which is why workspace regeneration needs no CLI flags.

Cross-repository context: none required. The tool touches no Keiki interface directly;
the corpus suites' dependency on `mori://shinzui/keiki/packages/keiki` is unchanged.


## Plan of Work

### Milestone 1: Manifest, driver package, and one suite regenerated with zero diff

This milestone creates the supplement manifest and the driver package, and proves the
core loop on a single representative history (`test/conformance-behavior-complete`,
which exercises generated modules, create-once Holes and BehaviorHoles, a record, and a

1. Resolve the repository root with `git rev-parse --show-toplevel` and treat all paths

2. Load and validate the supplement manifest.
3. Discover every committed scaffold record with
   `git ls-files 'keiro-dsl/test/**/keiro-dsl-scaffold-record*.txt'` and parse each.
   Derive one invocation per single-spec record: `scaffold <recSpecPath> --out

   `(none)`, `--collocate` when its layout is `collocated`, and any `extra-args` row
   for that directory. A record whose spec is `/dev/stdin` must be claimed by skeleton
   rows for the same directory (error otherwise, and error if skeleton rows exist for a
   directory with no such record); a workspace record must be claimed by a `workspace`
   row whose out-dir matches (error otherwise, in both directions). This
   cross-validation is what keeps the supplement honest against the trees.
4. Resolve the `keiro-dsl` binary once via `cabal list-bin keiro-dsl` (after `cabal
   build keiro-dsl exe:keiro-dsl`) and execute invocations directly, in deterministic
   order: all single and workspace invocations sorted by out-dir, then the skeleton
   rows in manifest order. Skeleton invocations run `keiro-dsl new <kind>`, capture
   stdout, and feed it as the child's stdin to `keiro-dsl scaffold /dev/stdin --out
   <dir> --module-root <Root>`. Stream each invocation's stderr report (the
   `(overwritten)` / `(unchanged)` / `(skipped: already present)` lines) to the operator.
5. A non-zero exit from any invocation (for example a `MissingGeneratedBanner` refusal)
   stops the run with the CLI's own message; the tool adds only which invocation
   failed. It never passes `--force-generated-overwrite`.
6. Finish by printing `git status --porcelain --` and `git diff --stat --` over the
   corpus paths (every derived out-dir plus `keiro-dsl/test/fixtures`), with a closing
   line telling the operator to review and commit; the tool itself never invokes
   `git add` or `git commit`.

## Idempotence and Recovery

The whole design is idempotence-first. Regeneration drives the public scaffolder, whose
workspace write path compares bytes and reports `(unchanged)` without writing, whose
single-spec path overwrites with deterministic identical bytes, and whose shared boundary
skips create-once files and refuses bannerless targets before any write. Running
`regenerate` converges once the current output baseline is committed; `--only` restricts
blast radius during iteration. The tool never deletes files, never edits cabal stanzas,
never forces overwrites, and never commits — every effect it can have is visible in
`git status` and reversible with `git checkout --` of the affected paths.

Order dependence is confined and declared: the eight skeleton invocations must run in
manifest order because they share one record slot (last writer wins); the driver
guarantees this, and a crash mid-sequence is repaired by simply re-running, which
replays all eight. A failed invocation leaves the CLI's partial output in place for
inspection; re-running after fixing the cause converges to the committed state.

The riskiest acceptance steps intentionally corrupt committed files; each is followed by
a regeneration or `git checkout --` restore in Concrete Steps, and none touches
anything outside `keiro-dsl/test` and `keiro-dsl/keiro-dsl.cabal`. There is no
database, network, or wire-format surface anywhere in this plan. If the plan must be
abandoned mid-way, revert the new package directory, manifest, script, Justfile lines,
`cabal.project` line, `test/Main.hs` helper, and doc/changelog edits with an explicit
patch; committed corpus bytes were never legitimately changed, so nothing else needs
rollback.

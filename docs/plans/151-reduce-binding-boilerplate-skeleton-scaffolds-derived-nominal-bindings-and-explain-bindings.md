# Reduce binding boilerplate: skeleton scaffolds, derived nominal bindings, and explain-bindings

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries,
Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.
If durable project context changes, update or create ADRs in docs/adr/ in the same change.


## Purpose / Big Picture

After this plan, a developer who declares a structural mapped type in a `.keiro` specification
no longer hand-writes most of the Haskell glue that connects their existing domain type to the
Keiro-generated wire codec. Three things become possible that are not possible today. First,
`keiro-dsl scaffold` emits a create-once binding module per structural mapped type with every
construction and destruction case already present as an explicitly marked hole, so the author
fills in semantic logic instead of discovering, by trial and error, which symbols the generated
ring expects; re-running the scaffolder after a spec change reports which holes are newly
required without ever overwriting functions the author already completed. Second, when the
consumer's Haskell record corresponds unambiguously to the declared shape (same field count,
matching names modulo a declared prefix convention, compatible field types), a `GHC.Generics`
derivation supplies the whole binding and the author writes nothing at all. Third,
`keiro-dsl check --explain-bindings` prints an authoring report listing every binding symbol the
spec requires, its expected Haskell type signature, the package and module that must own it, and
the reason it is required, so the cost of finding out "what do I still have to write?" drops to
one command.

None of this moves any wire policy out of the specification. The hard soundness constraint,
restated here because it governs every deliverable below: skeletons and derivation supply
**only nominal construction and destruction** of the consumer's type. Wire keys, union tags,
presence requirements, nullability, and on-missing defaults remain exclusively in the `.keiro`
spec, executed by the Keiro-generated codec that plan 150 lands. A wrong skeleton fill or a
wrong derived binding fails the generated conformance harness (codec goldens plus branch
coverage); it cannot silently alter the wire contract. This plan is EP-8 of the MasterPlan at
`docs/masterplans/25-structural-consumer-type-ergonomics-and-soundness-preserving-adoption-for-keiro-dsl.md`
and implements the low-risk ergonomics of sections 1 and 2 of
`docs/research/14-structural-consumer-type-tradeoffs.md`, plus one deliberately promoted
medium-risk item (derived nominal bindings) whose promotion rationale is recorded in the
Decision Log.

You can see it working by running the Experiment A acceptance scenario in Validation and
Acceptance: a three-field record, a five-arm tagged union, and a nested optional value go from
dozens of hand-written binding lines to only the semantic construction logic (zero lines for the
unambiguous record, per-arm payload logic for the union), while the generated bytes still match
the pinned JSON goldens.

  Rationale: `docs/research/14-structural-consumer-type-tradeoffs.md` places "`GHC.Generics` or

  2026-07-28) promotes it because the risk is bounded by construction: the derivation supplies
  only nominal construction/destruction; wire keys, union tags, presence, nullability, and

  generated conformance harness (codec goldens plus branch coverage from plan 150) rather than
  silently altering the wire contract. Binding boilerplate is the strongest force pushing
  consumers into opaque mode — the outcome the design most needs to avoid — so the ergonomic
  payoff justifies carrying the checked-machinery cost inside this soundness envelope. The
  negative proof (Proposal Test question 10) is a mandatory acceptance item, not an afterthought.
  Date: 2026-07-28

- Decision: Use `GHC.Generics`, not Template Haskell, for the nominal derivation.
  Rationale: Verified against the working tree on 2026-07-28: no package in this repository
  except `keiro-migrations/keiro-migrations.cabal` (an unrelated embedding use) depends on
  `template-haskell`; `keiro-dsl/keiro-dsl.cabal`, `keiro/keiro.cabal`, and
  `keiro-core/keiro-core.cabal` do not. `GHC.Generics` is already imported in
  `keiro-core/src/Keiro/Prelude.hs`, `keiro-dsl/src/Keiro/Dsl/Scaffold.hs`, and
  `keiro-dsl/src/Keiro/Dsl/Grammar.hs`, so `deriving stock (Generic)` is an established house
  convention. Generics keeps the derivation a plain library (type classes plus closed type
  families with `GHC.TypeLits.TypeError` diagnostics), imposes no staging restriction on
  consumer modules, and adds no new dependency; TH would add a dependency, a compile-stage
  ordering constraint on the consumer's leaf binding modules, and harder-to-test failure modes.
  If Milestone 2 discovers a correspondence check that Generics genuinely cannot express, the
  fallback is to narrow the derivable class (fail more cases into the skeleton path), never to
  guess.
  Date: 2026-07-28

- Decision: Skeleton hole bodies follow the repository's existing HOLE-stub convention
  (`error "HOLE: ..."` bodies under `-- HOLE` comments in create-once `HoleStub` modules), not
  GHC typed holes (`_holeName`).
  Rationale: Studied `emitHoles`, `holeUpcasterStubs`, and `holeProjectionStub` in
  `keiro-dsl/src/Keiro/Dsl/Scaffold.hs`: the generated ring's create-once `Holes.hs` compiles
  immediately with `error "HOLE: ..."` / `Left "HOLE: ..."` bodies so that the whole package —
  including the generated harness that then fails on the unfilled hole — builds on the first
  scaffold. A GHC typed hole is a hard compile error that would block the harness (and every
  other module) from building at all, destroying the "scaffold, build, watch the harness tell
  you what is unfilled" workflow the toolchain is built around. Compile-time enforcement is
  still obtained where it matters: skeleton bodies construct the generated shape type with
  complete record syntax and destructure it with exhaustive case alternatives, so when a spec
  change adds a field or union arm, an already-completed binding function stops compiling
  (missing-field / non-exhaustive-match, promoted to errors in the conformance suites) — the
  "compiler error at the application boundary" that section 1 of the research note asks for —
  while a freshly scaffolded, unfilled hole compiles and fails the harness instead.
  Date: 2026-07-28

## Context and Orientation

This section is self-contained; read it even if you know the repository.

### The repository and the toolchain

This repository hosts the Keiro event-sourcing runtime and its specification toolchain. The
packages named in `cabal.project` at the repository root are `keiro`, `keiro-core`,
`keiro-migrations`, `keiro-pgmq`, `keiro-test-support`, `jitsurei`, and `keiro-dsl`. The one
this plan changes is `keiro-dsl`: a command-line tool (`keiro-dsl/app/Main.hs`, an
optparse-applicative command tree with `parse`, `check`, `scaffold`, and `diff` subcommands)
plus a library under `keiro-dsl/src/Keiro/Dsl/`. A developer writes a `.keiro` specification
describing a service (aggregates, events, registers, and so on); `check` validates it;
`scaffold` emits Haskell modules; `diff --since <git-ref>` classifies evolution hazards between
two spec versions.

The scaffolder (`keiro-dsl/src/Keiro/Dsl/Scaffold.hs`) emits two kinds of module, distinguished
by `ModuleKind` in that file: `Generated` modules carry a `-- @generated` banner and are
overwritten on every run, and `HoleStub` modules are hand-owned — created only when absent,
never overwritten. The flagship `HoleStub` is `Holes.hs` (see `emitHoles` around line 1963): it
contains the aggregate's transducer body and any upcaster/projection holes as stubs whose bodies
are `error "HOLE: ..."` or `Left "HOLE: ..."` under `-- HOLE` comments. Everything compiles
immediately; the generated conformance harness then fails until the human fills the holes. This
"create-once Holes module" pattern is the convention the binding skeletons in this plan imitate.

Each scaffold run writes a scaffold record (`keiro-dsl/src/Keiro/Dsl/ScaffoldRecord.hs`,
`keiro-dsl-scaffold-record.<context>.txt` in the output directory): a versioned plain-text file
listing every emitted path tagged `generated` or `hole`. Its parser deliberately ignores unknown
lines "so v1 readers can consume records extended by later tool versions" — the extension point
this plan uses. The execution engine (`keiro-dsl/src/Keiro/Dsl/ScaffoldRun.hs`) reads the
previous record before writing, reports per-file `WriteDisposition` (`Overwritten` for
`Generated`, `Created` or `Skipped` for `HoleStub`), and reports as stale only files that appear
in the previous record but not in the current module set — stale reporting never touches files
the scaffold did not itself emit.

Validation (`keiro-dsl/src/Keiro/Dsl/Validate.hs`) exposes a closed `data DiagnosticCode`
registry shared by `check` and `diff`; per
`docs/adr/0004-evolution-changes-are-gated-at-the-earliest-sound-boundary.md` (ADR 0004),
machine-readable codes correlate the two commands and codes are append-only. ADR 0004 also
records the layered gate model this plan must not disturb: `check` rejects what one spec can
prove, `diff` classifies cross-spec hazards, runtime validated construction and conformance CI
independently defend assembly. The `docs/adr/` directory is a profile-governed OKF bundle
(`docs/adr/profile.dhall`); any ADR change must pass `just adr-validate`.

4. The generated conformance harness for structural types: binding round trips, generated JSON
   codec round trips against pinned goldens, missing-field/null/unknown-field/every-union-arm

### Terms used in this plan

A **structural mapped type** is a consumer-owned Haskell type declared in the `.keiro` spec
with an explicit wire representation, encoded and decoded by a Keiro-generated codec. A
**binding** is the typed pair of functions converting between the consumer type and the
declared shape type. A **shape type** is the record/union mirror of the declared wire structure
that the generated codec produces and consumes (plan 150 fixes where it is generated). A
**hole** is a scaffolded stub the human must fill, marked `-- HOLE` with an
`error "HOLE: ..."`-style body, in a create-once hand-owned module. A **nominal derivation** is
a `GHC.Generics` program that writes the binding automatically when, and only when, the field
correspondence between consumer type and shape type is unambiguous. **Binding drift** is a
difference between the binding obligations recorded at the last scaffold run and the
obligations the current spec implies.

### Milestone 1 — Binding skeleton scaffolds with newly-required-hole reporting

Scope: the scaffolder emits, for every structural mapped type in the spec, a create-once
binding module with every obligation present as a hole. Concretely, in
`keiro-dsl/src/Keiro/Dsl/Scaffold.hs` add an emitter (working name `emitBindingSkeleton`)
invoked from the structural scaffold path plan 150 added to `scaffoldModules` in
`keiro-dsl/src/Keiro/Dsl/ScaffoldRun.hs`, producing one `ScaffoldModule` of kind `HoleStub` per
structural mapped type, placed where the spec's binding declaration points (the spec names the
binding module; the skeleton is emitted at the corresponding path under the scaffold output
root, following the placement rules `holePrefixFor`/`Placement` already implement — study how
`Holes.hs` chooses its path and imitate it, honoring plan 150's leaf-module import discipline:
the skeleton imports only the consumer domain module, the shape-type module, and the binding
API module, never a generated codec module). The emitted module contains, per type: the
`StructuralBinding` value with `bindingToShape` written as a complete record construction (or
per-constructor `case` for unions) whose field values are `error "HOLE: fill <TypeName> bindingToShape.<field>"`
stubs, and `bindingFromShape` written as an exhaustive destructuring whose results are the analogous
stubs; the fixture stub; and, when the type is used as a register, the initial-value stub. Every
stub sits under a `-- HOLE:` comment in the same style as `emitHoles`. Because construction is
complete and destructuring exhaustive, a later spec change that adds a field or arm makes an
already-filled function fail to compile, while a fresh unfilled skeleton compiles and fails the
harness — the enforcement split recorded in the Decision Log.

Re-scaffold reporting: extend the scaffold record with one line per binding obligation, in the
spirit of the existing `generated`/`hole` lines (for example
`binding <TypeName> <symbol> <obligation-kind>`), emitted by `renderRecord` and parsed by
`parseRecord` in `keiro-dsl/src/Keiro/Dsl/ScaffoldRecord.hs` — coordinate with the binding-
identity entries plan 150 already added; extend those rather than adding a parallel shape if
they exist. Old records without the lines still parse (the parser ignores unknown lines; keep
that property in reverse by tolerating their absence). In `ScaffoldRun.hs`, after reading the
previous record, compute the set difference between current obligations and recorded
obligations and surface it on the `ScaffoldReport` (working name `reportNewHoles`); the CLI
prints a "newly required holes" section listing each new symbol, its type, and the hand-owned
file that needs it. `HoleStub` write semantics are untouched: existing skeleton files are
`Skipped`, never overwritten, exactly as `writeModule` does today. When a skeleton file exists
but new obligations target it, the report tells the author what to add by hand (with the
expected signatures); the scaffolder never edits a hand-owned file.

At the end of this milestone, scaffolding the Experiment A spec into an empty directory creates
the binding skeleton modules; the package compiles; the conformance harness fails on the
unfilled holes; re-running scaffold reports zero new holes and skips the skeletons; editing the
spec to add a field and re-running reports exactly one newly required hole. Unit tests in
`keiro-dsl/test/` cover emission text, create-once behavior, record round-trip with binding
lines, and the new-holes diff.

### Milestone 2 — Derived nominal bindings via GHC.Generics

Scope: a consumer whose type corresponds unambiguously to the declared shape writes no binding
at all. Add, beside the `StructuralBinding` API module plan 150 published (same package; the
module is consumer-facing, so it must be importable from leaf binding modules), a module
(working name suffix `.Generic`) exporting roughly:

```haskell
genericStructuralBinding
    :: (Generic domain, Generic shape, GNominalBinding (Rep domain) (Rep shape))
    => StructuralBinding domain shape
```

together with a declared prefix convention: the derivation compares field names after stripping
a stated prefix from the shape side (for example `shapeKey` corresponds to `key`), with the
prefix supplied as a type-level symbol or via a small options record — pick the encoding that
yields the clearest type errors and record the choice in the Decision Log. `GNominalBinding` is
a closed type-class hierarchy over `GHC.Generics` representations that succeeds only when the
two representations have the same constructor count, the same field count per constructor,
matching selector names modulo the prefix, and pairwise-coercible-or-equal field types
(recursing through the binding API for nested mapped types per plan 150's design). Every
ambiguous or mismatched case — a renamed field, an arity mismatch, an incompatible field type,
a missing selector — must fail at compile time via `GHC.TypeLits.TypeError` with a message that
names the mismatching fields and directs the author to the skeleton path ("no unambiguous
correspondence for field `contentHash`; fill the binding by hand in the scaffolded module
<module name>"). The derivation must never guess.

State the soundness constraint in the module's Haddock header verbatim, because consumers will
read it there: the derivation supplies only nominal construction and destruction; wire keys,
union tags, presence, nullability, and defaults remain exclusively in the `.keiro` spec and the
generated codec; a wrong derived binding fails the generated conformance harness and cannot
silently alter the wire contract.

Tests: positive — the Experiment A three-field record derives and passes the full harness;
negative — compile-fail fixtures (the repository has no compile-fail harness today; add
minimal ones as separate `should-not-compile` sources exercised by a test that invokes GHC, or
follow whatever convention plan 150 established for its negative fixtures — decide and record)
for renamed field, arity mismatch, and incompatible type, each asserting the diagnostic text
mentions the skeleton path. Acceptance: the record's hand-written binding from Milestone 0 is
deleted and replaced by one `genericStructuralBinding` line, and the harness (goldens included)
still passes byte-identically.

### Soundness gate: the ten-question Proposal Test

Per the MasterPlan, every child plan answers the Proposal Test from
`docs/research/14-structural-consumer-type-tradeoffs.md` ("A Proposal Test for Future Keiro
Improvements") in its Validation section. Questions 1 and 10 are answered in depth as required.

**1. Authority (in depth).** The wire schema is owned, before and after this plan, by exactly
one artifact: the `.keiro` specification, executed by the codec that plan 150 generates from
the resolved type graph. Nothing this plan emits or derives contains a wire key, union tag,
presence rule, nullability rule, or default. The skeleton emits calls into the consumer's
constructors and pattern matches over the shape type — the shape type itself is generated from
the spec, so even the skeleton's field spellings are downstream of the spec, not a second
authority. The generic derivation reads only `GHC.Generics` metadata of the two Haskell types;
it cannot mention a wire identity because the binding API gives it no vocabulary to do so — its
output is a `StructuralBinding`, whose only capabilities are constructing and destructing the
consumer value. `--explain-bindings` is read-only over the resolved graph. The delegation
direction fixed by the codec-authority ADR created by plan 149/150 (consumer instances may
delegate to the generated codec, never the reverse) is untouched: this plan adds no code path
in which a consumer `ToJSON`/`FromJSON` instance is consulted. Reviewers should verify
mechanically at Milestone 4: the derivation module imports neither `Data.Aeson` encoding
internals nor any generated codec module, and the skeleton emitter's import list names only
the consumer domain module, the shape module, and the binding API.

**2. Replay.** Unchanged. Bindings do not touch event emission; forward register updates are
reconstructed from emitted private events exactly as plan 150's forward-versus-replay harness
assertion proves, and that assertion runs unchanged over Experiment A.

**3. Visibility.** No new Keiki claim is made. Derived and skeleton bindings are construction
plumbing outside the symbolic language; no guard or update syntax is added.

**4. Compatibility direction.** Unchanged; `diff` classification (plan 149) is not touched.
The newly-required-holes report is an authoring aid computed from scaffold records, not a
compatibility claim.

**5. Ownership.** Private types and public DTOs remain separate; skeletons are emitted only
for structural mapped types on the surfaces IR-1 permits, and nothing here exports a private
type publicly.

**6. Completeness.** Skeleton emission, obligation computation, and `--explain-bindings` all
traverse the resolved type graph through the same total traversal registry IR-1 mandates
("adding a new type-expression constructor cannot silently omit a subsystem"); Milestone 1 and
3 tests must include the exhaustiveness pattern plan 149/150 established so a new constructor
breaks compilation of the new traversals too.

**7. Migration.** No migration surface changes: generated bytes are proven byte-identical to
pinned goldens (acceptance item 4), and scaffold records with binding lines remain readable by
older parsers (unknown-line tolerance) while new code tolerates their absence.

**8. Recovery.** Scaffolding remains idempotent and create-once (see Idempotence and
Recovery); a half-finished fill leaves the package either non-compiling (spec-change case) or
harness-failing (fresh-hole case), both loud; deleting a skeleton file and re-scaffolding
recreates it.

**9. Performance.** The derivation is compile-time; the produced binding is ordinary record
construction, no slower than the hand-written form. If Milestone 2's harness runs show
Generics-induced runtime overhead on the union path, record measurements in Surprises &
Discoveries and fall back to skeleton-only for that shape — never to an alternate codec.

**10. Negative proof (in depth).** Two mutation tests, added to the IR-1 conformance suite in
Milestone 4, prove the harness actually guards the new machinery. (a) **Wrong derived
binding:** add a fixture pair of types engineered so the generic correspondence is judged
unambiguous but semantically wrong — two fields of the same Haskell type (`Text`) whose values
are swapped by a deliberately perverse hand-supplied binding standing in for a hypothetical
buggy derivation (and, additionally, a compile-fail fixture proving the real derivation
*refuses* the renamed-field case rather than producing this binding). Run the generated
harness against the perverse binding: the codec golden comparison must fail (the emitted JSON
carries the swapped values) and/or the round-trip assertion must fail. The test asserts the
harness exits non-zero with the golden mismatch named. (b) **Wrong skeleton fill:** fill the
five-arm union skeleton mapping one arm's payload to the wrong constructor. The branch-coverage
assertion plan 150 generates (every union arm exercised from declared fixtures/generators) plus
the golden comparison must fail on exactly that arm; the test asserts the failure names the
arm. Both tests demonstrate the load-bearing claim made throughout this plan: a wrong nominal
binding — derived or hand-filled — cannot silently alter the wire contract, because the
generated conformance harness, not the binding author, is the gate. If either mutation passes
the harness, this plan's machinery is unsound and must not ship; that is the failure condition
this question exists to make observable.

## Idempotence and Recovery

Every step is safe to repeat. `keiro-dsl scaffold` is already idempotent by construction:
`Generated` modules are rewritten deterministically, `HoleStub` modules (including all binding
skeletons this plan adds) are `Skipped` whenever present, and the scaffold record is rewritten
atomically at the end of a successful run — a re-run after a crash simply re-plans and
re-writes. The newly-required-holes report is a pure diff between the current plan and the last
recorded run; running scaffold twice in a row reports zero new holes. If a scaffold record is
lost or corrupted, the next run treats the run as first-time for reporting purposes (no new-
holes diff, no stale report) but still never overwrites an existing hand-owned file — the worst
outcome of a lost record is a quieter report, never data loss. If an author damages a skeleton
beyond repair, deleting the file and re-scaffolding recreates the pristine skeleton; completed
work in other files is untouched. The derivation and `--explain-bindings` are pure and
side-effect free. Documentation edits (guides, ADRs) are ordinary git-tracked changes;
`just adr-validate` failing after an ADR edit blocks nothing else and is fixed by amending the
ADR frontmatter/log. If Milestone 0 discovers plan-150 drift so large that a milestone is
infeasible as written, stop, record it in Surprises & Discoveries, revise the plan (Revision
Protocol), and only then continue — the plan file itself is the recovery point.

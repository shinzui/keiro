# Modularize the Keiro Megaparsec grammar by language concern

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries,
Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.
If durable project context changes, update or create ADRs in docs/adr/ in the same change.


## Purpose / Big Picture

After this change, the Keiro source grammar is organized by language concern instead of living in
one 2,000-line `Keiro.Dsl.Parser` module. Contributors adding or reviewing a declaration, mapped
type, expression, aggregate, coordination node, integration node, queue, read model, workflow, or
operation can find its complete grammar in a named internal module with a small import boundary.
`Keiro.Dsl.Parser` becomes a stable facade that selects a language, invokes the document grammar,
lowers the located surface result, and renders compatibility failures.

This is a behavior-preserving extraction. Running the 0.7 compatibility oracle before and after
each family move produces identical acceptance, surface spans, lowered `Spec`, canonical text,
curated diagnostics, and generated bytes. No new syntax or diagnostic policy is introduced here.

- Observation: The existing `Keiro.Dsl.Workspace` module imports Megaparsec for the independent

  Evidence: The final import inventory contains frontend grammar imports only below
  `Keiro/Dsl/Parser/`, plus the pre-existing imports at `Workspace.hs:108-110`.
  Impact: The parser-boundary test permits this separate manifest parser while keeping source,

  substantial core even after the concern split.
  Evidence: `Parser.Core` is 416 lines; the eleven concern/composition modules range from 60 to 338

  Impact: Keeping one acyclic core is clearer than duplicating lexer, bounded-literal, feature-gate,
  and span logic merely to make every internal file the same size.


## Decision Log

Record every decision made while working on the plan.

- Decision: Split modules by grammar concern, not by arbitrary line count or one file per production.
  Rationale: A concern module should own a coherent syntax vocabulary and be independently reviewable;
  excessive micro-modules would hide grammar order and backtracking relationships.
  Date: 2026-08-01

- Decision: Keep all production modules internal to the package and expose only the facade and the
  surface/frontend types created by EP-173.
  Rationale: Parser combinators, ordering, and Megaparsec error components are implementation details,
  not a public language API.
  Date: 2026-08-01

- Decision: Move productions without redesigning them, one family at a time, and run the compatibility
  oracle after every move.
  Rationale: Mechanical extraction and semantic improvement have different failure modes. Keeping them
  separate makes any drift attributable and reviewable.
  Date: 2026-08-01

- Decision: Use twelve internal modules: `Core`, `Preamble`, `Document`, `Declaration`, `Mapped`,
  `Expression`, `Aggregate`, `Coordination`, `Integration`, `Queue`, `ReadModel`, and `Workflow`.
  Rationale: This gives each grammar concern an obvious owner, leaves shared primitives below all
  families, and keeps document dispatch above them without an import cycle.
  Date: 2026-08-01

## Plan of Work

Milestone 1 creates the internal directory `keiro-dsl/src/Keiro/Dsl/Parser/` and registers every
new module in the library stanza's `other-modules`. `Parser.Core` owns the parser type, source-span
capture, custom error component, lexer/space consumer, token/keyword/identifier parsers, bounded
numeric and quoted-string primitives, delimiter helpers, and the authoritative reserved-word set.
It may depend on `Source`, `Syntax`, `Grammar` leaf types, and `LanguageVersion`, but not on a node
family or the public facade.

`Parser.Preamble` owns initial preamble recognition and source-language selection.
`Parser.Document` owns the selected-body entry point, context/module/layout clauses, top-level item
ordering, and construction of `SurfaceSource`. `Document` imports each top-level family through a
narrow exported parser. Preserve the existing rule that a real later preamble is contextual syntax
while a nested identifier spelled `language` remains data. After this move, run all source-language,
span, lowering, and 0.7 compatibility tests before continuing.

Milestone 2 creates `Parser.Declaration`, `Parser.Mapped`, and `Parser.Expression`.
`Declaration` owns IDs, enums, rules, and top-level declaration wrappers. `Mapped` owns structural,
opaque, and nominal declarations, type expressions, shapes, fields, arms, defaults, Haskell source,
and required/duplicate clause collection. `Expression` owns legacy and typed scalar terms, roots,
paths, literals, unsupported collection forms, and operator tables. `Expression` must not know about
aggregate transitions; it exports expression parsers parameterized by the selected frontend context.

Move code rather than reimplementing it. Preserve `try`, `lookAhead`, label, lexeme, and alternative
ordering. Keep exact custom error offsets and surface spans. Run mapped, nominal, expression,
round-trip, and full compatibility groups after each module lands.

Milestone 3 creates coherent node modules. `Parser.Aggregate` owns aggregate headers, registers,
states, commands, events, wire/projection/snapshot clauses, transitions, and transition clauses; it
imports `Parser.Expression`. `Parser.Coordination` owns process, router, timer, resolve, dispatch,
policy, binding, and correlation syntax. `Parser.Integration` owns contract, intake, emit, and
publisher syntax. `Parser.Queue` owns workqueue and pgmq-dispatch syntax. `Parser.ReadModel` owns
read-model syntax. `Parser.Workflow` owns workflow and operation syntax. If a module becomes larger
than the original concern boundary permits, split a child such as `Parser.Coordination.Timer`, but
keep one concern-level re-export used by `Document`.

Every node module returns the surface top-level item defined by EP-173. It must not call
`lowerSurfaceSource`, `validateService`, scaffold code, or workspace code. The aggregate module is
the only node module allowed to import the expression module unless a future already-released
production demonstrably uses expression syntax; do not create speculative dependencies.

Milestone 4 reduces `Keiro.Dsl.Parser` to public type aliases, the existing `parseSource`,
`parseSpec`, `parseSpecText`, `renderParseFailure` compatibility surface, and the advanced surface
entry point re-export or delegation agreed in EP-173. It imports `Parser.Document` and `Frontend`,
not individual families. Add an import-boundary test or a repository check using `rg` that rejects
imports of `Keiro.Dsl.Parser` from internal parser modules and rejects Megaparsec imports from
`Keiro.Dsl.Syntax`/`Source`/semantic consumers.

The facade should contain orchestration and compatibility rendering only; use review judgment rather
than a brittle line-count test, but a file still containing grammar productions means the extraction
is incomplete. Run the entire Hspec suite, build all packages, and compare generated conformance trees
through the existing freshness tests.

## Idempotence and Recovery

Extract one concern per working commit and keep the repository compiling. File moves are reversible,
but never use destructive Git commands to recover; restore a failing production from the prior
commit with an explicit patch or revert the isolated commit. If an import cycle appears, move the
shared primitive downward into `Parser.Core` only when it is truly grammar-neutral; otherwise pass a
parser function as an argument rather than importing a higher-level module. Keep temporary
re-exports only until their callers have moved, then remove them before completing the plan.


## Interfaces and Dependencies

`Keiro.Dsl.Parser` retains the released signatures recorded by EP-172. Internal concern modules
export parsers in the package's parser monad, conceptually:

```haskell
type P = Parsec FrontendParseComponent Text

pDocument :: FrontendContext -> P SurfaceSpec
pTopDeclaration :: FrontendContext -> P SurfaceTopItem
pAggregate :: FrontendContext -> P SurfaceTopItem
pExpression :: FrontendContext -> P SurfaceExpr
```

Use the concrete surface types delivered by EP-173; do not create parallel lookalikes for individual
modules. `FrontendContext` may still be the current language version during this mechanical plan;
EP-175 owns the explicit syntax profile. New parser modules are `other-modules`, not exposed modules.
Any new product record follows EP-173's frontend-local convention; do not rename existing records.
Continue using the existing Megaparsec and `parser-combinators` bounds from
`keiro-dsl/keiro-dsl.cabal`.

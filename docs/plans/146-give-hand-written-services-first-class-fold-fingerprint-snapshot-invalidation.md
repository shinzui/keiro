# Give hand-written services first-class fold-fingerprint snapshot invalidation

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries,
Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.
If durable project context changes, update or create ADRs in docs/adr/ in the same change.


## Purpose / Big Picture

Keiro snapshots are cached hydration seeds: instead of replaying a stream's whole event log
through the aggregate fold on every command, Keiro can load a stored `(state, registers)` pair
and replay only the tail. A snapshot is only safe to reuse when it was produced by the *same
fold logic* the current binary runs. Services generated by `keiro-dsl` get that safety wired
automatically: the scaffolder derives a fingerprint of the spec-visible fold surface and mixes
it into the snapshot discriminator, so a spec-visible fold change makes old snapshots miss and
fall back to a full replay. A hand-written service gets none of that. Its author must remember
to bump an integer (`stateCodecVersion`) by hand every time fold logic changes; forgetting means
STALE SNAPSHOTS ARE SERVED AS CORRECT STATE with no error of any kind. The guarantee analysis
behind `docs/research/14-structural-consumer-type-tradeoffs.md` identified this as the single
most consequential *silent* loss of bypassing the DSL, and this plan shrinks that delta of the
sanctioned hand-written escape hatch: hand-written services keep their freedom, but the default
recipe for building a snapshot codec now forces the author to hold a visible, hand-owned fold
identity in their hands.

After this change, a hand-written service author writes:

```haskell
stateCodec = Just (defaultStateCodecWithFold (FoldVersion "orders-fold-v3") 1)
```

instead of `Just (defaultStateCodec 1)`. The `FoldVersion` token is a piece of text the author
bumps in the same edit that changes a guard, update, target, or any other fold behavior. A
changed token changes the snapshot discriminator, the old snapshot row simply is not found, and
hydration falls back to a full replay — the safe, already-tested degradation path. You can see
it working by running `cabal test keiro-test` from the repository root: the suite includes a
test that stores a snapshot under one fold token and proves that a codec carrying a different
token rejects the stale seed and the command completes by full replay. Both snapshot-bearing
streams in the `jitsurei` example application adopt the new helper, and the operator guides
document it as the default recipe.

## Decision Log

- Decision: The fold identity for a hand-written service is an explicit, hand-owned token the
  author bumps alongside fold edits — full automatic fingerprinting of hand-written folds is
  rejected as impossible to do honestly.
  Rationale: The DSL fingerprint (`keiro-dsl/src/Keiro/Dsl/FoldFingerprint.hs`) hashes a *spec*:
  a finite, canonical, declarative description of states, registers, transitions, guards,
  writes, emits, and referenced rules. A hand-written service has no spec to fingerprint; its
  fold lives in opaque compiled Haskell (guard closures, update functions, and everything they
  transitively call). Any scheme that hashes source files or function representations is either
  unsound (misses logic in transitively called helper modules, so a real change keeps the hash
  equal — exactly the silent failure we are eliminating) or wildly over-invalidating and
  non-deterministic (formatting edits, inlining, and rebuild differences change the hash). The
  generated-code comment at `keiro-dsl/src/Keiro/Dsl/Scaffold.hs` lines ~1858-1868 already
  records that even for DSL services a Holes-only (hand-owned module) fold edit is invisible to
  the automatic fingerprint. Presenting a leaky automatic hash as a guarantee would violate the
  master plan's non-negotiable (no false confidence, research note guarantee G1/G6 spirit); an
  explicit token is honest about who owns the obligation while making it structurally
  impossible to construct the recommended codec without confronting it.
  Date: 2026-07-28

- Decision: The API is `newtype FoldVersion = FoldVersion Text` plus
  `defaultStateCodecWithFold :: ... => FoldVersion -> Int -> StateCodec (s, RegFile rs)`, both
  in `keiro/src/Keiro/Snapshot/Codec.hs`, implemented as
  `withFoldFingerprint token . defaultStateCodec` — no new discriminator machinery.
  Rationale: `withFoldFingerprint` already exists, is what DSL-generated code composes (see
  `stateCodecExpr` in `keiro-dsl/src/Keiro/Dsl/Scaffold.hs` lines 1846-1854), and renders the
  operator-readable `<state-shape-hash>;fold=<token>` form recorded in ADR 0003. Reusing it
  means hand-written and generated services share one storage format, one lookup path
  (`keiro/src/Keiro/Snapshot/Schema.hs`), and one set of behavioral tests. The dedicated
  `FoldVersion` newtype (rather than a bare `Text` argument) makes the call site self-labeling
  — `defaultStateCodecWithFold (FoldVersion "orders-fold-v3") 1` cannot be misread as a stream
  name or codec-version string — and gives Haddock a stable anchor for the bump discipline. No
  `IsString` instance: forcing the constructor keeps the token visible and greppable.
  Date: 2026-07-28

- Decision: `defaultStateCodec` and `withFoldFingerprint` are kept, exported, and
  un-deprecated; the helper is additive and documentation makes it the default recipe.
  Rationale: DSL-generated modules call `withFoldFingerprint <derived> (defaultStateCodec n)`
  and must keep compiling; deprecating either would spray warnings through generated code.
  Existing keiro tests also drive both directly. The "hard-to-forget" property comes from three
  reinforcing places instead: the helper is the only snapshot-codec constructor the guides show
  for hand-written services, `defaultStateCodec`'s Haddock explicitly redirects hand-written
  services to the helper, and every hand-written example in the repository (jitsurei) uses it.
  Date: 2026-07-28

- Decision: The token is a change detector, not a monotonic version; any non-empty text is
  accepted and no runtime validation is added.
  Rationale: Same semantics `withFoldFingerprint` already documents ("keep it stable when fold
  semantics are stable and change it whenever ... event-folding behavior changes"). Even a
  sloppy token (including the empty string) yields a discriminator distinct from the
  no-fingerprint form, so there is no soundness hole to guard against — only a hygiene concern,
  which the Haddock addresses by recommending a `<service>-fold-vN` convention. Rejecting empty
  text at runtime would add a partial constructor for no safety gain.
  Date: 2026-07-28

- Decision: Adopting the helper in jitsurei changes both streams' `stateShapeHash`, so any
  existing local snapshot rows miss once and full-replay; no migration is written.
  Rationale: This is exactly the safe degradation ADR 0003 designs for — a changed
  discriminator is an ordinary advisory miss, the event log is the source of truth, and the row
  repopulates when the policy next fires. jitsurei is a demo application; a one-time replay per
  stream in a developer database is the intended behavior, not damage.
  Date: 2026-07-28

## Context and Orientation

This repository is a Cabal multi-package Haskell project (see `cabal.project` at the root).
The packages relevant here are `keiro` (the runtime library — command running, hydration,
snapshots), `keiro-core` (shared core types, including `StateCodec` in
`keiro-core/src/Keiro/EventStream.hs`), `keiro-dsl` (the spec toolchain that generates
services; only read here, never edited), `keiro-test-support` (the shared PostgreSQL test
fixture), and `jitsurei` (the example application demonstrating hand-written services). This
plan belongs to master plan
`docs/masterplans/25-structural-consumer-type-ergonomics-and-soundness-preserving-adoption-for-keiro-dsl.md`
as its EP-3, but is self-contained: everything needed to implement it is in this file.

Terms used below. An *aggregate* is a state machine folded from a stream's stored events; the
*fold* is that event-to-state function (in keiki terms: the transducer's guards, register
updates, emitted outputs, and target states). *Hydration* is reading and folding stored events
to reconstruct current state before deciding a command. A *snapshot* is a stored JSON encoding
of the folded `(state, registers)` pair at a known stream version, letting hydration replay
only the tail. A *hand-written service* defines its `EventStream` record and transducer
directly in Haskell (as jitsurei does), instead of generating them from a `.keiro` spec.

How snapshot compatibility works today. Per
`docs/adr/0003-snapshot-compatibility-is-a-three-component-discriminator.md`, a snapshot row
is tagged with three discriminators: `stateCodecVersion` (a manually owned `Int`),
`regfileShapeHash` (derived from the keiki register-file layout), and `stateShapeHash`
(derived from the control-state datatype, optionally composed with a fold fingerprint).
`lookupSnapshot` in `keiro/src/Keiro/Snapshot/Schema.hs` (the SQL at lines ~106-125) matches
all three server-side; a row that does not match all three is simply not found, and
`lookupSnapshotSeed` in `keiro/src/Keiro/Snapshot.hs` (lines ~80-107) reports
`SnapshotUnavailable SnapshotNotFound`, which the command runner treats as "replay from the
beginning". The write path (`writeSnapshotStmt`, Schema.hs lines ~127-155) lets a changed
discriminator replace the row even at a lower stream version so a rolled-back deployment can
reclaim the slot. Mismatch therefore always degrades to a full replay — a performance cost,
never wrong state.

The codec constructors live in `keiro/src/Keiro/Snapshot/Codec.hs`. `defaultStateCodec`
(lines ~38-54) builds a `StateCodec (s, RegFile rs)` from a caller-supplied `Int` version plus
the two derived hashes. `withFoldFingerprint` (lines ~56-69) post-composes a caller-supplied
`Text` fold identity into `stateShapeHash`, rendering it as
`<state-shape-hash>;fold=<fingerprint>`. `StateCodec` itself is defined in
`keiro-core/src/Keiro/EventStream.hs` (lines ~109-116); its Haddock already warns that
hand-written guard and update bodies are not structurally inspectable. Both Codec.hs exports
are re-exported through `Keiro.Snapshot` (module `keiro/src/Keiro/Snapshot.hs` re-exports
`module Keiro.Snapshot.Codec`), which is what consumers import.

What the DSL wires automatically and hand-written services lack.
`keiro-dsl/src/Keiro/Dsl/FoldFingerprint.hs` computes a sixteen-hex-digit FNV-1a hash over an
aggregate spec's canonical fold surface (states and terminality, register types and initials,
transition mode/guards/writes/emits/targets, transitively referenced rules).
`keiro-dsl/src/Keiro/Dsl/Scaffold.hs` (`stateCodecExpr`, lines 1846-1854) emits
`Just (withFoldFingerprint "<derived>" (defaultStateCodec <n>))` into every generated
snapshot-bearing stream, and the accompanying generated comment (lines 1856-1869) warns that
even for generated services, fold changes made only in the hand-owned Holes module are
invisible and require a manual `state-codec version=` bump. A fully hand-written service is
all Holes, so *nothing* about its fold participates in the discriminator unless the author
manually bumps `stateCodecVersion` — the failure this plan makes hard to commit.

Where hand-written snapshot codecs are constructed today. In `jitsurei/src`, exactly two
streams carry snapshots (verified by grepping for `stateCodec = Just` and `snapshotPolicy`):
`snapshotOrderEventStreamDef` in `jitsurei/src/Jitsurei/OrderStream.hs` (lines 61-66;
`snapshotPolicy = Every 2`, `stateCodec = Just (defaultStateCodec @OrderRegs @OrderState 1)`)
and `escalationEventStreamDef` in `jitsurei/src/Jitsurei/EscalationProcess.hs` (lines ~160-169;
`snapshotPolicy = OnTerminal`, same bare `defaultStateCodec ... 1` shape). All other jitsurei
streams have `stateCodec = Nothing` (`jitsurei/src/Jitsurei/Snapshots.hs` only re-exports
`snapshotOrderEventStream`). Both bare codecs are exposed to the silent-staleness hazard.

Existing test infrastructure. `keiro/test/Main.hs` opens with
`main = withMigratedSuite $ \fixture -> hspec $ ...` using
`keiro-test-support/src/Keiro/Test/Postgres.hs`: one cached ephemeral PostgreSQL server per
suite, a single migrated *template database*, and a fresh clone per example via

template-database fixtures, never per-example migration — and new tests must use the same

Normative references and their connection to this plan.
`docs/improvement-requests/support-structural-consumer-owned-types-in-keiro-dsl.md` (IR-1)

needed for this work. The operator-facing procedure this plan improves is documented in

Milestone 1 — the helper in keiro, proven by tests. In
`keiro/src/Keiro/Snapshot/Codec.hs`, add a `FoldVersion` newtype and a
`defaultStateCodecWithFold` function, and export both from the module's export list (they flow
through `Keiro.Snapshot`'s `module Keiro.Snapshot.Codec` re-export automatically; no cabal
change is needed because no new module is created). The complete addition:

```haskell
{- | A hand-owned identity for a hand-written service's event fold.

The DSL derives a fold fingerprint from the spec automatically; a hand-written
service has no spec, so its fold identity must be owned by hand. Treat the
token as a change detector, not an encoding version: keep it stable while fold
semantics are stable, and change it in the same edit that changes any guard,
register update, emitted output, or target state — including logic in helper
functions the fold calls. A convention such as @\"orders-fold-v3\"@ keeps the
token greppable and reviewable. Forgetting to bump it recreates the silent
stale-snapshot hazard this type exists to prevent; see
'defaultStateCodecWithFold'.
-}
newtype FoldVersion = FoldVersion Text
    deriving stock (Eq, Show)

{- | The default snapshot codec for hand-written services: 'defaultStateCodec'
with a hand-owned 'FoldVersion' composed into the control-state discriminator
via 'withFoldFingerprint'.

Prefer this over bare 'defaultStateCodec' whenever the service's fold is
hand-written. A changed token changes the stored discriminator, so an old
snapshot is simply not found and hydration falls back to a full replay of the
event log — a performance cost, never wrong state. The rendered discriminator
stays operator-readable as @\<state-shape-hash\>;fold=\<token\>@.
-}
defaultStateCodecWithFold ::
    forall rs s.
    (CanonicalStateShape s, FromJSON s, KnownRegFileShape rs, RegFileToJSON rs, ToJSON s) =>
    FoldVersion ->
    Int ->
    StateCodec (s, RegFile rs)
defaultStateCodecWithFold (FoldVersion token) version =
    withFoldFingerprint token (defaultStateCodec version)
```

## Validation and Acceptance

Acceptance is behavioral. After the change, from the repository root:

1. `cabal test keiro-test` passes, and specifically contains passing examples named
   "composes the hand-owned fold version into the state discriminator", "uses the fold
   fingerprint as a snapshot discriminator", "full-replays under a changed fold and persists
   the new discriminator", and "pins the manual-contract hazard when fold logic changes
   without a discriminator bump" — the middle two now driven through
   `defaultStateCodecWithFold`. Together these observe: a snapshot written under
   `FoldVersion "fold-v1"` is served to an identical-token codec at the stored stream
   version; the same row yields `SnapshotUnavailable SnapshotNotFound` to a
   `FoldVersion "fold-v2"` codec; a command run under the changed token still succeeds with
   the correct final stream version (proving full replay of the event log, not an error and
   not stale state) and the snapshot row afterward carries the new
   `<hash>;fold=fold-v2` discriminator.
2. `cabal test jitsurei-test` passes with both adopted streams, proving adoption did not
   change observable snapshot behavior (row written at the expected stream versions).
3. `grep -rn "defaultStateCodec " jitsurei/src` returns no bare uses — every jitsurei
   snapshot codec goes through `defaultStateCodecWithFold`.
4. The guides render the new recipe: `docs/guides/snapshots-and-hydration.md` shows
   `defaultStateCodecWithFold (FoldVersion ...)` as the hand-written default, and
   `just adr-validate` passes after the ADR 0003 amendment.

Soundness gate — the research note's Proposal Test
(`docs/research/14-structural-consumer-type-tradeoffs.md`, "A Proposal Test for Future Keiro
Improvements"), answered for this change:

1. Authority: the wire schema of the snapshot is still owned by `defaultStateCodec`'s
   encode/decode pair; the helper touches only the discriminator. No second codec authority
   is created.
2. Replay: unchanged — events remain the source of truth; the helper only affects whether a
   cached seed is consulted.
3. Visibility: no new claim of solver visibility is made; the token is explicitly documented
   as a hand-owned change detector, not a checked property.
4. Compatibility direction: the discriminator distinguishes exactly the snapshot-hydration
   question; event, queue, and public-contract compatibility are untouched.
5. Ownership: the token is owned by the hand-written service beside its fold; generated
   services keep their derived fingerprint. No shared artifact couples them.
6. Completeness: the helper is one total function over the existing tested primitives; the
   pure composition test fails if the token stops reaching `stateShapeHash`, and the DB tests
   fail if lookup stops matching on it.
7. Migration: adopting the helper changes `stateShapeHash`, which existing rows fail to
   match; that is the designed advisory-miss migration (one full replay per stream, row
   repopulates). No byte rewriting, no upcasters.
8. Recovery: this is the load-bearing gate. A discriminator mismatch must degrade to full
   replay and may NEVER serve stale state: `lookupSnapshot` matches all three components
   server-side, a miss is `SnapshotNotFound`, and the command runner replays from the start
   of the log — asserted by the changed-fold full-replay test. Rollback is equally safe: the
   write path (`writeSnapshotStmt`) lets the old release's discriminator replace the newer
   row, so a rolled-back deployment reclaims the slot and continues (Schema.hs module
   header). A half-adopted deployment (one binary with the token, one without) can thrash
   the single snapshot row, which is the documented mixed-deployment performance caveat, not
   a correctness risk.
9. Performance: zero steady-state overhead (one `Text` append at codec construction). The
   adoption cost is the one-time full replay per stream, stated in the guides.
10. Negative proof: the stale-seed rejection test (a `fold-v2` codec must NOT receive the
    `fold-v1` seed) proves the guarantee would visibly fail if the helper dropped the token,
    and the retained "pins the manual-contract hazard" test proves by construction what the
    silent failure looks like when an author changes the fold WITHOUT bumping the token —
    documenting the residual obligation honestly rather than pretending the helper removes
    it.


## Idempotence and Recovery

Every step is an ordinary source edit plus a test run; all are safe to repeat. `cabal test`
runs are idempotent — each example gets a fresh clone of the suite's template database and
drops it afterward, and the ephemeral server is cached and restored per run. No production
data is touched anywhere in this plan; the only database rows affected by adoption are
advisory snapshot rows in developers' local `jitsurei` databases, which regenerate on the
next policy-triggered append. If a partial edit leaves the tree unbuildable, `git status` /
`git diff` against the small file set above (one library module, one test module, two
jitsurei modules, three guides, one ADR) localizes the damage; reverting any single file
restores a consistent state because the change is purely additive at the library level. If
the ADR amendment trips `just adr-validate`, fix frontmatter drift (the bundle is strict
about `docId`, timestamps, and the log); the code milestones do not depend on the ADR step
and remain valid while it is retried.

# Add typed domain outcomes to the DSL

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries,
Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.
If durable project context changes, update or create ADRs in docs/adr/ in the same change.


## Purpose / Big Picture

After [the runtime outcome API](231-add-typed-domain-command-outcomes.md) is stable, a Keiro
DSL author will be able to declare the aggregate's typed rejection and no-op result types
and label every live transition as accepted, rejected with a typed reason expression, or
no-op with a typed explanation. Generated Haskell will expose a
`DomainCommandHandler` wired to the exact edge selected by Keiki, so services receive the
same typed `DomainDecision` whether their aggregate was handwritten or generated.

The feature belongs in the DSL because outcome completeness, type correctness, event
cardinality, and state-preservation can be checked when the model is authored. It is a good
language addition only if it does not invent a second guard evaluator or change event
history. The generated classifier therefore dispatches exclusively on Keiki's exact
`EdgeRef`, reason expressions reuse the existing typed term evaluator, and direct nested
state/index cases keep classification independent of edge position. Generated source grows
once per annotated silent edge and is guarded by fixed-size scaling benchmarks.

The observable demonstration is a language-5 aggregate with accepted, rejected, and no-op
edges. `keiro-dsl check` accepts the complete model and rejects missing or inconsistent
annotations. Scaffolding generates a compiling domain handler and conformance package.
Behavior tests prove the exact rejection/no-op reason for sibling edges, mutation tests
detect a swapped edge reason, and a language-4 golden fixture remains byte-for-byte
unchanged.

## Surprises & Discoveries

- Discovery: Generated outcome classification introduces no new domain evaluation, but a
  naive association-list or sequential edge search would make each classification linear in
  the number of silent edges. The generator must instead emit direct nested `case` dispatch
  by source state and zero-based edge index, and source/generation scaling needs its own
  evidence.


## Decision Log

- Decision: Make this plan depend on Plan 231 and do not implement a provisional private
  runtime result type in generated code.
  Rationale: Generated and handwritten aggregates must share one public command contract;
  the DSL should consume a tested API rather than define a competing one.
  Date: 2026-08-10

- Decision: Introduce the syntax only in candidate language 5; leave published languages
  1 through 4 and their generated bytes unchanged.
  Rationale: Outcome clauses are new source syntax. ADR 0016 freezes published versions but
  explicitly permits correcting the active candidate profile before publication.
  Date: 2026-08-10

- Decision: Require an outcome declaration on every live transition in an
  outcome-enabled aggregate.
  Rationale: Exhaustiveness is the main value of a typed domain result. Inferring no-op from
  absence of events or defaulting an omitted clause would preserve the current ambiguity.
  Date: 2026-08-10

- Decision: Permit `accepted` only on transitions with one or more emitted events, and
  permit `rejected`/`no-op` only on eventless state-preserving live transitions.
  Rationale: These categories then agree with persistence facts and the replay-safety
  contract. Replay-only transitions do not execute forward commands and have no outcome.
  Date: 2026-08-10

- Decision: Evaluate a typed reason expression only after Keiki selects the edge, using the
  existing typed term evaluator and the pre-command registers/command.
  Rationale: Exact `EdgeRef` must remain the sole selection authority. Re-evaluating guards
  would risk disagreement and duplicate domain logic.
  Date: 2026-08-10

- Decision: Add separate syntax and runtime capability markers, and make outcome metadata
  part of semantic diff and behavior identity but not fold compatibility.
  Rationale: Tooling must gate and report the new surface exhaustively, while outcome labels
  do not change persisted events, replay, snapshots, or state folding.
  Date: 2026-08-10

- Decision: Generate the handler in the aggregate's generated event-stream module and route
  service execution through the existing single runtime facade.
  Rationale: This follows ADRs 0017 and 0020: one generated owner per path and one supported
  service runtime entry point.
  Date: 2026-08-10

- Decision: Render the silent classifier as a nested source-state/edge-index `case`, emit
  exactly one arm per silent edge, and extend the existing DSL scaling benchmark rather than
  introducing a runtime map or a second selection table.
  Rationale: Direct pattern dispatch keeps reason lookup independent of declaration position,
  while one constant-size arm per edge keeps generated source and generation time linear.
  The selected arm alone evaluates its reason term, so unselected reasons allocate nothing
  and the returned payload does not keep the whole `SilentCommandContext` alive.
  Date: 2026-08-10

- Decision: Generate directly against the committed Plan 231 runtime names and
  ADR 0029; do not add a naming adapter in generated code.
  Rationale: The planned core type names landed unchanged. The exact integration
  points are `runDomainCommandWithProjections`,
  `runDomainCommandWithCatalogProjections`, `DomainProcessManager`,
  `DomainRouter`, and their `runDomain*` one-shot/worker families.
  Date: 2026-08-10

## Context and Orientation

This plan is the DSL follow-up requested alongside
[`docs/improvement-requests/return-typed-domain-command-outcomes-and-rejection-details.md`](../improvement-requests/return-typed-domain-command-outcomes-and-rejection-details.md).
It must begin only after [Plan 231](231-add-typed-domain-command-outcomes.md) has delivered
and named the runtime `DomainDecision`, `DomainCommandOutcome`, `SilentCommandContext`, and
`DomainCommandHandler` interfaces. Those names landed unchanged, together with
`SilentDomainDecision`, `runDomainCommand`, and `forgetDomainDecision`.
Outcome-aware integration uses `runDomainCommandWithSql`,
`runDomainCommandWithSqlEvents`, `runDomainCommandWithProjections`,
`runDomainCommandWithCatalogProjections`, `DomainProcessManager`, and
`DomainRouter`; the coordinator modules export both detailed one-shot and
bounded-retention worker entry points. Generated code should construct the
handler and let each application/runtime facade choose the appropriate runner.

`keiro-dsl/src/Keiro/Dsl/Grammar.hs` defines the parsed `Aggregate` and `Transition` nodes.
A transition currently contains source state, command, implementation kind, optional guard,
register writes, emitted event names, target state, live/replay-only mode, and location. It
does not carry a domain outcome. `keiro-dsl/src/Keiro/Dsl/Parser/Aggregate.hs` parses clauses
such as `guard`, `write`, `emit`, `implementation hole`, and `goto`; it is the place to add
the aggregate-level outcome declaration and transition-level outcome clause.
`keiro-dsl/src/Keiro/Dsl/PrettyPrint.hs`, canonical encoding, source indexing, and parser
round-trip tests must evolve in lockstep with the AST.

`keiro-dsl/src/Keiro/Dsl/Expression.hs` and
`keiro-dsl/src/Keiro/Dsl/Parser/Expression.hs` already support typed scalar expressions over
command fields, aggregate registers, literals, enums, ids, time, and mapped scalar values.
The generator can lower those expressions to Keiki `Term`s, and
`mori://shinzui/keiki/packages/keiki` exports `evalTerm`. Outcome reasons should reuse this
path instead of adding a Haskell callback hole or a second expression language.

`keiro-dsl/src/Keiro/Dsl/Validate.hs`, `TypeGraph.hs`, and the aggregate checks enforce name,
type, reachability, determinism, replay, and state-changing-epsilon constraints. The DSL can
therefore reject accepted transitions with no events, silent outcomes that emit or mutate
durable state, missing/duplicate outcome clauses, a reason with the wrong declared type, and
outcomes on replay-only edges before Haskell generation. The runtime still receives a
`ValidatedEventStream`, whose Keiki validation force-enables the durable epsilon check.

`keiro-dsl/src/Keiro/Dsl/LanguageVersion.hs` declares syntax features, runtime capabilities,
and per-language profiles. Languages 1 through 4 are published. Language 5 is the active
candidate and already owns projection-catalog features. Each new runtime capability needs an
explicit entry in the exhaustive fold-compatibility segment; omission is intentionally a
compile error.

`keiro-dsl/src/Keiro/Dsl/Diff.hs`, `SemanticContract.hs`, `SemanticImpact.hs`,
`FoldFingerprint.hs`, and `CanonicalEncoding.hs` decide which source changes are behavior,
runtime, or persistence changes. Changing `rejected AlreadyCancelled` to
`rejected CapacityUnavailable` changes command behavior and must appear in semantic diff and
behavior identity. It must not alter fold fingerprints, historical event compatibility,
snapshot compatibility, or replay requirements because neither annotation changes stored
events.

`keiro-dsl/src/Keiro/Dsl/AggregateGenerationPlan.hs`, `EventOutput.hs`,
`GeneratedHaskellLanguage.hs`, and `Scaffold.hs` plan and render the generated aggregate
modules. Today the generated `.../EventStream.hs` owns the validated stream. It should also
own the `DomainCommandHandler` and a pure exact-edge classifier. The classifier can pattern
match on `EdgeRef.edgeSource` and `edgeIndex`, then evaluate the corresponding typed reason
term using the pre-command registers and command from `SilentCommandContext`.

`keiro-dsl/bench/parser-scaling/Main.hs` and the `keiro-dsl-parser-bench` component already
measure source/workspace scaling with `tasty-bench`. Extend that integration point with
outcome-enabled check and generation scenarios rather than adding another benchmark package.
Generated classifier source must contain one constant-size arm per silent edge. A direct
nested `case` first on source state and then on the contiguous edge index avoids a runtime
list traversal or map lookup, evaluates only the selected reason, and lets GHC compile the
index dispatch efficiently. Compilation still processes source proportional to edge count;
that linear code-size cost is intentional and must be visible in the scaling evidence.

`keiro-dsl/src/Keiro/Dsl/BehaviorCoverage.hs` and the generated `BehaviorContract` currently
model `LiveExpectation` as `Emits (NonEmpty event)`, generic `Rejects RejectionClass`, or
`NoOp`. Generic rejection covers `NoOutgoingEdges` and `NoMatchingEdge`; successful no-op
checks the exact selected edge plus state/register preservation. Plan
[159](159-generate-complete-reachable-state-holes-and-spec-behavioral-conformance.md)
explicitly deferred domain-specific reason support to this improvement request. This plan
must extend accepted silent-edge conformance with exact typed reasons while retaining generic
unmatched-step coverage.

`keiro-dsl/src/Keiro/Dsl/ConformancePackage.hs`, `StructuralConformance.hs`,
`RuntimePackage.hs`, and `ScaffoldRun.hs` define generated package dependencies and file
ownership. A new fixture package such as
`keiro-dsl/test/conformance-domain-outcomes/` should exercise the public generated surface
through `keiro`, not import internal source modules ad hoc.

The relevant ADRs are:

- [ADR 0002](../adr/0002-replay-only-edges-are-the-sanctioned-remedy-for-guard-tightening.md): replay-only
  edges never handle forward commands and receive no outcome clause.
- [ADR 0004](../adr/0004-evolution-changes-are-gated-at-the-earliest-sound-boundary.md):
  all syntactically knowable outcome errors belong in DSL validation, with the existing
  validated runtime boundary as defense.
- [ADR 0016](../adr/0016-source-language-provenance-wraps-the-semantic-keiro-dsl-graph.md):
  new syntax and runtime needs source-version provenance; candidate language 5 can be
  amended, published languages cannot.
- [ADR 0017](../adr/0017-aggregate-transitions-have-explicit-generated-or-hole-behavior-ownership.md):
  exact `EdgeRef` is the conformance identity, eventless state change is invalid, and every
  generated path has one owner.
- [ADR 0018](../adr/0018-runtime-semantics-use-capability-profiles-and-frozen-fold-identity.md): every
  capability is typed, profile-gated, and exhaustively assigned fold impact.
- [ADR 0020](../adr/0020-service-conformance-packages-import-one-runtime-owned-facade.md):
  generated service packages consume one runtime facade and preserve generated/create-once
  ownership.

[ADR 0029](../adr/0029-typed-domain-decisions-are-successful-additive-command-outcomes.md)
is the committed runtime-domain-outcome decision. At the start of this
implementation, decide whether the DSL consequences fit as an amendment or need
a separate ADR. Do not duplicate or contradict its definition of rejection,
no-op, unmatched failure, retry authority, or payload-free telemetry.


## Plan of Work

### Milestone 1: grammar, AST, and semantic checking

First reconcile the interfaces in Plan 231 with the committed exports in
`keiro/src/Keiro/Command.hs`; record any naming-only adjustment in this plan's Decision Log.
Then extend `keiro-dsl/src/Keiro/Dsl/Grammar.hs` with aggregate-level domain outcome type
references and a transition outcome sum. Extend
`keiro-dsl/src/Keiro/Dsl/Parser/Aggregate.hs` and `PrettyPrint.hs` with this candidate syntax:

```text
language keiro-dsl 5

enum ReservationRejection { AlreadyCancelled=already-cancelled CapacityUnavailable=capacity-unavailable }
enum ReservationNoOp { DuplicateRequest=duplicate-request }

aggregate Reservation
  domain-outcomes rejection=ReservationRejection no-op=ReservationNoOp
  ...

  Eligible -- Cancel -->
    outcome accepted
    emit Cancelled
    goto CancelledState

  CancelledState -- Cancel -->
    guard cmd.requestId != reg.lastRequestId
    outcome rejected ReservationRejection.AlreadyCancelled
    goto CancelledState

  CancelledState -- Cancel -->
    guard cmd.requestId == reg.lastRequestId
    outcome no-op ReservationNoOp.DuplicateRequest
    goto CancelledState
```

The aggregate declaration enables the feature and supplies both result types. Each live
transition in an enabled aggregate has exactly one `outcome` clause. `accepted` has no reason
expression and requires at least one `emit`. `rejected <expr>` and `no-op <expr>` require no
emits, no writes, and `goto` equal to the source. Replay-only transitions reject an outcome
clause and are excluded from exhaustiveness. Aggregates without `domain-outcomes` retain
their current syntax and semantics.

Extend expression ownership/source mapping so a reason expression receives the same source
locations and typed roots as guards and writes. In `Validate.hs` and the checked type graph,
resolve the two declared types, type-check each expression against its corresponding type,
and report stable located diagnostics for missing or duplicate declarations/clauses,
unresolved types, wrong reason type, accepted-without-events, silent-with-events,
silent-with-write, silent-state-change, and replay-only outcome. Add parser round trips,
pretty-print goldens, diagnostic goldens, and a positive `domain-command-outcomes.keiro`
fixture. This milestone is complete when the narrow parser/validation tests pass and a
language-4 fixture rejects the new syntax with the language-feature diagnostic.

### Milestone 3: generated handler and service facade

Extend `AggregateGenerationPlan.hs`, `EventOutput.hs`, `HaskellImport.hs`, and `Scaffold.hs`
so an outcome-enabled generated aggregate's `Generated/<Context>/<Aggregate>/EventStream.hs`
exports the Plan 231 `DomainCommandHandler` alongside its `ValidatedEventStream`. Generate a
total classifier over every exact live silent-edge `EdgeRef`. For each arm, evaluate the
already type-checked reason `Term` with Keiki `evalTerm` using the pre-command register file
and command from `SilentCommandContext`. Accepted edges never enter the silent classifier.
An impossible edge reference should fail with a generated invariant message naming the
aggregate and edge, not default to a reason.

Render the classifier as a nested `case`: first match `edgeSource`, then match the
zero-based `edgeIndex` within that source. Emit exactly one arm for every rejected/no-op edge
and no arm for accepted or replay-only edges. Do not generate an association list, `Map`,
linear `find`, repeated guard predicates, or one whole copy of the command/register context
per arm. Bind the context fields once outside the nested dispatch and construct the strict
`SilentRejected` or `SilentNoOp` value directly around the selected `evalTerm` result. This
keeps runtime selection independent of whether the matching edge is first or last and lets
the returned value release the context except for data deliberately contained in the reason.

Update generated aggregate/service harnesses and the service runtime facade to expose the
outcome-aware direct, projection, router, and process-manager runners delivered by Plan 231.
Do not generate new create-once holes for reasons: the DSL expression owns the value. Update
`AggregateGenerationPlan`, manifest, scaffold-record, and import-planning tests so each new
file/export has exactly one owner and collisions are diagnosed before writes.

Scaffold the positive fixture twice into a clean temporary directory and compare trees to
prove idempotence. Compile the generated package through its public Cabal dependency on
`keiro`. Extend `keiro-dsl/bench/parser-scaling/Main.hs` with outcome-enabled check and
generation fixtures containing 8, 32, 128, and 512 silent edges. Add structural generation
tests that count exactly one classifier arm per silent edge and reject generated source that
imports a map or contains sequential `lookup`/`find` dispatch. Record a committed
`keiro-dsl/bench/baseline-domain-outcomes.csv` and add it to `Justfile`'s manual
`bench-regression` target using the repository's 25-percent regression convention.

## Validation and Acceptance

Acceptance requires these externally observable behaviors:

1. A language-5 aggregate with declared rejection/no-op types and exactly one valid outcome
   on every live transition parses, pretty-prints, reparses to the same AST, validates, and
   scaffolds successfully.
2. The same syntax under languages 1, 2, 3, or 4 fails with the standard located
   feature/version diagnostic. Existing language-4 emitted canonical bytes and generated
   goldens remain byte-for-byte equal.
3. Missing/duplicate aggregate declarations, missing/duplicate live-edge clauses, unresolved
   outcome types, and ill-typed reason expressions each fail `keiro-dsl check` at the owning
   source location with a stable diagnostic code.
4. `accepted` without an event, rejected/no-op with any event or write, rejected/no-op whose
   target differs from its source, and any outcome on a replay-only edge are rejected before
   scaffolding writes files.
5. Generated code constructs the Plan 231 `DomainCommandHandler`; accepted commands return
   the exact non-empty event batch, while the two sibling silent edges return their exact
   declared typed reasons without a second guard selection.
6. A truly unmatched command still returns generic `CommandRejected` rather than one of the
   declared reasons. An ambiguous command remains `CommandAmbiguous`.
7. Changing only an outcome kind, type, or reason expression produces a precise
   command-behavior semantic diff and changes behavior identity, while fold fingerprints,
   event compatibility, snapshot compatibility, and replay impact remain unchanged.
8. `DomainCommandOutcomeSyntax` and `TypedDomainCommandOutcomes` are present only in the
   candidate language-5 profiles, and the latter has an explicit `Nothing` fold segment.
   Exhaustiveness tests fail if a capability branch is omitted.
9. The generated event-stream module is the single owner of the handler, the service package
   uses the supported runtime facade, and a second scaffold into the same tree is idempotent.
   No generated/create-once ownership path collides.
10. Generated conformance compares exact typed reasons. Swapping two handler edge mappings,
    changing rejection to no-op, or changing a reason makes the mutation suite fail; it
    cannot pass because expected and actual values came from the same generated mapping.
11. Documentation gives a complete compilable syntax example, explains expression scope and
    migration from legacy epsilon edges, and distinguishes a domain result from unmatched
    failure and persistence/replay impact.
12. The runtime ADR is reconciled, any DSL ADR is allocated and validated, the improvement
    request records both completed plans, and all commands in Concrete Steps succeed.
13. Generated classifier source has exactly one direct arm per rejected/no-op edge, groups

## Idempotence and Recovery

Parser, validation, build, test, diff, formatting, and OKF commands are safe to repeat.
Scaffolding must itself be idempotent: rerunning it against the same checked source and output
directory must not alter create-once files or change generated bytes. Use `mktemp -d` for
experiments; retain the exact printed path and never apply recursive cleanup to an unresolved
variable or repository directory.

The committed conformance tree is generated output. Change the grammar/generator first and
regenerate through the normal scaffold command; do not hand-edit generated modules to make a
golden pass. Preserve create-once Haskell fills. If ownership planning refuses a partially
generated tree, inspect its scaffold record and rerun into a fresh temporary directory before
changing any committed sidecar.

The outcome-generation benchmark is deterministic input generation plus pure check/render
work and is safe to repeat. Refresh
`keiro-dsl/bench/baseline-domain-outcomes.csv` only after investigating a reported change in
time, residency, or rendered byte growth; do not make a regression disappear by replacing
the baseline without recording the reason in Progress and Surprises & Discoveries.

Published language profiles and their goldens are recovery anchors. If a change unexpectedly
moves language-4 bytes or fold fingerprints, stop and fix the new feature gate rather than
refreshing those baselines. Candidate language 5 may be corrected in place, but do not mark
it published as part of this feature.

The outcome annotation carries no durable state and requires no data migration or rollback.
Removing it after deployment changes the generated command API, so the safe application
rollback is to keep the prior generated facade and DSL source together. Preserve unrelated
dirty work and avoid destructive Git recovery commands.

Do not update the improvement request to implemented until Plan 231 and every milestone here
have passed. If an ADR identifier was allocated, retain and correct it rather than deleting
or reusing the identifier.

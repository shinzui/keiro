# Render generated structural Haskell types with minimal safe parentheses

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries,
Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.
If durable project context changes, update or create ADRs in docs/adr/ in the same change.


## Purpose / Big Picture

After this change, structural Haskell types generated by `keiro-dsl scaffold` use only
the parentheses required by Haskell's type grammar. A generated record field declared
as `Optional Text` will read `description :: !(Maybe Text)` instead of
`description :: !(Maybe (Text))`; a `List Text` field will read `tags :: ![Text]`
instead of `tags :: !([Text])`. Nested expressions remain unambiguous: for example,
`List (Optional Text)` becomes `![Maybe Text]`, while a strict `Map Text` remains
`!(Map Text Text)` because a type application must be grouped after a strictness bang.

The result is observable by scaffolding
`keiro-dsl/test/fixtures/structural-conformance.keiro` and inspecting the generated
`Structural/Shape` modules. Focused renderer assertions and the compiled structural and
behavior-complete conformance suites will prove that the output is both more idiomatic
and accepted by GHC. This is a presentation-only change: parsed DSL meaning, wire
schemas, fingerprints, imports, binding APIs, and runtime behavior must remain
unchanged.

## Surprises & Discoveries

- Observation: `renderShapeType` in
  `keiro-dsl/src/Keiro/Dsl/Scaffold.hs` is the only source of the redundant
  parentheses in generated Haskell. The shared `recordFields` helper merely prefixes
  `!`; `renderShapeType` itself currently emits `(Maybe (<child>))`, `([<child>])`, and
  `(Map Text (<child>))`.

- Observation: the same shape renderer is used in two strict contexts. Record fields
  call it through `recordFields`, and structural union constructors call it through
  `renderArm`. A safe correction must cover both rather than special-case record text.

- Observation: a second renderer, `renderExprType` in
  `keiro-dsl/src/Keiro/Dsl/ExplainBindings.hs`, prints similar text such as
  `Maybe (Text)` and `Map Text (Text)`. That text is not generated Haskell: it is a
  human-facing binding signature and is persisted in `keiro-dsl-scaffold-record.*.txt`.
  `newBindingObligations` in `Keiro.Dsl.ScaffoldRun` compares complete `BindingHole`
  values, including that signature. Changing it in this task would make an unchanged
  consumer binding appear as a new obligation on the first scaffold after upgrade.

- Observation: the committed generated corpus contains only three Haskell modules with
  the exact faulty structural-type pattern:
  `keiro-dsl/test/conformance-structural/Generated/StructuralConformance/Structural/Shape/ArtifactInfo.hs`,
  `keiro-dsl/test/conformance-structural/Generated/StructuralConformance/Structural/Shape/ArtifactMetadata.hs`,
  and
  `keiro-dsl/test/conformance-behavior-complete/Generated/BehaviorComplete/Structural/Shape/StartPayload.hs`.
  Other visually similar output is necessary grouping for tuples, type applications
  after `!`, or nested type-constructor arguments such as
  `!(Maybe (K.EdgeRef Vertex))`.

- Observation: the wider generated-Haskell audit found conservative parentheses in two
  expression renderers that do not consume `ResolvedTypeExpr`.
  `renderBranchSchema` can emit `BranchOptional (BranchScalar)`,
  `BranchField ... (BranchScalar)`, and `Just (BranchScalar)` in codec-comparison
  modules. `encodeShapeExpr` can emit `toJSON (item)` and `toJSON (payload)` in
  structural codecs. Those parentheses are redundant for an atomic child but required
  when the same position contains a constructor application, selector application, or
  lambda. They need their own expression-precedence audit and are not safely solved by
  the type renderer in this plan.

- Observation: one committed generated fixture contains the redundant constraint
  `tshow :: (Show value) => value -> Text`, but the current emitter already renders
  `tshow :: Show value => value -> Text`. The main test's `normalizeGenerated` helper
  explicitly tolerates that formatter-only historical spelling, so there is no current
  generator change to make for it here.

- Observation: Cabal 3.16.1.0 splits the plan's quoted
  `--test-options='--match structural scaffold'` value before Hspec receives it, so
  the first focused run exited with `unexpected argument 'scaffold'`. Passing
  `--test-option=--match --test-option='structural scaffold'` preserves the match
  phrase as one argument.
  Evidence: the renderer and test module compiled before the test executable rejected
  the command line, so this did not indicate an implementation failure.

- Observation: the first commit attempt used a stale installed pre-commit hook whose
  Fourmolu command omitted the repository's `GHC2024` and `ImportQualifiedPost` parser
  options, so it could not parse the test module's existing postpositive qualified
  imports. Entering `nix develop` refreshed the generated hook from
  `nix/treefmt.nix`, which already declares those options. The earlier full `nix fmt`
  run had succeeded with the current formatter configuration.

## Context and Orientation

`keiro-dsl` parses source types such as `Optional Text`, `List Text`, and `Map Text`
into `TypeExpr` in `keiro-dsl/src/Keiro/Dsl/Grammar.hs`. Validation and reference
resolution turn those values into the closed `ResolvedTypeExpr` datatype in
`keiro-dsl/src/Keiro/Dsl/TypeGraph.hs`. Its constructors are scalar leaves, `ROptional`,
`RList`, `RMap`, and `RRef`; it contains no function arrows, constraints, infix type
operators, or tuples. `foldTypeExpr` is the total fold used by consumers, so adding a new
type constructor forces this renderer to be updated at compile time.

Structural shapes are private generated representations of consumer-owned mapped types.
`emitShape` in `keiro-dsl/src/Keiro/Dsl/Scaffold.hs` emits one Haskell module per
structural declaration. For a record it passes every resolved field through
`renderShapeType` and then through `recordFields`, which produces `field :: !<type>`.
For a tagged union, `renderArm` produces `Constructor !<type>` from the same renderer.
The renderer therefore returns text suitable immediately after a strictness bang.

Haskell type application associates to the left. `Maybe Text` and `Map Text Text` are
applications, so after `!` they must be grouped as `!(Maybe Text)` and
`!(Map Text Text)`. Scalar names, qualified type names, and list syntax are atomic in
that position, so `!Text`, `!ArtifactKind.ArtifactKindShape`, and `![Text]` require no
outer parentheses. When an application is itself an argument to another application,
it also needs grouping: `Maybe (Map Text Text)` and `Map Text (Maybe Text)`. A list's
brackets already delimit a complete type, so `[Maybe Text]` is unambiguous and more
idiomatic than `[(Maybe Text)]`.

The required rendering examples for this plan are:

```haskell
Text                         -- Text
Optional Text                -- (Maybe Text) after !
List Text                    -- [Text] after !
List (Optional Text)         -- [Maybe Text] after !
Map Text                     -- (Map Text Text) after !
Map (Optional Text)          -- (Map Text (Maybe Text)) after !
Optional (List Text)         -- (Maybe [Text]) after !
Optional (Map Text)          -- (Maybe (Map Text Text)) after !
```

The comments show the source `TypeExpr` followed by the text that
`renderShapeType` must return in its strict context. Parentheses shown around a root
application are part of the returned text because the caller adds `!` without further
syntax awareness.

`keiro-dsl/test/Main.hs` already has a `structural scaffold` Hspec group and helpers
such as `mappedSpec`, `completeStructural`, `recordShape`, and
`generatedTextEndingIn`. It also uses
`keiro-dsl/test/fixtures/consumer-types.keiro`, whose `ArtifactInfo` record covers
`Optional Text`, `List Text`, `List (Optional Text)`, and `Map Text`. That is the primary
focused regression surface. The compiled suites
`keiro-dsl-conformance-structural` and
`keiro-dsl-conformance-behavior-complete` own the committed generated modules affected

## Plan of Work

### Milestone 1: Make structural type rendering precedence-aware

Edit `renderShapeType` and nearby private declarations in
`keiro-dsl/src/Keiro/Dsl/Scaffold.hs`. Keep
`renderShapeType :: HaskellImportPlan -> Context -> TypeGraph -> ResolvedTypeExpr -> Text`
unchanged for its callers. Change its `foldTypeExpr` result from raw `Text` to a small
private value containing the rendered text and whether the result is an atomic type or
a type application.

Scalar leaves and resolved references are atomic. `ROptional` constructs the application
`Maybe <argument>`, and `RMap` constructs `Map Text <argument>`; both are application
results. `RList` constructs `[<complete child type>]` and is atomic. Add one helper that
renders a child in application-argument or strict-bang position: return an atomic child
unchanged and wrap an application child in one pair of parentheses. Use that helper for
the child of `Maybe`, the value of `Map`, and the final root returned by
`renderShapeType`. Do not use it inside list brackets, which accept a complete type and
therefore render `[Maybe Text]` directly.

Add focused examples to the `structural scaffold` group in
`keiro-dsl/test/Main.hs`. The existing `consumer-types.keiro` shape assertion must pin
the exact field fragments `description :: !(Maybe Text)`, `tags :: ![Text]`,
`labels :: ![Maybe Text]`, and `attributes :: !(Map Text Text)`, and must reject the four
legacy spellings `description :: !(Maybe (Text))`, `tags :: !([Text])`,
`labels :: !([(Maybe (Text))])`, and `attributes :: !(Map Text (Text))`. Extend the
named `Keiro.Dsl.Scaffold` import with its already-exported `scaffoldStructural`
function. Add a synthetic `mappedSpec` case using `recordShape` to pin nested
`Map (Optional Text)`, `Optional (List Text)`, and `Optional (Map Text)` output. Add a
synthetic structural union with optional, list, and map payload arms so the shared strict
union context is independently protected.

Milestone 1 is complete when the focused Hspec group passes and its expected strings
demonstrate both parenthesis removal and preservation. A mutation that removes the root
parentheses from `Maybe` or `Map`, or one that leaves the outer list parentheses, must

## Interfaces and Dependencies

This plan uses only repository-local modules and the existing GHC/Cabal toolchain. Per the
repository dependency policy, no external API lookup or dependency-bound change is
required.

`Keiro.Dsl.TypeGraph` supplies `ResolvedTypeExpr`, `MappedKey`, `TypeExprAlgebra`, and
`foldTypeExpr`. `Keiro.Dsl.Scaffold` continues to publish no new API. Its existing private
entry point remains:

```haskell
renderShapeType :: HaskellImportPlan -> Context -> TypeGraph -> ResolvedTypeExpr -> Text
```

Add only private implementation types and helpers near that function. One acceptable
shape is a two-constructor precedence type (`AtomicType` and `ApplicationType`) plus a
record containing precedence and rendered `Text`, and a helper with behavior equivalent
to:

```haskell
renderStrictOrApplicationArgument :: RenderedShapeType -> Text
```

The names are not public contracts, but the semantics are: scalar/reference/list results
are atomic; `Maybe`/`Map` results are applications; application children are parenthesized
only in application-argument or root strict position; list children are rendered as
complete types without an extra group.

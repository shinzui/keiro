# Composable multi-file service workspaces for keiro-dsl

This MasterPlan is a living document. The sections Progress, Surprises & Discoveries,
Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.
If durable project context changes, update or create ADRs in docs/adr/ in the same change.


## Vision & Scope

After this initiative, one Keiro service can keep each complete aggregate in its own
`.keiro` file while `keiro-dsl` treats the set as a single service contract. A small,
deterministic **workspace manifest** names the service, carries the module-root and
layout authority, and lists the member `.keiro` files explicitly; the service's
context comes from the member files themselves, which must agree. `keiro-dsl check`,
`keiro-dsl scaffold`, and `keiro-dsl diff` each accept the manifest as input and operate
on **one resolved service graph**: shared IDs, enums, rules, mapped structural/opaque
declarations, and read models resolve once across all member files, with duplicate and
conflict diagnostics that cite every relevant file and span. Scaffolding plans the
complete generated module set for the whole workspace before writing anything, emits
exactly one context-level `StructuralProjections` facade from the merged mapped-type
graph, and keeps one scaffold record and manifest keyed by a stable workspace identity —
so two aggregates in one context no longer overwrite each other's records, flag each
other's modules as stale, or clobber the context facade from an incomplete graph.
Diffing compares two whole-workspace graphs resolved from git revisions, classifies a
shared-declaration change at every use site, and emits one compatibility vector,
coverage report, and replay-impact report for the service.

The initiative implements
[IR-2](../improvement-requests/support-composable-multi-file-service-specifications-in-keiro-dsl.md)
(`docs/improvement-requests/support-composable-multi-file-service-specifications-in-keiro-dsl.md`),
whose factual claims were verified against this repository on 2026-07-29: every CLI
command today takes exactly one spec file (`keiro-dsl/app/Main.hs`), the scaffold record
and build manifest are keyed only by context
(`keiro-dsl/src/Keiro/Dsl/ScaffoldRecord.hs`, `ScaffoldRun.hs`), the structural facade
module name is purely context-derived and unconditionally overwritten
(`keiro-dsl/src/Keiro/Dsl/Scaffold.hs`), and stale detection compares the previous
context-keyed record against the current single spec's plan — an existing test proves a
second same-context spec reports the first spec's files as stale
(`keiro-dsl/test/Main.hs`, "reports the entire old tree across a module-root flip").
The fleet motivation is real: Kotei keeps one aggregate per file across six-plus
`.keiro` files all declaring `context kotei`
(`/Users/shinzui/Keikaku/bokuno/kotei/kdsl/*.keiro`), while Danwa places three
aggregates in one file — both shapes must remain valid.

In scope: the workspace manifest form and loader, the composed service graph with
cross-file name resolution and conflict refusal, whole-service `check`, whole-service
`scaffold` with workspace-keyed atomic history and an explicit adoption path from
existing per-context records, whole-service `diff` with unified reports, fixtures and
acceptance tests for every IR-2 acceptance bullet, and adoption documentation covering
both the one-file and per-aggregate layouts. Existing single-file commands, grammar,
golden fixtures, and generated bytes for a single-spec context remain unchanged; a
single `.keiro` file behaves as a one-member workspace.

Out of scope, per IR-2's own exclusions: partial aggregate declarations spread across
files, order-sensitive textual includes or macros, dynamic runtime loading or plugin
discovery, cross-service private-type sharing, weakening the generated-ring/Holes
firewall, and merging separate bounded contexts merely because they share a repository.
Also out of scope: transactional (staged temp-file/rename) writes for the module
emission loop itself. IR-2's atomicity requirement is that every refusal, collision,
parse error, or validation error is detected **before** the first output byte changes;
that matches the existing plan-then-write architecture in
`keiro-dsl/src/Keiro/Dsl/ScaffoldRun.hs` and this initiative extends detection to the
whole workspace rather than introducing filesystem transactions.


## Decomposition Strategy

The initiative decomposes by functional concern into four child plans: one foundation
plan that decides the workspace form and builds the loader, composed graph, and
whole-service `check`; two consumer plans that retarget the scaffolder and the differ
onto the composed graph; and one proving plan that adds the fleet-style fixture,
end-to-end acceptance tests, and documentation. The foundation must come first because
every other plan consumes its artifacts — the manifest grammar, the `WorkspaceSpec`
resolved graph, the multi-file diagnostic type, and the CLI input dispatch. Scaffolding
and diffing are independent of each other (they share only read access to the composed
graph and the workspace identity) and can proceed in parallel once the foundation is
complete. The proving plan comes last because its acceptance scenarios exercise all
three commands against the same fixture workspace.

The alternative decomposition of putting the design decision (manifest form, identity,
ownership rules) in its own plan was rejected: the decision is only testable through the
loader that implements it, and a decision-only plan would produce no independently
verifiable behavior. Instead the foundation plan's first milestone records the durable
decision as an ADR. A second alternative — folding scaffold and diff into one "consumers"
plan — was rejected for scope balance: each retarget touches a distinct subsystem
(`ScaffoldRun`/`ScaffoldRecord`/`Manifest` versus `Diff`/`DiffReport`/`ReplayImpact`/
`Coverage`) and each is independently verifiable, so merging them would create one
oversized plan with no coupling benefit.

ADR context, per `agents/skills/exec-plan/ADR.md`: the local corpus was scanned and no
existing ADR covers workspaces, multi-file input, or scaffold-record identity. Three
records constrain the design and are carried into the children:
[ADR-4](../adr/0004-evolution-changes-are-gated-at-the-earliest-sound-boundary.md)
(`docs/adr/0004-evolution-changes-are-gated-at-the-earliest-sound-boundary.md`) — each
evolution hazard is checked at the earliest boundary with enough evidence, which is why
cross-file conflicts must be refused at compose time rather than surfacing later as
scaffold collisions;
[ADR-12](../adr/0012-structural-consumer-mappings-use-one-schema-authority-and-total-bindings.md)
(`docs/adr/0012-structural-consumer-mappings-use-one-schema-authority-and-total-bindings.md`)
— one schema authority per structural mapping, which forces a shared declaration such as
`ProjectId` to resolve to exactly one nominal generated type across the workspace; and
[ADR-13](../adr/0013-structural-coverage-is-reporting-first-and-opacity-gates-are-opt-in.md)
(`docs/adr/0013-structural-coverage-is-reporting-first-and-opacity-gates-are-opt-in.md`)
— coverage stays reporting-first, so the whole-service coverage report aggregates
per-file findings without inventing new gates. The improvement request itself
originates from the Mori project (`origin: mori://shinzui/mori`, Mori MasterPlan 22);
no cross-repository ADR governs this design, so the workspace decision will be recorded
locally as a new ADR by EP-1 (expected `ADR-14` via `okf id next`).

## Dependency Graph

EP-1 has no dependencies and must be implemented first. It delivers the artifacts
every other plan compiles against: the workspace manifest grammar and parser, the
`WorkspaceSpec` composed-graph type with per-declaration source ownership, multi-file
diagnostics, and the CLI dispatch that recognizes a workspace input versus a single
`.keiro` file.

EP-2 hard-depends on EP-1 because the scaffold planner's new entry point takes a
`WorkspaceSpec` — without it there is nothing to plan over, and the workspace identity
that keys the new record does not exist. EP-3 hard-depends on EP-1 for the same
artifacts plus the loader's ability to resolve a workspace from an arbitrary source
(the working tree now, `git show` blobs for `--since`).

EP-2 and EP-3 do not depend on each other and can proceed in parallel after EP-1.
They share an integration point rather than a dependency: both consume the workspace
identity and the composed graph read-only, and EP-3's ownership-move reporting must
agree with EP-2's record ownership model (see Integration Points). Whichever lands
second must reconcile against the first's merged code.

EP-4 hard-depends on all three: its fixture workspace is checked with EP-1's `check`,
scaffolded twice for idempotence with EP-2's `scaffold`, and diffed across revisions
with EP-3's `diff`. Documentation cannot honestly describe workflows that do not exist
yet.


## Integration Points

**Workspace manifest format and identity.** Defined by EP-1 and recorded in a new ADR.
Consumed by every other plan: EP-2 keys the scaffold record and build manifest by the
workspace identity, EP-3 resolves the old member set from the manifest at a git
revision and stamps the identity into its reports, EP-4 documents the format. The
manifest is a file (not repeated CLI flags), because `diff --since <rev>` must be able
to reconstruct the member list as it existed at `<rev>` from git alone, and because the
scaffold record needs one durable identity that outlives file renames. Later plans must
not invent secondary identity sources.

**`WorkspaceSpec` composed graph and loader API.** Defined by EP-1 in a new module
(working name `keiro-dsl/src/Keiro/Dsl/Workspace.hs`). It carries the merged
declarations with per-declaration owning file and span, the member `Spec`s, and the
effective context/module-root/layout. EP-2 and EP-3 take it as their input type and
must not re-parse member files themselves; EP-1 also provides source-abstract loading
(filesystem or `git show` content) so EP-3 does not shell out per member file with its
own logic.

**CLI input dispatch.** Defined by EP-1 in `keiro-dsl/app/Main.hs`: how a command
decides its `FILE` argument is a workspace manifest versus a single `.keiro` spec, and
the shared single-file-as-one-member-workspace fallback. EP-2 and EP-3 extend
`scaffold` and `diff` through the same dispatch; they must not add parallel flags or
subcommands.

**Scaffold record and build manifest schema.** Extended by EP-2
(`keiro-dsl/src/Keiro/Dsl/ScaffoldRecord.hs`, `Manifest.hs`): workspace-keyed file
names, per-module source-file ownership so moving an aggregate between member files is
an ownership move rather than a stale/new pair, and the versioned adoption path that
imports existing per-context records without deleting anything. EP-3 reports ownership
moves and must classify them exactly as EP-2 records them. EP-4 tests migration from
independently scaffolded per-context records.

**Multi-file diagnostics.** EP-1 extends diagnostic rendering
(`keiro-dsl/src/Keiro/Dsl/Validate.hs` renders with a single file path today) so one
diagnostic can cite locations in several files. EP-3 reuses the same rendering for
use-site classification findings. The diagnostic shape is EP-1's to define.

Cross-plan decisions that should become ADRs: the workspace identity and
shared-declaration ownership rules with the no-silent-merge stance (EP-1); the
workspace-keyed scaffold history model and its adoption semantics from per-context
records (EP-2, extending EP-1's ADR or adding its own); and the deliberate exclusion
of filesystem-transactional writes (recorded in this MasterPlan's scope, promoted if
it proves contentious during implementation).

## Surprises & Discoveries

Document cross-plan insights, dependency changes, scope adjustments, or unexpected
interactions between child plans. Provide concise evidence.

- **EP-1 delivered seven workspace `DiagnosticCode`s, not nine.** Manifest syntax and
  structure refusals (a member listed twice, an invalid member path) carry no code,
  because a malformed manifest never reaches the composer — exactly as a malformed
  `.keiro` file never reaches `validateSpec` and carries no code either. Adding
  constructors nothing can emit would put permanently dead entries in an append-only
  registry. **EP-2 and EP-3 must not expect `WorkspaceDuplicateMember` or
  `WorkspaceInvalidMemberPath`.** The codes that exist are
  `WorkspaceMemberUnreadable`, `WorkspaceMemberParseFailed`, `WorkspaceContextMismatch`,
  `WorkspaceAuthorityConflict`, `WorkspaceDuplicateDeclaration`,
  `WorkspaceDuplicateNodeName`, and `WorkspacePathCollision`. (2026-07-29)

- **The only existing seam from a planned module back to its owning node is the origin
  string.** `Keiro.Dsl.Scaffold.nodeOrigin` formats it as `<kind> <name> (line N)`, and
  EP-1's cross-member collision check recovers ownership by parsing that suffix and
  resolving the line through the workspace line map. It works — the
  `workspace-path-collision` fixture proves it end to end — but it is string-shaped.
  **EP-2 needs per-module source ownership as a first-class record field**, so EP-2
  should add a structured owner to `ScaffoldModule` (or to the planner's result) rather
  than parsing origins, and may then simplify EP-1's collision check to use it. Note the
  happy accident this seam gives for free: context-level modules (the
  `StructuralProjections` facade, the replay-audit assembly) carry no line, are emitted
  once for the whole merged spec, and therefore cannot produce a false cross-member
  collision. (2026-07-29)

- **`ContentSource` is rooted at the manifest's own directory, and the manifest is read
  through it by base name.** So EP-3's git-blob source must be rooted at the manifest's
  *repository-relative directory* at the target revision, after which every member path
  from the manifest resolves unchanged. This is why member paths are constrained to stay
  inside the manifest's tree. (2026-07-29)

- **EP-1's cross-member collision check is deliberately skipped when the merged spec has
  any error diagnostic**, because the scaffold planner is only ever fed specs that passed
  validation. **EP-2 must keep its own intra-member collision gate**: `check` still does
  not catch a collision that lives entirely inside one member, and must not start to —
  that would change existing single-file behavior. (2026-07-29)

- **`Keiro.Dsl.Workspace` imports `Keiro.Dsl.ScaffoldRun`, so no `WorkspaceSpec`-taking
  function can live in `ScaffoldRun`.** EP-1's cross-member collision check calls
  `planScaffoldWithGoldens`, which makes the dependency one-way and permanent. EP-2's plan
  had specified `planWorkspaceScaffoldWithGoldens` and `executeWorkspaceScaffold` as
  additions to `ScaffoldRun.hs`; they landed in new modules
  `keiro-dsl/src/Keiro/Dsl/WorkspaceScaffold.hs` and
  `keiro-dsl/src/Keiro/Dsl/WorkspaceAdoption.hs` instead, with `ScaffoldRun` exporting the
  gates and helpers they reuse (`pureRefusals`, `missingGeneratedBanners`, `staleAgainst`,
  `constraintPlan`, `mappingDrift`, `newBindingObligations`). **EP-3 must plan for the same
  constraint**: whole-workspace diffing consumes `WorkspaceSpec` and so cannot extend
  `Keiro.Dsl.Diff` if that module ever becomes a `Workspace` dependency — today it is not,
  so `Diff` is still open to it, but check before assuming. (2026-07-29)

- **Ownership is now first-class, and EP-1's origin-string parsing can be retired.** EP-2
  added `scaffoldStructuralOwners` and `bindingSkeletonOwners` to `Keiro.Dsl.Scaffold`
  (each defined so the existing function is `map fst` of it) plus `nodeIdentity` lookups
  through `wsOwnership`, giving every planned module a structured
  `ModuleProvenance = ContextLevel | MemberOwned FilePath`. EP-1's collision check still
  recovers ownership by parsing `nodeOrigin`'s `(line N)` suffix; it works and is proven by
  the `workspace-path-collision` fixture, so it was left alone rather than rewritten
  mid-initiative, but the structured seam now exists if it becomes a maintenance problem.
  **EP-3 should consume `ModuleProvenance`/the record's optional `owner` field, not
  origins.** (2026-07-29)

- **An ownership move must be classified as path-unchanged-owner-changed, and EP-3 must
  match it exactly.** `OwnershipMove { omPath, omPrevious, omCurrent }` in
  `Keiro.Dsl.WorkspaceScaffold` is computed against the previous workspace record before
  stale detection and can never overlap it, because a moved module's path is still produced.
  `Nothing` on either side means context-level. The scaffold report proves the move is not a
  content change: the test asserts every disposition is `unchanged`/`skipped`. A diff that
  reported such a move as a removal plus an addition would contradict the record.
  (2026-07-29)

- **A binding skeleton can belong to no single member.** `bindingSkeletonModules` groups
  obligations by owning module, and its own comment notes that several mapped declarations
  may intentionally share one leaf binding module — across members, in a workspace. Such a
  module is recorded as context-level (owner absent), the same as the facade and the
  replay-audit assembly. **EP-3 and EP-4 must not assume ownerless implies "facade or
  replay-audit".** (2026-07-29)

- **`oneMemberWorkspace :: FilePath -> Spec -> WorkspaceSpec` is available and proven
  equivalent** to single-spec validation, diagnostic for diagnostic, over four fixtures
  including one that produces errors. EP-2 and EP-3 can take `WorkspaceSpec` as their
  only input type and route single `.keiro` files through it — while the CLI keeps the
  pre-existing single-file branches textually untouched, which is what guarantees
  byte-identical behavior for existing users. (2026-07-29)

- **Whole-workspace diff citations are top-level owner spans plus exact semantic
  paths.** EP-1's `OwnershipIndex` stores each shared declaration or node's original
  `Loc`, while the existing differ stores exact nested uses as `ckPaths` without field
  spans. EP-3 therefore renders a precise semantic path and cites the owning
  declaration's start line. **EP-4 must assert this established shape rather than
  expecting nested field source lines that no current graph carries.** The committed
  workspace diff golden is the contract tripwire. (2026-07-29)

- **Workspace report values live at the JSON schema owner and are re-exported by the
  diff wrapper.** `OwnedSite`, `WorkspaceChange`, `WorkspaceMeta`, and
  `WorkspaceDiffReport` are defined in `Keiro.Dsl.DiffReport` to avoid a cycle
  (`WorkspaceDiff` needs `renderFinding`; the report needs owned changes), then
  re-exported from `Keiro.Dsl.WorkspaceDiff`. EP-4 should consume the wrapper's public
  API, not depend on the defining module as an ownership claim. (2026-07-29)

- **The prerequisite plans already produced the right fleet fixture and acceptance
  seams.** EP-4 promoted `keiro-dsl/test/fixtures/workspace/` rather than creating a
  duplicate `workspace-fleet/`: EP-1 owns its composition tests, EP-2 owns its plan and
  filesystem tests, and EP-3's separate old/new fixtures own shared-declaration evolution.
  EP-4 added the missing CLI assertion that parse, validation, and collision failures in
  any member leave the prior output tree and bookkeeping byte-identical. The final suite
  has 373 examples and zero failures. (2026-07-29)


## Decision Log

- Decision: Implement IR-2 as a MasterPlan with four child plans (foundation, scaffold,
  diff, proving) rather than one ExecPlan.
  Rationale: the work spans four distinct subsystems (parser/loader, scaffolder,
  differ, fixtures/docs), exceeds five milestones, and scaffold/diff can proceed in
  parallel once the foundation exists — coordination is the hard problem, which is the
  MasterPlan threshold in `agents/skills/master-plan/MASTERPLAN.md`.
  Date: 2026-07-29

- Decision: The workspace input is a manifest file with an explicit member list, not
  repeated `--spec` flags or a directory glob.
  Rationale: `diff --since <rev>` must reconstruct the member set as it existed at the
  old revision, which only works if the membership is itself a versioned file; a stable
  workspace identity must outlive member renames, which flags cannot provide; and
  globs make membership order- and filesystem-dependent, violating IR-2's determinism
  principle. Exact syntax is EP-1's decision, recorded in its ADR.
  Date: 2026-07-29

- Decision: Member files remain complete, independently valid `.keiro` specs; the
  composer requires context agreement and rejects duplicate declarations even when
  they are textually identical (single-owner rule, no silent merge).
  Rationale: IR-2 explicitly prefers refusal over first-wins or silent merging;
  keeping members independently checkable preserves the single-file toolchain and
  review ergonomics, and matches ADR-12's one-schema-authority stance — a shared
  declaration must have exactly one owning file producing one nominal generated type.
  Date: 2026-07-29

- Decision: Whole-workspace "atomicity" means all refusals are detected before the
  first write (extending the existing plan-then-write architecture across members);
  staged temp-file/rename writes are out of scope.
  Rationale: verification on 2026-07-29 showed `ScaffoldRun.hs` already separates pure
  planning from execution for a single spec and IR-2's acceptance wording ("detected
  before any generated file, manifest, or record is changed") matches
  detection-before-write, not filesystem transactions. Introducing staging would be
  scope creep orthogonal to composition.
  Date: 2026-07-29

- Decision: Scaffold records become workspace-keyed with per-module source ownership;
  the single-file path keeps its current context-keyed names and bytes.
  Rationale: IR-2 requires that moving an aggregate between files is not misclassified
  as another spec's stale output, which needs ownership in the record; unchanged
  single-file naming preserves backward compatibility for every existing consumer
  (Kotei, Danwa) until they opt into a workspace.
  Date: 2026-07-29

- Decision: EP-2's scaffold-history and adoption model is recorded as its own ADR
  ([ADR-15](../adr/0015-workspace-scaffold-history-is-workspace-keyed-with-attributable-adoption.md))
  rather than as an amendment to EP-1's ADR-14, and it fixes the record file naming that
  ADR-14 left open.
  Rationale: the `docs/adr` profile is one decision per file, and the two records have
  different lifecycles — ADR-14 answers "what is a workspace", ADR-15 answers "what does a
  workspace leave on disk". The Integration Points section allowed either; the fallback of
  amending ADR-14 for naming was unnecessary because ADR-14 deliberately said nothing about
  record file names.
  Date: 2026-07-29

- Decision: EP-3 and EP-4 keep EP-2's exact ownership vocabulary: an ownership move is
  path-unchanged-with-changed-owner, an absent owner means context-level, and neither is a
  content change.
  Rationale: the scaffold record is the durable statement of what the workspace produced;
  a diff that classified the same event differently would contradict a file on disk that a
  human can read. Recorded here because it is the integration point EP-2 and EP-3 share
  without depending on each other.
  Date: 2026-07-29


## Outcomes & Retrospective

Summarize outcomes, gaps, and lessons learned at major milestones or at completion.

**Initiative completed 2026-07-29.** All four child plans are Complete. A service can
now keep complete aggregates in separate same-context member files under one versioned
manifest, and `parse`, `check`, `scaffold`, and `diff` treat that manifest as one service
contract. Composition resolves shared declarations once with single-owner enforcement
and multi-file diagnostics. Scaffolding plans the full module set, emits context-level
modules once, keeps collision-proof workspace-keyed history with per-module ownership,
adopts attributable legacy output without deletion, and proves refusal-before-write.
Diff reconstructs both member sets from Git, classifies shared evolution at every owned
use site, and separates ownership/authority motion from wire evolution.

EP-4 closed the initiative with a bullet-by-bullet IR-2 traceability sweep, 373 green DSL
examples, a falsification check of determinism and atomicity assertions, and documentation
for single-file, fresh workspace, and legacy-adoption workflows. The final ADR
distillation pass found the durable context already recorded: ADR-14 owns workspace
identity/canonical single-owner composition; ADR-15 owns workspace-keyed history and
attributable adoption; ADR-4 owns the composed diff boundary and its advisory codes;
ADRs 12 and 13 continue to constrain schema authority and reporting-first coverage.
No new ADR was warranted for acceptance evidence or documentation wording.

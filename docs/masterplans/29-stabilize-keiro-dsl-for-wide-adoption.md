# Stabilize keiro-dsl for wide adoption

This MasterPlan is a living document. The sections Progress, Surprises & Discoveries,
Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.
If durable project context changes, update or create ADRs in docs/adr/ in the same change.


## Vision & Scope

The 2026-08-04 pre-adoption audit (five parallel reviews of the generator, generated output,
evolution contract, and validation layer, plus an empirical re-scaffold of Mori's committed
workspace) found that keiro-dsl's identity layer — frozen fold fingerprints, systematic diff
classification, append-only language versions — is already adoption-ready, but seven concrete
gaps stand between today's toolchain and a release that services can adopt and evolve without
churn. This initiative closes all seven.

After the initiative is complete: the next keiro-dsl release scaffolds Mori's existing workspace
unchanged (today's unreleased naming enforcement refuses it because the contract field `family`
in `mori://shinzui/mori`, project-relative path `domain/project-signals.keiro` (artifact-level
source URI pending), normalizes to a conservatively reserved Haskell word, and
renaming the field would break the Kafka wire contract on `mori.project.v1`); a spec author can
give any field an independent generated Haskell selector while keeping its wire key, so a
reserved-name refusal is always actionable and never wire-breaking; `keiro-dsl check` states the
effective language contract it applied, can refuse specs below a CI-required language floor, can
escalate warnings to failures, and reports every refusal that `scaffold` would raise, so a green
`check` means a green scaffold; the generated aggregate harness treats replay-only initial
transitions correctly with one source-wide transition layout (ExecPlan 191); the committed
conformance corpus (~38 compiled suites) regenerates through one tool instead of by hand, making
intentional output changes cheap; generated behavior-contract and harness modules meet the bar a
maintainer expects of hand-written code (signatures, annotated behavior keys, failure messages
carrying state/command/actual-versus-expected, `-Wall`-clean imports, read-model facts that
compare against runtime values); and every construct the grammar accepts is either enforced,
diagnosed, or explicitly documented as descriptive-only — none silently does nothing.

Out of scope: proposed feature IRs (dynamic router fan-out, structural consumer-owned types,
multi-stream coordination, first-class aggregate time, typed command outcomes, async projection
apply, terminal outbox rejection); version-aware fleet upgrade tooling (IR-5 in
`docs/improvement-requests/add-version-aware-keiro-dsl-upgrade-and-fleet-rewrite-tooling.md`);
deferred maintainability work (splitting `Scaffold.hs`, options-record entry points, a shared
wire-schema intermediate representation, import-planner adoption in integration emitters); and
any Keiki semantics or dependency-bound change.


## Decomposition Strategy

The initiative decomposes into eight ExecPlans by functional concern, each independently
verifiable: field-identity aliases plus a corrected reserved-name policy (the release blocker),
the already-planned transition-layout repair (ExecPlan 191, adopted into this MasterPlan), the
CLI language-contract and warning-enforcement surface, closing the `check`-versus-`scaffold`
refusal gap, conformance-corpus regeneration tooling, generated-output polish, the
accepted-but-inert surface triage, and the sidecar rename with one ledger durability contract
(ExecPlan 198, added 2026-08-05 from revised IR-19).

The boundaries follow three principles. First, merge work that must change the same decision:
the reserved-name regression fix and alias support are one plan (EP 192) because both live in the
same field-identity model and validation site — trimming the reserved list without aliases leaves
genuine keywords like `case` as wire-breaking dead ends, and aliases without trimming keep false
refusals for contextual keywords like `family`. Second, keep gates separate from generators:
EP 193, 194, and 197 change what `check` says and refuses without touching generated bytes, so
they can land in any order relative to the output-changing plans (191, 192, 196). Third, make
churn cheap before spending it: EP 196 rewrites the two roughest generated modules across the
whole committed corpus, so it hard-depends on EP 195's regeneration tooling and soft-depends on
the other output-changing plans to batch fixture refreshes.

With eight plans, work is grouped into three phases. Phase 1 unblocks the release (EP 192,
EP 191, EP 193). Phase 2 makes the gates truthful and the sidecars honest (EP 194, EP 197,
EP 195, EP 198 — all parallel). Phase 3 spends one deliberate churn event on generated-output
quality (EP 196).

Relevant local ADRs, read during decomposition:

  EP 194 and EP 197 are direct applications; EP 192's reserved-name refusal stays at `check` but
  becomes actionable. Its append-only `DiagnosticCode` inventory constrains every plan that adds

  replay-only edges are inversion-only with live-first fallback; EP 191 makes the generated

- [ADR 0012](../adr/0012-structural-consumer-mappings-use-one-schema-authority-and-total-bindings.md)

## Dependency Graph

The only hard dependency is EP 196 on EP 195. EP 196 rewrites the generated
`BehaviorContract.hs` and `Harness.hs` templates and prunes import emission across every module
family, which invalidates most of the ~38 committed conformance suites at once; without EP 195's
regeneration tool that refresh is a multi-day hand edit, which is exactly the churn tax this
initiative exists to remove.

Soft dependencies order work to avoid rework, not to block it. EP 196 should follow EP 191
because both restructure `keiro-dsl/src/Keiro/Dsl/Harness.hs` emission (191 changes which
declarations exist; 196 changes how they read), and should follow EP 192 so alias-aware codec
output is regenerated once, not twice. EP 194 and EP 197 benefit from EP 193's machine-readable
`check` report and severity policy landing first, so their new diagnostics are born into the
final rendering contract rather than migrated later; both can proceed independently against the
existing text rendering if EP 193 is delayed. EP 196 should also follow EP 198, because EP 198
renames the sidecar files present in every committed scaffold history: batching that rename
into the same EP-195-driven corpus refresh spends the fixture churn once.

EP 192, EP 191, EP 193, EP 195, and EP 198 are mutually independent and can proceed in parallel today.
EP 194 and EP 197 both concentrate edits in `keiro-dsl/src/Keiro/Dsl/Validate.hs`; they can
proceed in parallel but should coordinate merge order (see Integration Points).

Phase 1 (release unblock): EP 192, EP 191, EP 193. Completing Phase 1 permits the next
keiro-dsl release: Mori's workspace scaffolds again, replay-only initial edges generate correct
harnesses, and adopters get an honest, CI-enforceable `check`. Phase 2 (truthful gates): EP 194,
EP 195, EP 197 in parallel. Phase 3 (one churn event): EP 196, after which the corpus is
regenerated once, EP-195's clean-tree policy gate is activated, and the release is tagged
as the stable adoption baseline.


## Integration Points

**Field-identity model** (EP 192 defines; EP 197 consumes). EP 192 introduces the resolved
field identity — DSL name, generated Haskell selector, wire key — in the checked graph, and owns
`haskellKeywords` in `keiro-dsl/src/Keiro/Dsl/HaskellName.hs`. Any EP 197 rule that touches
field naming must consume the resolved identity rather than raw `Grammar.hs` field names. The
identity model and reserved-word policy are durable: EP 192 records them by amending
[ADR 0019](../adr/0019-generated-haskell-has-an-explicit-edition-and-local-extension-contract.md)
and creating a new ADR for the three-namespace field identity.

**Diagnostic codes and severity** (EP 193 defines the contract; EP 192, 194, 197 add codes).
`DiagnosticCode` values are append-only per ADR 0004. EP 193 owns the `check` CLI surface: the
effective-language notice, `--min-language`, `--deny-warnings`, and the versioned JSON report
schema (`keiro-dsl/check-report/1`, keys append-only, readers ignore unknown keys). Plans that
add or move diagnostics emit them through the existing `Validate.hs` diagnostic pipeline and
must not invent parallel rendering. New codes introduced by EP 192/194/197 appear in the JSON
report without schema changes. EP 194 leaves `GeneratedPlanningInvariantViolation` as the current
registry tail; EP 197 appends after it and its new validation errors automatically suppress pure
planning through `checkServiceDiagnostics`.

**`keiro-dsl/src/Keiro/Dsl/Validate.hs`** (EP 192, 194, 197 all edit; EP 191 Milestone 2 adds
harness-helper occurrences). Rules are additive and localized, so conflicts are textual, not
semantic. Coordination rule: whichever plan merges later rebases its rule list; no plan
reorders existing rules, because diagnostic order is part of the deterministic output contract.

**`keiro-dsl/src/Keiro/Dsl/Harness.hs`** (EP 191 restructures; EP 196 restyles). EP 191 owns
which declarations are emitted (mode-aware layout consumption); EP 196 owns how emitted code
reads (shared sample constants, signatures, labels). EP 196 must start from EP 191's merged
state of `emitHarness`; this is the reason for the soft dependency.

**Conformance corpus and regeneration** (EP 195 defines; EP 191, 192, 196, 197 consume).
EP 195's tool drives the public `keiro-dsl` CLI over each committed fixture spec into its suite
directory, overwrites only banner-recognized generated files, never touches create-once modules
(ADR 0015), and reports the diff for review. Every later plan refreshes fixtures only through
this tool. The tool also owns keeping `keiro-dsl/keiro-dsl.cabal` test-component module
inventories consistent with regenerated trees.
The first honest replay found that the current committed baseline already differs in 387
files, so EP 196 Milestone 4 owns activating `check` and the `just verify` policy immediately
after its already-planned single corpus refresh; EP 195 deliberately does not land a red gate.

**Language gating of new enforcement** (EP 193 makes gating visible; EP 197 applies it).
New EP 197 refusals follow the established pattern: errors under the language-4
`StrictSpecSurfaceValidation` closure set when the defect is internally decidable and would
produce wrong or non-compiling output; warnings (CI-escalatable via EP 193) when the surface is
merely inert. Surfaces deliberately left descriptive-only must be named as such in
documentation and in the ADR 0004 inventory row that EP 197 amends.

**Fold and wire identity neutrality** (all plans). No plan changes fold fingerprints, wire
bytes, snapshot discriminators, or behavior keys for existing specs. Each output-changing plan
proves this with the existing normalized byte-equality and fold-baseline goldens
(`keiro-dsl/test/fixtures/fold-identity-baseline.golden`); EP 192 additionally proves that an
alias-free spec generates byte-identical output.

## Surprises & Discoveries

Discoveries made while drafting the child plans (2026-08-04), each verified against the working
tree by the drafting research and recorded in the owning child plan:

- The `check`-versus-scaffold gap is narrower than the audit headline: most lowering refusals
  already have unconditional check counterparts; only the two empty-node codes need promotion.
  But drafting found a new defect — workspace `check` drops even single-member generated-path
  collisions because of an `owners > 1` filter (`keiro-dsl/src/Keiro/Dsl/Workspace.hs` region
  1065). EP-194 fixes both.
- The doubled `family` diagnostic in the Mori reproducer has a structural cause: `ContractField`
  carries no source location, so both declaring events anchor the error at the contract header
  line. EP-192 adds per-field locations (`cfLoc`), which fixes deduplication and improves every
  contract diagnostic.
- Three divergent Haskell keyword sets exist (`HaskellName.hs`, `NominalType.hs`,
  `HaskellImport.hs`); EP-192 consolidates them into one authority as part of the reserved-list
  trim.
- `eventOutputCanonical` feeds the fold fingerprint with both selector and wire-name slots; this
  drove EP-192's decision that the fold canonical stays DSL-identity-only and the default
  selector is the raw DSL bytes, keeping aliases replay-neutral and alias-free specs
  byte-identical.
- The audit's "oversized windows lower to zero" claim was wrong in mechanism: `readMaybe @Int`
  wraps rather than failing (`ghc -e` evidence in EP-197), so the `"0"` fallback arm is
  unreachable for parsed windows and the real failure mode is a garbage wrapped delay. Same
  remedy (bounded validation), corrected diagnosis.
- The audit's claim that `runReadModelFacts` is orphaned was wrong: two hand-owned suite drivers
  call it. EP-196 keeps the runner and repairs only the vacuous fact rows.
- The regeneration corpus is 34 committed scaffold histories reproduced by 41 public-CLI
  invocations and compiled by 35 cabal test suites (the audit estimated ~38 suites). One
  generated module — the structural tree's `ArtifactCatalog.BehaviorContract` — is compiled by
  no component at all; EP-195 surfaced it and EP-196 Milestone 3 closes it (cascaded 2026-08-04,
  see EP-196's revision note).
- An existing test pins empty `check` stderr for compatibility-only fixtures
  (`keiro-dsl/test/Main.hs` region 611-635); EP-193's effective-language notice deliberately
  changes that tested contract, so the pin moves with it.
- Post-closure review of EP-192 found two implementation omissions in the otherwise-complete
  three-namespace identity contract: scalar/projection renderers still used raw command DSL names,
  and a legal event-version bump suppressed a simultaneous selector advisory. The follow-up routes
  all affected expression emitters through one selector lookup and classifies the advisory
  independently of event-version movement; focused regressions pin both behaviors.
  The complete DSL unit suite passes with 565 examples and zero failures after the repair.
- EP-191's compiled fixture work showed that generated harness values are deterministic type
  defaults rather than guard-solved samples, so complementary proof guards must deliberately
  admit those defaults. It also made one intentional single/workspace byte difference visible:
  workspace composition relocates source-line evidence in `BehaviorContract.hs`. The parity test
  keeps all other aggregate modules byte-exact and normalizes only that diagnostic line while
  pinning exact behavior keys and `EdgeRef`s.
- EP-193's machine report needs no schema adaptation for EP-194 or EP-197: diagnostic codes are
  open strings, related source/workspace locations already share one entry shape, and workspace
  member provenance is append-only. Both children can add validation codes through the existing
  `keiro-dsl/check-report/1` builders.
- EP-194's case-fold proof showed that `GeneratedOccurrenceCollision` and generated-path
  collision evidence necessarily coexist for duplicated case variants. The shared source checker
  now matches the pre-existing workspace rule: that one validation error does not block planning,
  so `GeneratedPathCollision` can name every colliding file and claimant; every other validation
  error still suppresses planning. The duplicated aggregate claims nine generated paths, so the
  deterministic contract is one located diagnostic per path rather than one summary diagnostic.
- EP-195 found that the generated corpus trees were committed but 33 of the 34 authoritative
  scaffold-record/build-manifest pairs were ignored and absent from Git, so the planned
  `git ls-files` discovery could not work in CI. EP-195 now force-tracks only the bounded corpus
  sidecars, preserves the global ignore rule for ordinary scaffold output, and excludes one stale
  nested skeleton pair in favor of the root eight-invocation history.
- EP-195's first complete 41-invocation replay changed 387 tracked files (944 insertions,
  417 deletions): current-version banners and additive record/manifest rows plus generated
  facts already assigned to EP-196. The run also found 108 generated paths outside actual
  Cabal component closures: 107 deliberate non-target surfaces in narrow legacy suites and
  the one unexpected structural BehaviorContract already assigned to EP-196. EP-195 restored
  every generated byte, records each exemption by path, and transfers policy-gate activation
  to EP-196 after the single batched refresh.

  Date: 2026-08-04

  wire-breaking dead ends; aliases without trimming keep false refusals for contextual keywords
  (`family`, `via`). The motivating regression — Mori's `family` contract field — is a contract
  field, which IR-6 as written does not cover.
  Date: 2026-08-04

  Date: 2026-08-04

  Rationale: EP 196 invalidates most committed conformance suites at once; hand-refreshing them

  Date: 2026-08-04

  Date: 2026-08-04

  Date: 2026-08-05

  its clean-tree `check`/Justfile/`verify` gate in EP-196 Milestone 4 immediately after the

  Rationale: The first complete replay proved that a gate wired today is necessarily red, while

  template changes. EP-196's hard dependency is the working driver, which is complete; moving
  activation preserves one churn event and a green repository.
  Date: 2026-08-05


## Outcomes & Retrospective

selector, and wire-key identities under language 4; the generated-Haskell keyword policy admits
contextual words that compile, while explicit aliases provide a wire-stable escape for hard
keywords. Generation, diff, replay-impact, documentation, ADRs, and IR-6 all use the same resolved
identity contract. The 560-example DSL suite, all conformance components, the repository build,
and both generated-code policy checks pass. Strict improvement-request validation retains one
unrelated baseline failure in IR-19 for a missing recommended `reviews` field; EP-192's plan
records the exact exception. The remaining master-plan children are not yet implemented.

selector advisories across legal event-version bumps. These corrections preserve the existing wire
and fold contracts and are covered by focused regressions plus the green 565-example DSL unit
suite.

interleaved live and replay-only initial edges, with all 19 obligations filled, one live initial
acceptance probe, no legacy-only probe, and replay edges attributed at indices 1 and 2. Its
single/workspace idempotence proof, 29-fact generated service package, fold baseline, and
falsification script are green.

source-wide outgoing-edge identity, and require semantic plus lexical duplicate-declaration
preflight. The replay-safety/toolchain guides and both changelogs publish the same contract, and

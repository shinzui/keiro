# Keiro 0.18.0.0 → 0.19.0.0

This edge moves the upstream cohort: Kiroku 0.8 → 0.9 (with its new schema migration `0012`),
Shibuya 0.9 → 0.10, `shibuya-pgmq-adapter` 0.16.0.0 → 0.16.1.0, and the `pg-migrate` family
1.1 → 1.2. Keiro's own API changes are two record fields in `keiro`.

The Kiroku half is **entailed**: the `kiroku-upgrade` edge `0.8.0.2 -> 0.9.0.0` runs before this
one and owns every Kiroku source and database step, including the cutover for migration `0012`.
Do not repeat or paraphrase that work here. This edge covers what remains once Kiroku is done:
Keiro's composed migration plan, the Shibuya 0.10 upgrade, Keiro's own record changes, and the
dependency overrides the 0.18.0.0 edge authorized and this release retires.

## Precondition

Apply this edge when the project depends on any Keiro package. Each step states which package or
surface makes it applicable. Report an inapplicable step as not applicable and continue; do not
exit nonzero merely because the project does not use that surface. Start from a clean working tree
and confirm the entailed Kiroku edge completed, or was reported not applicable, before editing.

## Step 1 — Align dependencies

Update every Keiro package the project consumes to the 0.19.0.0 lockstep set, and move the cohort
bounds the project names directly:

- `kiroku-store >=0.9.0.1 && <0.10` and `kiroku-store-migrations ^>=0.6.0.0`. The floor is
  0.9.0.1, not 0.9.0.0: it carries the idle-publisher retention fix.
- `shibuya-core ^>=0.10.0.0`, `shibuya-pgmq-adapter ^>=0.16.1.0`, and, if used,
  `shibuya-kiroku-adapter ^>=0.5.1.5` (the first adapter release on both Shibuya 0.10 and
  Kiroku 0.9.0.1).
- `pg-migrate`, `pg-migrate-embed`, `pg-migrate-cli`, `pg-migrate-import-codd`, and
  `pg-migrate-test-support` at `^>=1.2.0.0`.
- If the project depends on `pgmq-migration`, raise its floor to `>=0.6.1.1 && <0.7`. 0.6.1.1 is
  the first release that accepts `pg-migrate` 1.2; with 0.6.1.0 the plan cannot solve against
  `keiro-migrations`.
- `keiki >=0.9 && <0.10` and the rest of the `pgmq-*` family at `>=0.6 && <0.7` are unchanged.

**Remove** `pg-migrate-test-support:ephemeral-pg` from the project's `allow-newer` if the
0.17.0.0 → 0.18.0.0 edge added it: `pg-migrate-test-support` 1.2 accepts `ephemeral-pg` 0.3.
This edge authorizes **no** `allow-newer` entries. Report any solver conflict rather than adding
`allow-newer`, source-repository overrides, or unreviewed pins.

## Step 2 — Keiro's composed migration plan

For projects that run Keiro's composed migration plan (`keiro-migrations`, `keiro-migrate`, or
`keiro-test-support` fixtures), the plan now carries Kiroku `0012` ahead of Keiro's own
migrations and grows from 43 to 44 entries. Update tests that assert the plan's length, a
pending-migration count, or an offset into the plan (`drop 11` over the Kiroku prefix becomes
`drop 12`). No Keiro migration payload changed, so no recorded checksum moves and no ledger fixup
is required for Keiro's own component.

A persistent database is handled by the entailed Kiroku edge's cutover. Do not run the composed
`up` against one as part of this edge.

## Step 3 — Adapt Shibuya 0.10 consumers

This step applies to projects that import `Shibuya.*` directly — typically worker entry points
that call `runApp`, `stopAppGracefully`, or inspect processor state. Code that only uses Keiro's
workers, routers, process managers, and job runners needs nothing here; Keiro's own public API is
unchanged by the Shibuya upgrade.

- `ShutdownConfig` gains a strict `totalShutdownTimeout :: NominalDiffTime`, bounding adapter
  shutdown plus graceful drain before a forced supervisor stop. Record construction must supply
  it. Prefer updating `defaultShutdownConfig` (30s drain, 60s total). Where the project sets its
  own `drainTimeout`, choose a total that is at least that large and fits inside the deployment's
  termination grace period.
- `ConfigError` gains `DuplicateProcessorId`; `PolicyError` gains `InvalidConcurrency` and
  `ConcurrencyCapacityOverflow`. Extend exhaustive matches, typically in startup error reporting.
  Startup now rejects duplicate processor IDs; if that surfaces, give each processor a distinct
  ID rather than suppressing the error.
- `ProcessorState`'s `Processing` constructor gains a third field (a sampled last-progress
  timestamp). Extend constructor patterns; JSON consumers see an additive `lastProgress` key.
- A permanent framework-owned finalization failure now throws `ProcessorFailure` carrying the
  failed message's identity, instead of being absorbed as a graceful `ProcessorHalt`. Review
  code and alerts that treat a halt as benign or a failure as fatal, and supervision strategy
  choices, in that light.

## Step 4 — Adapt Keiro record construction

- `keiro`'s `RunCommandOptions` gains `seedVerifyInFlightLimit :: Int`. Prefer record update of
  `defaultRunCommandOptions`, which supplies the process-wide default of one in-flight sampled
  snapshot verification. Zero restores the old unbounded behavior; do not choose it without a
  reason recorded in the project.
- `KeiroMetrics` gains `snapshotSeedSkipped` and `snapshotSeedVerificationFailed`. Code that
  obtains metrics through `newKeiroMetrics` needs nothing; code that constructs the record
  directly must supply both.

## Step 5 — Re-scaffold DSL services

For projects with a `.keiro` spec, re-scaffold. The provenance banner on every generated file
restamps from `0.18.0.0` to `0.19.0.0`; generated code imports only Shibuya modules that did not
change, so the restamp is the only expected difference. Any other generated change is a defect
to report, not something to hand-edit. Commit the source, hand-owned fills, ledger, and
generated changes together.

## Validate

Run the consumer's normal build and tests, including every database-backed suite: a missed
migration-count assertion fails at run time, not compile time. If a worker entry point changed in
Step 3, run it long enough to stop it gracefully and confirm shutdown completes within the new
total deadline.

This repository uses `cabal build all`, `just verify`, and `nix flake check` as the reference
gates. Do not add `allow-newer`, hand-edit generated files, mutate Keiro or Kiroku tables with ad
hoc SQL, or apply migration `0012` to a database the entailed Kiroku edge has not established is
disposable.

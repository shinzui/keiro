# Keiro 0.12.0.0 → 0.13.0.0

This edge is almost entirely an **upstream absorption**. Keiro 0.13.0.0 moves the
package set onto `kiroku-store` 0.8.0.0 and `kiroku-store-migrations` 0.4.0.0;
Keiro's own API is unchanged apart from one behavioral fix that follows from
that move.

The Kiroku work itself is **not in this prompt**. This edge entails
`kiroku-upgrade` `0.7.0.1 -> 0.8.0.0`, which Seihou runs before this one under
Kiroku's own guidance. Assume it has been applied: the project's exhaustive
`StoreError` matches already carry the new constructor, and its migration ledger
question has already been answered. Do not redo that work here. If you find it
has *not* been done, stop and report — do not perform it yourself.

## Precondition

Report this edge **not applicable** when the project does not depend on any
Keiro package. Depending on Kiroku alone is not enough; such a project needs
`kiroku-upgrade` directly, not this blueprint.

## Step 1 — Confirm the version window

Seihou's normal workflow is that you bump the dependency first and then migrate
the source up to it, so the project's build plan usually already resolves Keiro
0.13.0.0 by the time this edge runs.

Check. If the project still declares 0.12-era bounds, raise them now — every
Keiro package it depends on, in lockstep, because their internal bounds are
locked to each other and a partial bump will not solve:

`keiro-core`, `keiro`, `keiro-pgmq`, `keiro-migrations`, `keiro-dsl`,
`keiro-ops`.

If the project names `kiroku-store` or `kiroku-store-migrations` directly, those
bounds move too — to `>=0.8 && <0.9` and `^>=0.4.0.0`. `kiroku-store-migrations`
0.3.2.0 and 0.3.2.1 are deprecated on Hackage and must not be resolved.

Do not touch bounds on libraries this edge does not name.

## Step 2 — Transient store failures now retry instead of halting

### What changed inside Keiro

`kiroku-store` 0.8.0.0 types PostgreSQL's class-40 transaction-rollback codes —
`40001` (`serialization_failure`) and `40P01` (`deadlock_detected`) — as a new
`StoreError` constructor, `TransientTransactionFailure`, rather than as
`UnexpectedServerError`.

`Keiro.ProcessManager.isTransientStoreError` classifies the new constructor as
**transient**. That is a real behavior change, not just a compile fix:
`isTransientStoreError` returned `False` for `UnexpectedServerError`, and
`decideForFailures` treats a non-transient, non-rejection failure as systemically
deterministic — so a serialization failure or deadlock surfaced by the store used
to finalize `AckHalt` and **stop the subscription**. It now finalizes `AckRetry`
and the source event is retried after the configured
`WorkerOptions.transientRetryDelay`.

### What this project must do

For most projects: **nothing.** A process manager or router built with Keiro's
own worker gets the new behavior by upgrading.

Check for these three cases, in this order:

1. **A project-owned `StoreError` or `CommandError` classifier.** If this project
   defines its own function deciding whether a Keiro or Kiroku error is worth
   retrying — rather than using `isTransientStoreError` / `isTransientCommandError`
   — it needs the new constructor treated as transient. The entailed
   `kiroku-upgrade` edge covers matches on `StoreError` itself; what remains here
   is a classifier over Keiro's `CommandError` that inspects the wrapped
   `StoreFailed`, `RetryExhausted`, or `ConflictFixpoint` payload.

2. **A direct `runCommand` caller that classifies the result.**
   `Keiro.Command.isRetryableConflict` is deliberately **unchanged**: it covers
   optimistic-concurrency conflicts (`WrongExpectedVersion`,
   `StreamAlreadyExists`), which need the aggregate re-hydrated and the decision
   recomputed. A transient rollback is a different condition, so `runCommand`
   still returns `Left (StoreFailed (TransientTransactionFailure code message))`
   for its caller to handle. If this project calls `runCommand` outside a Keiro
   worker and inspects the failure, add that case and retry it.

3. **Tests asserting the old classification.** A test asserting that a
   `40001`/`40P01` condition halts a worker, or expecting
   `UnexpectedServerError "40001"`, now asserts the wrong thing. Grep the test
   sources for `40001`, `40P01`, `AckHalt`, and `UnexpectedServerError` together.

### What not to do

- Do not reclassify `UnexpectedServerError` generally. Only those two SQLSTATEs
  moved out of it; everything else it carries is still "investigate, do not
  retry".
- Do not change `transientRetryDelay`, retry limits, or backoff to compensate.
  A condition that previously halted now retries; if that retry rate is wrong
  for this project, that is a tuning decision to raise with its owners, not a
  change to make silently inside an upgrade.

## Step 3 — The composed migration plan grows by one

`keiro-migrations` composes Kiroku's plan **ahead of** Keiro's. Kiroku 0.4.0.0
adds migration `0011`, so the composed plan grows from 40 migrations to 41, and
the extra entry lands in the Kiroku prefix — which shifts every offset into the
Keiro half.

This matters only if the project asserts something about the composed plan. Look
for:

- a hard-coded count of pending or applied migrations;
- an index or offset into the plan (`drop 10` over Kiroku's prefix becomes
  `drop 11`; an offset that skipped the whole Kiroku half moves by one);
- an expected list of migration ids;
- an assertion on the Kiroku schema comment, which becomes
  `Managed by pg-migrate component kiroku through 0011`.

Update those fixtures and run the project's migration suite.

If the project runs `keiro-migrate` (or its own runner composing Keiro's plan)
against a **persistent** database and it now fails with
`MigrationChecksumMismatch` on `kiroku/0010`, that is the entailed Kiroku edge's
territory — it has already established whether this database is affected and
named the fixup its operator must run. Do not apply a ledger fix from inside this
edge.

## Step 4 — Regenerate, if this project uses the DSL

`keiro-dsl` 0.13.0.0 changes no generated output for this edge; the language
contract and every wire, fold, snapshot, and behavior-key identity are stable.
A project on the DSL therefore does not need to regenerate to cross this edge.

Regenerate only if the project's own build or conformance target demands it, and
if a regeneration produces a diff, report it rather than reverting it.

## Proving it

Run the project's own build and test commands — the ones this repository
actually defines, not assumed ones. At minimum the build must succeed against
the raised bounds, and any suite covering error classification or migration
plans must pass.

If the project has a disposable development database, `keiro-migrate verify`
followed by `up` against it proves the composed plan applies end to end. Do not
run either against a database holding real data as part of this edge.

Report which commands you ran, which you could not, and why.

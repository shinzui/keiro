# Keiro 0.13.0.0 → 0.14.0.0

This edge is **entirely Keiro's own**. No upstream cohort member moves: this
release keeps `kiroku-store >=0.8 && <0.9`, `kiroku-store-migrations
^>=0.4.0.0`, `keiki >=0.9 && <0.10`, and `shibuya-core ^>=0.9.0.0`. Nothing is
entailed, so everything this edge needs is in this prompt.

Keiro 0.14.0.0 adds a **terminal rejection outcome to the transactional
outbox**: a publisher can now permanently refuse a message with a validated
stable code, and Keiro records that refusal as durable audit truth instead of
retrying it to the dead-letter state. That adds constructors to two exported sum
types, fields to three exported records, and one new migration.

## Precondition

Report this edge **not applicable** when the project does not depend on any
Keiro package.

A project that depends on Keiro but **never uses the outbox** still has real
work here if it constructs `KeiroMetrics` by hand or runs `keiro-migrate`. Do
not report it inapplicable on the strength of "we don't publish to Kafka" —
check the three cases in Step 2 first.

## Step 1 — Confirm the version window

Seihou's normal workflow bumps the dependency first and migrates source up to
it, so the build plan usually already resolves 0.14.0.0 by the time this edge
runs.

Check. If the project still declares 0.13-era bounds, raise them now — every
Keiro package it depends on, in lockstep, because their internal bounds are
locked to each other and a partial bump will not solve:

`keiro-core`, `keiro`, `keiro-pgmq`, `keiro-migrations`, `keiro-dsl`,
`keiro-ops`.

Do **not** move `kiroku-store`, `kiroku-store-migrations`, `keiki`, or
`shibuya-core`: this release does not move them, and widening them here would
admit a cohort Keiro 0.14.0.0 was never built against.

### If the project pins a Hackage index-state

A pin that predates this release's upload makes the solver unable to see it at
all, and no amount of correct source editing will fix that. Advance the pin past
the last upload in this release and run `cabal update` so the local index
carries it. If the project's comment explains which cohort the pin covers,
update that comment too.

If `cabal update` reports the requested index-state is newer than the latest
known one, that is a stale local index, not a bad pin — run `cabal update` again
and retry.

### If the solve still fails, read the conflict before editing anything

A project may depend on **another library that itself depends on Keiro** —
Kioku is the common case. Such a library pins its own Keiro bounds, and until
*it* publishes a release admitting 0.14.0.0, the solver cannot satisfy both. The
conflict names the package and the bound.

That is a **hard blocker, not a bounds problem in this project**. Do not work
around it with `allow-newer`, a `source-repository-package` override, or bounds
widened beyond what the release supports. Stop, report which package blocks the
solve and which bound of its released version excludes 0.14.0.0, and say the
upgrade needs that library released first.

Report this as a stopped edge, not an inapplicable one: the precondition is met
and the work is real, it is just blocked upstream.

## Step 2 — Adopt the new terminal rejection outcome

### What changed

Four exported types grew, all in `keiro`:

- `Keiro.Outbox.PublishOutcome` gains `PublishRejected !PublishRejection`,
  alongside the existing `PublishSucceeded` and `PublishFailed`.
- `Keiro.Outbox.Types.OutboxStatus` gains `OutboxRejected`, whose wire text is
  `"rejected"` in both `statusText` and `parseStatus`.
- `Keiro.Outbox.Types.OutboxRow` gains `rejectedAt :: !(Maybe UTCTime)` and
  `rejection :: !(Maybe PublishRejection)`.
- `Keiro.Outbox.Types.OutboxPublishSummary` gains `rejected :: !Int`.
- `Keiro.Telemetry.KeiroMetrics` gains `outboxRejected`.

`Keiro.Outbox.Types` newly exports the abstract type `PublishRejection`, its
smart constructor `mkPublishRejection :: Text -> Maybe Text -> Either
PublishRejectionError PublishRejection`, the field accessors
`publishRejectionCode` / `publishRejectionDetail`, and `PublishRejectionError`.

`PublishRejection` is **abstract** — there is no exported data constructor. Build
one only with `mkPublishRejection`, which enforces the contract the database also
enforces: the code matches `^[a-z][a-z0-9._-]{0,63}$`, and the detail, when
present, is non-empty and at most 1024 UTF-8 bytes. Do not try to reach the
constructor through `Keiro.Outbox.Rejection`; that module is deliberately not
exposed.

### What this project must do

Work through these in order.

1. **Exhaustive matches over `PublishOutcome`.** Any `case` over a publisher's
   result now misses `PublishRejected`. With `-Wincomplete-patterns` the compiler
   finds every site; if the project does not build with that warning, grep for
   `PublishSucceeded` and check each match.

   Decide per site what a rejection means there. It is **not** a failure: it
   schedules no retry, consumes no attempt, and does not halt a `StopTheLine`
   publisher — the ordered successors behind it are released exactly as a
   successful publish releases them. Treating it as a failure branch will
   produce wrong retry accounting even though it compiles.

2. **Exhaustive matches over `OutboxStatus`.** Same shape — `OutboxRejected` is
   a new terminal state that sits beside `OutboxSent`, not beside `OutboxDead`.
   A rejected row was refused on purpose; a dead row exhausted its attempts.
   Anything that reports "stuck" or "needs operator attention" should count
   `OutboxDead` and not `OutboxRejected`.

3. **Direct record construction.** A project that builds `OutboxRow`,
   `OutboxPublishSummary`, or `KeiroMetrics` with explicit record syntax — most
   often in test fixtures — must initialize the new fields. `Nothing` for
   `rejectedAt` and `rejection`, `0` for `rejected`. Projects that obtain
   `KeiroMetrics` from `newKeiroMetrics` are unaffected.

4. **Assertions on `OutboxPublishSummary`.** `published + rejected + retried +
   dead` is now the count of rows the pass **durably finalized**, and it can be
   less than `claimed` when stale-claim recovery wins a race against the pass.
   The previous documented invariant was `published + retried + dead == claimed`.
   A test asserting that equality can now fail legitimately under contention.
   Assert on the individual counters, not on the identity.

### Emitting a rejection

Only if this project wants the new behavior. A publisher that should permanently
refuse a message returns `PublishRejected` with a rejection built by
`mkPublishRejection`. Choose a **stable** code — it is machine-readable audit
data operators will filter on, so it should name the condition
(`schema.unregistered`, `payload.too-large`), not restate a transport message.
Put the variable part in the detail.

`mkPublishRejection` returns `Left`; handle it rather than partial-matching. A
code the validator refuses is a bug in the calling code, not a runtime condition
to swallow.

### What not to do

- Do not reach for rejection as a way to drain a backlog of messages that are
  merely failing. It is terminal and permanent by design. A transport problem is
  `PublishFailed`; that is what backoff and dead-lettering exist for.
- Do not add a retry path for rejected rows. There is deliberately no transition
  out of `rejected`, and the database enforces the audit columns' shape.
- Do not widen the code or detail bounds. The Haskell validator and the
  `0031` CHECK constraints encode the same contract; a value that passes one and
  not the other will fail at the database.

## Step 3 — Apply migration `0031`

`keiro-migrations` 0.14.0.0 adds `0031.sql`. It is **purely additive**: no
existing migration's payload or checksum changes, so **no ledger fixup is
needed** and no database is at risk of `MigrationChecksumMismatch` from this
release. Run the project's ordinary `keiro-migrate up`.

What `0031` does to `keiro.keiro_outbox`:

- adds `rejected_at`, `rejection_code`, `rejection_detail`;
- adds three CHECK constraints tying those columns to `status = 'rejected'` and
  enforcing the code and detail bounds;
- **rebuilds** the two partial head-of-line indexes,
  `keiro_outbox_head_of_line_idx` and `keiro_outbox_source_order_idx`, so their
  predicates exclude `'rejected'` and rejected rows stop blocking ordered
  successors.

### Operational note for a large outbox

Read this before running it against production. The migration is written as a
plain `ALTER TABLE` with `ADD CONSTRAINT ... CHECK`, and it drops and recreates
both indexes **without** `CONCURRENTLY`. On a large or hot `keiro_outbox` table
that means an `ACCESS EXCLUSIVE` lock held for a full validating scan plus two
index builds, during which publishers block.

Do not rewrite the migration to avoid this — its checksum is recorded and
editing it desynchronizes every database that has applied it. Instead, size the
window: check the table's row count first, and if it is large enough to matter,
schedule the upgrade when the outbox is drained and publishers are stopped. A
drained outbox makes the whole operation fast, because the partial indexes being
rebuilt cover only non-terminal rows.

If the project asserts a **count** of pending or applied migrations, or an
expected list of migration ids, Keiro's half of the composed plan grows by one.
Update those fixtures.

## Step 4 — `keiro-ops` output gained columns

Only if the project consumes `keiro-ops` output programmatically.

`outbox list` now accepts `--status rejected`, and its output grew in both
renderings:

- the human table gains three trailing columns: `rejected_at`,
  `rejection_code`, `rejection_detail`;
- the JSON objects gain three keys of the same names.

A consumer that reads the JSON by key is unaffected. One that parses the table
positionally, asserts a column count, or snapshot-tests the output must be
updated. The new columns are appended, so existing positions do not shift.

## Step 5 — Regenerate, if this project uses the DSL

`keiro-dsl` has **no functional change** in this release — the language contract
and every wire, fold, snapshot, and behavior-key identity are stable, and the
generator emits no code that matches on `PublishOutcome` or constructs
`OutboxRow`. A DSL project therefore does not need to regenerate to cross this
edge.

It does change one line per generated file: every generated artifact carries a
`@generated by keiro-dsl <version>` provenance header, so a regeneration under
0.14.0.0 rewrites that header from `0.13.0.0` throughout. That one-line-per-file
diff is the expected shape. If a regeneration produces a diff **beyond** those
headers, report it rather than reverting it.

Regenerate only if the project's own build or conformance target demands it — a
project that pins generated output and checks it against the current toolchain
version needs the header refresh; one that does not, does not.

## Proving it

Run the project's own build and test commands — the ones this repository
actually defines, not assumed ones. At minimum:

- the build must succeed against the raised bounds, with no incomplete-pattern
  warnings introduced by the new constructors;
- any suite covering outbox publication, publish summaries, or migration plans
  must pass.

If the project has a disposable development database, `keiro-migrate verify`
followed by `up` against it proves the composed plan applies end to end. Do not
run either against a database holding real data as part of this edge; the
operational note in Step 3 is the guidance for that case.

Report which commands you ran, which you could not, and why.

# Keiro 0.14.0.0 → 0.15.0.0

This edge is entirely Keiro's own. The upstream cohort is unchanged:
`kiroku-store >=0.8 && <0.9`, `kiroku-store-migrations ^>=0.4.0.0`, `keiki
>=0.9 && <0.10`, and `shibuya-core ^>=0.9.0.0`. It entails no upstream edge.

Keiro 0.15.0.0 changes the public Haskell record model emitted and consumed by
`keiro-dsl`. Product-field selectors and owner-prefixed field labels are gone;
the replacement uses concise repeated labels with `DuplicateRecordFields`,
`NoFieldSelectors`, and `OverloadedRecordDot`. Existing generated projects also
must explicitly adopt the `idiomatic-v2` generated-Haskell edition before their
next scaffold run can write files.

## Precondition

Report this edge not applicable when the project does not depend on
`keiro-dsl`, does not contain a `keiro-dsl` scaffold ledger, and does not compile
package-authored `Keiro.Dsl.*` records. A project may need either the package API
migration or the generated-project migration, or both.

Start from a clean working tree. The edition migration records durable backups,
but neither it nor this agent can safely roll back unrelated edits.

## Step 1 — Confirm the lockstep dependency update

Raise every Keiro package dependency the project uses to the 0.15.0.0 lockstep
release: `keiro-core`, `keiro`, `keiro-pgmq`, `keiro-migrations`,
`keiro-test-support`, `keiro-dsl`, and `keiro-ops`.

Do not move the Kiroku, Keiki, or Shibuya cohort bounds: this release does not
change them. If another released package excludes the 0.15.0.0 bound, stop and
report that solver conflict; do not use `allow-newer`, a git override, or a
wider unsupported bound.

## Step 2 — Migrate package-authored `keiro-dsl` records

Search code that imports `Keiro.Dsl.*` for generated selector functions and
owner-prefixed record labels. Replace reads with record-dot syntax or
constructor-directed pattern matches, and use concise labels for construction.
The exhaustive mapping, including the twelve deliberate single-field newtype
unwrappers that remain functions, is in
`keiro-dsl`'s `record-field-migration-0.15.md` extra source file.

Enable the four required language extensions in affected components:

```cabal
default-extensions:
  DuplicateRecordFields
  NoFieldSelectors
  OverloadedRecordDot
  OverloadedStrings
```

Do not mechanically rename every same-spelled field, qualify a removed selector
to bypass the change, or add `FieldSelectors` as a compatibility escape hatch.
Those changes can silently select the wrong record type; let GHC's type errors
drive each local migration.

## Step 3 — Adopt existing generated projects

For every recorded scaffold ledger below the project, first inspect the
generated-edition and any sidecar/name migration state. Run the normal scaffold
command with `--apply-generated-haskell-edition` to migrate a pre-v2 ledger.
If the same project also needs the legacy sidecar or module-name migration, pass
both required apply flags in the same run. The tool refuses ordinary scaffolding
before writing until this explicit, backup-backed adoption occurs.

Reconcile the generated Cabal fragment: add the context structural-conformance
and behavior-source-map modules where the scaffold requires them, preserve the
new default extensions, then compile the generated runtime package and run its
conformance target. Do not hand-edit generated files or delete edition backups;
regenerate through `keiro-dsl` and keep the backups as the migration evidence.

## Step 4 — Validate

Run the project's normal build and tests, including the generated service's
runtime/conformance target when it has one. In this repository, the release is
validated with:

```sh
cabal build all
just verify
```

The successful result has no remaining package-authored selector calls, all
recorded scaffolds at `idiomatic-v2`, and generated modules plus their Cabal
inventory accepted by GHC. `.keiro` syntax, JSON and wire identities, and runtime
semantics do not change in this edge; do not rewrite them merely to cross 0.15.

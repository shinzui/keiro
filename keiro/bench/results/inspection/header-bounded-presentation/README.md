# Bounded fresh header presentation

Five allocation-attribution trials use the production default HTTP application with a running workflow header and an external sequential TCP client. The mount checks live schema and the complete current header on every request. An unchanged exact image permits reuse of canonical JSON plus its bounded encoding, with a 32-entry / 1-MiB charged retention cap. Missing, failed and oversized observations evict their presentation. The public OpsResult remains unchanged.

Reusing the complete image's own lookup identity removes redundant parameter serialization. A foreign identity starts with an incomplete image that cannot compare equal to a complete header. The owning tests compare all fields and BC/distant fractional dates against the ordinary decoder. All 16 owning-query, 51 ops and 29 HTTP tests pass, including churn, oversized changes, deletion/recreation and warm schema drift.

The median conditional point session allocates about 7.9 kB and the default HTTP header about 42 kB per request, versus about 101 kB through the uncached canonical runner. Exact values and all five samples are in summary.json. This is attribution with one running header, not the completed-header/client matrix or matched writer acceptance. Client allocations are outside RTS counters. One TCP setup is amortized over 1,000 requests. Libraries use O1, the driver O2, GHC 9.12.4 and RTS -N2 -T.

The manifest hashes the binary, retained driver and production sources. source.patch.gz includes the new cache module and reconstructs the candidate from its parent commit.

This finite-timestamp measurement predates the explicit infinity parity correction. It remains allocation attribution, not final-candidate acceptance.
